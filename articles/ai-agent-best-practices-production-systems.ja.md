# 本番システムのためのAIエージェント・ベストプラクティス：アーキテクチャ、ツール、Evals、セキュリティ、運用

AIエージェントは、単なる機能フラグでも、ベンダー製品のカテゴリでもない。モデルによる推論、ツール、コンテキスト、状態、権限、UX、評価、運用を組み合わせた本番システムである。

最も安全で効果的なエージェント導入は、実際の仕事を解決できる範囲で、最も自律性の低い設計から始めることだ。タスク、根拠、制御がそれを正当化できる場合に限り、エージェンシーを追加していく。

本ガイドは、実システムにおけるAIエージェントの設計、評価、運用、ガバナンスに責任を持つエンジニア、プロダクトチーム、プラットフォームチーム、セキュリティチーム、組織リーダーを対象としている。

内容は、タスクとアーキテクチャの選択から始まり、ツールとコンテキスト設計、人間による制御とセキュリティ、さらに評価、運用、UX、組織ガバナンスへと進む。

## 1. AIエージェントは何が違うのか

AIエージェントとは、AIモデルを中核とし、目標を解釈し、次のステップを推論し、ツールを使い、一定の自律性を持って環境内で行動できるソフトウェアシステムである。

この定義は意図的に「そのシステムに何を許可するか」に焦点を当てている。重要なのは、大規模言語モデルを使っているかどうかではない。多くのシステムが使っている。重要なのは、そのシステムが複数ステップにまたがって判断し、ツールを選び、外部システムに影響を与え、時間をかけて作業を継続し、ビジネス上の状態を変更できるかどうかである。

返金ポリシー情報を検索するだけの読み取り専用サポートアシスタントと、実際に返金を実行するエージェントは異なる。パッチを提案するコーディングアシスタントと、プルリクエストを開き、テストを実行し、コードをマージするエージェントは異なる。情報源を要約するリサーチアシスタントと、営業連絡をスケジュールしたりCRMを更新したりするエージェントは異なる。

システムが「答える」段階から「行動する」段階へ移ると、リスクは上昇する。いったんシステムがお金を使う、記録を変更する、メッセージを送る、コードを変更する、認証情報にアクセスする、外部に公開する、といったことが可能になると、エンジニアリング上の責任は変わる。ツール設計、権限、評価、オブザーバビリティ、人間による承認、インシデント対応、ガバナンスが、システムの中心的な要素になる。

### 用語についての短い補足

用語は正確に使う。

* **AIエージェント**：推論し、ツールを使い、行動できる、モデル中心のコンポーネント。
* **エージェント的ワークフロー**：モデルが制御フロー、ツール選択、推論、次の行動に動的に影響を与えるワークフロー。
* **エージェント的システム**：エージェントを取り巻くより広いプロダクトやプラットフォーム。ワークフロー、ツール、制御、実行基盤、UX、オブザーバビリティ、人間のプロセスを含む。
* **エージェンシー**：固定された経路に従うのではなく、システムがステップ、ツール、タイミング、行動を選べる度合い。
* **自律性**：人間の直接介入なしに、システムが行動し、作業を継続できる度合い。

エージェンシーはスペクトラムとして捉えるとよい。ルーティング、連鎖、計画、ツール利用、マルチエージェントのオーケストレーション、自律実行は、それぞれ分けて設計できる選択肢である。

| パターン | 制御フロー | 典型的な用途 | リスクプロファイル |
|---|---:|---|---|
| 決定論的ワークフロー | コードやルールで事前定義 | 標準フォーム、固定された承認フロー、単純な抽出 | 最低。最もテストしやすい |
| ルーティング型ワークフロー | モデルまたはルールが経路を選択 | サポートのトリアージ、意図分類、モデルルーティング | 中程度。ルーティングミスが作業を誤った方向に導く |
| 連鎖的なモデル呼び出し | 逐次的なモデルステップ | 抽出 → 検証 → 要約、下書き → 批評 → 修正 | 中程度。失敗が連鎖的に増幅される |
| ツール利用型エージェント | モデルがツールを選択して呼び出す | リポジトリ検索、CRM参照、ポリシー取得、チケット下書き | 高め。ツール選択と入力が重要 |
| マルチエージェントシステム | 複数のエージェントまたはワーカーが協調 | リサーチ統合、コードベース分析、並列ドキュメントレビュー | 高め。調整と衝突解決が重要 |
| 自律的に行動するエージェント | 限定的な人間介入でエージェントが行動 | 長時間の復旧対応、運用自動化、外部トランザクション | 最高。強力な制御と根拠が必要 |

このスペクトラムは、チャットボット、検索システム、ワークフロー自動化、実際に行動するエージェントを同じ種類のシステムとして扱うことを避ける助けになる。それぞれ、作用範囲、失敗モード、ガバナンス要件が異なる。

## 2. 仕事を解決できる最もエージェント性の低いアーキテクチャを選ぶ

タスクを解決できる最もエージェント性の低いアーキテクチャを使う。

この原則は保守的に聞こえるが、実務的である。自律性は無料ではない。評価、セキュリティ、レイテンシ、コスト、運用、ユーザーの信頼から予算を消費する。より自律的な設計が正当化されることもあるが、それは代表的なタスクと測定された改善によって証明されるべきである。

アーキテクチャのはしごから始める。下位の段では仕事を十分に解決できない場合にのみ、上位へ進む。

### アーキテクチャ選択のはしご

1. **決定論的ワークフロー**

   タスクが予測可能で、曖昧さが少なく、ルールや固定ステップで表現できる場合に使う。

   例：標準フォーム検証、パスワードリセットのルーティング、明確なポリシールールに基づく適格性チェック。

   柔軟な分類、解釈、経路選択が必要になったら上位へ進む。

2. **ルーティング型ワークフロー**

   システムが意図を分類し、経路を選び、モデルを選択し、既知のワークフローへタスクをルーティングする必要がある場合に使う。

   例：請求、アカウント、技術、返金のリクエストをそれぞれ異なるフローへ振り分けるサポート受付システム。

   各経路で、複数の依存関係を持つモデルステップや中間出力が必要になったら上位へ進む。

3. **連鎖的なモデルワークフロー**

   タスクが構造化された段階から恩恵を受けるが、制御フローはほぼ事前定義のままでよい場合に使う。

   例：文書からフィールドを抽出し、それらを検証し、結果を要約し、返信の下書きを生成する。

   システムが動的にツールを選んだり、ツール結果に応じて次のステップを適応させたりする必要が出たら上位へ進む。

4. **ツール利用型エージェント**

   モデルがツール群から選び、構造化された入力で呼び出し、出力を解釈し、タスクを継続する必要がある場合に使う。

   例：リポジトリを検索し、ファイルを編集し、テストを実行し、プルリクエストを準備するコーディングエージェント。

   並列調査、専門ロール、協調的な統合が必要で、単一のエージェントでは不十分な場合に上位へ進む。

5. **マルチエージェントシステム**

   専門化、並列性、構造化された議論が本当に結果を改善する場合に使う。

   例：別々のエージェントが情報源を検索し、主張を抽出し、矛盾を確認し、コーディネーターのもとで調査結果を統合するリサーチワークフロー。

   タスクが限定的な人間介入で時間をかけた行動を必要とし、制御が十分成熟している場合にのみ上位へ進む。

6. **自律的に行動するエージェント**

   システムが境界づけられた独立性を持って行動する必要があり、強い根拠、権限、モニタリング、復旧経路、人間によるオーバーライドが備わっている場合にのみ使う。

   例：決定論的なチェックに合格した後、ポリシーに基づいて既知のサービスを再起動できる、狭い範囲の運用復旧エージェント。

「まだエージェントを使わない」判断をするための良いテストは単純だ。仕事が予測可能で、曖昧さが少なく、ルールで表現でき、計画やツール選択を必要としないなら、決定論的ワークフローを使う。サポートシステムがパスワードリセット依頼をルーティングするだけなら、自律的な解決エージェントを作るべきではない。バックオフィスの文書処理が標準フォームを扱うなら、まず決定論的な抽出と検証を使う。計画は例外処理にだけ追加する。

ベースライン優先の開発は特に重要である。よりエージェント性のある設計にコミットする前に、単純なワークフローと比較する。顧客サポートシステムなら、ルーティングと検索から始められる。複数ステップの推論、ポリシー解釈、システム横断の更新が必要なケースだけを、エージェント的な解決器へエスカレーションすべきである。

モデル選択も同じ判断に含まれる。最大・最高性能のモデルをデフォルトで選ばない。タスクが本当に複数ステップの推論を必要とする場合に推論モデルを使う。タスクが本当にテキスト以外の知覚に依存する場合にマルチモーダルモデルを使う。検索、圧縮、状態管理では効率よく必要情報を提供できない場合に、大きなコンテキストウィンドウを使う。

実践的なローンチルールはこうだ。追加したエージェンシーは、追加されるコスト、レイテンシ、安全性の負担、評価の複雑さを正当化できるだけの成果改善をもたらさなければならない。

## 3. ループを検査可能にする

複雑なエージェントの振る舞いを、ひとつの大きなプロンプトの中に消してしまってはいけない。

自律性を高める前に、ループを見える形にする。有用なデフォルトループは次のとおりである。

1. リクエストと現在状態を観察する。
2. 関連するコンテキストを集める。
3. 計画または次のステップを決める。
4. ツール、ワークフロー、または応答を通じて行動する。
5. 結果を検証する。
6. 復旧する、助けを求める、または継続する。

正確なループは変わってよいが、段階の境界が重要である。それらは、評価、トレースレビュー、人間へのハンドオフ、リトライ、中断、本番オブザーバビリティのための面を作る。

コーディングエージェントは、「このバグを直して」から直接パッチへ飛ぶべきではない。より検査しやすいワークフローは、リポジトリの指示を確認し、関連ファイルを特定し、計画を提案し、焦点を絞った変更を行い、lintとテストを実行し、diffを要約し、プルリクエストを開く、という流れである。リサーチエージェントは、検索、抽出、統合、ファクトチェックを分離すべきである。マルチエージェント分析ワークフローでは、最終品質と衝突解決に責任を持つリードエージェントまたはコーディネーターが必要である。

問題に合ったワークフロー表現を使う。グラフノード、再利用可能なワークフロー、段階的なツール呼び出し、ルール、サブエージェントのロール、プルリクエストタスクなどである。目的はアーキテクチャごっこではない。作業を再実行可能かつレビュー可能にすることだ。

マルチエージェントシステムは、並列性、専門化、多数の情報源にまたがる統合が本当に必要な場合に有用である。自動的に優れているわけではない。調整責任者のいない複数エージェントは、重複作業、一貫しない結論、不明確な責任を生みやすい。

良い分解は、調整コストがタスク価値を上回る手前で止まる。テスト可能な5段階のワークフローは、誰にも検査できない形で交渉し合うエージェントの群れより、多くの場合優れている。

## 4. ツールを狭い契約として設計する

ツールは、AIエージェントを有用にする場所である。同時に、危険にする場所でもある。

ツールはオープンエンドな権力ではなく、狭い契約であるべきだ。明確な目的、精密なスキーマ、予測可能な出力、明示された副作用、スコープされた権限、設計されたエラー時の挙動、トレース要件を持つ必要がある。

| ツール契約の要素 | 定義すべきこと | 例 |
|---|---|---|
| ツール名 | 明確でタスク固有の名前 | `check_refund_eligibility` |
| 目的 | そのツールが実行する狭い仕事 | 注文が返金レビューの対象になるか判断する |
| 入力スキーマ | 必須フィールド、任意フィールド、検証ルール | `order_id`, `customer_id`, `reason_code` |
| 出力スキーマ | コンパクトで構造化された応答 | `eligible`, `reason`, `policy_reference`, `next_allowed_action` |
| 副作用 | ツールが読み取り、書き込み、送信、支払い、状態変更を行うか | 読み取り専用の適格性チェック。返金は実行しない |
| 権限境界 | 誰または何が、どの条件で呼び出せるか | サポートエージェントのロール。対象顧客アカウント範囲のみ |
| エラー時の挙動 | 想定される失敗とリトライ規則 | `ORDER_NOT_FOUND`, `POLICY_SERVICE_TIMEOUT` |
| 拒否時の挙動 | ポリシーがアクションをブロックしたときに何が起きるか | 拒否理由と許可されたフォールバックを返す |
| ロギング／トレーシング要件 | 監査とデバッグのために記録すべきこと | ツールバージョン、入力ハッシュ、ポリシー判断、トレースID |

ツールのリスクは副作用に大きく依存する。読み取り専用検索ツール、下書き作成ツール、決済ツール、管理者権限ツールが、同じ承認モデルやロギングモデルを共有すべきではない。

繰り返し行う操作には、目的特化のツールを優先する。返金ワークフローで本当に必要なのが、適格性を確認し、返金リクエストの下書きを作り、人間の承認へ回すことなら、エージェントに決済システムへの生アクセスを与えるべきではない。リポジトリ検索ツールは、ファイル全体をコンテキストウィンドウに流し込むのではなく、簡潔なシンボル、ファイル、行のコンテキストを返すべきである。データベースツールは、そのリスクに対して環境、権限、レビュー過程が設計されている場合を除き、生SQL実行ではなく、検証済みのビジネスクエリを公開すべきである。

ツール出力はコンパクトで曖昧さのないものにする。大きなペイロードはコンテキストを浪費し、モデルに構造を推測させる。曖昧なペイロードは、エージェントが結果を読み違えたり、誤った次ステップを取ったりする可能性を高める。

失敗、拒否、部分成功の経路を通常の挙動として設計する。拒否された返金ツール呼び出しが、ワークフロー全体を崩壊させてはいけない。何がブロックされたのか、なぜなのか、次に何ができるのかをエージェントに伝えるべきである。追加情報を求める、エスカレーションする、メモの下書きを作る、停止する、といった選択肢である。

ツール利用は直接評価する。エージェントが正しいツールを選ぶか、有効な入力を渡すか、出力を正しく解釈するか、エラーを扱えるか、拒否後に復旧できるかをテストする。最終回答が一見妥当でも、トレースを見るとエージェントが誤ったツールを呼んだり、ポリシー応答を無視したりしていることがある。

## 5. コンテキスト、メモリ、状態を分離する

エージェントに必要なのは、常にすべての情報を与えることではなく、適切なタイミングで適切な情報を与えることである。

コンテキストエンジニアリングとは、エージェントが利用できる情報環境全体を設計することである。そこには、指示、検索・取得された事実、例、制約、会話履歴、ツール出力、中間成果物、状態、メモリが含まれる。プロンプトエンジニアリングは、その一部にすぎない。

これらのカテゴリを明示的に分ける。

| 情報の種類 | 内容 | 典型的な保存場所 |
|---|---|---|
| アイデンティティとロール | エージェントが誰として行動するか | システム設定 |
| タスク指示 | エージェントが何をすべきか | プロンプトまたはワークフロー設定 |
| 制約とポリシー | エージェントがしてはならないこと | ポリシーレイヤーとプロンプト |
| 検索・取得された事実 | このタスクのために取得された情報 | 検索結果またはツール出力 |
| セッション履歴 | 直近のやり取りのコンテキスト | 会話状態 |
| 永続状態 | 持続的なタスク進捗 | データベースまたはワークフローストア |
| メモリ | ターン、セッション、実行をまたいで保持される情報 | 検証付きのメモリストア |
| 中間成果物 | 計画、下書き、要約、抽出データ | 成果物ストア |
| 外部知識 | 文書、コード、チケット、CRMレコード | ソースシステムとインデックス |

コンテキストウィンドウをアプリケーション状態全体として使ってはいけない。長いコンテキストウィンドウは有用だが、状態スキーマ、検索、圧縮、キャッシュ、永続化の必要性をなくすものではない。

サポート返金エージェントで考えると、この区別は具体的になる。

* **コンテキスト**：現在のユーザーリクエスト、関連する返金ポリシーの抜粋、直近の会話ターン。
* **検索・取得された事実**：注文ステータス、支払い方法、発送状態、過去の返金履歴。
* **永続状態**：ケースステータス、承認待ち、割り当てキュー、最後に完了したワークフローステップ。
* **メモリ**：ポリシーが保存を許可している場合の、検証済みユーザー設定。
* **成果物**：返金説明または承認リクエストの下書き。

コーディングエージェントは、関連ファイルとリポジトリ指示を取得すべきだが、進捗、判断、テスト結果はプロンプト外に永続化すべきである。長時間実行されるリサーチエージェントは、調査結果を構造化された成果物として保存し、中断後に再開できるようにすべきである。

設計時には実践的な問いを立てる。

* このステップのコンテキストに何を入れるべきか。
* 何を永続状態に入れるべきか。
* 必要なときだけ取得すべきものは何か。
* 圧縮または要約すべきものは何か。
* キャッシュすべきものは何か。
* 検証なしにメモリへ書き込んではならないものは何か。
* どの取得コンテンツを信頼できないものとしてラベル付けすべきか。

メモリには特別な注意が必要である。メモリストアは継続性を改善できるが、誤った情報、機密情報、悪意ある情報を保持してしまうこともある。メモリ書き込みを検証する。メモリへのアクセス範囲を絞る。メモリストアを汚染から守る。特にユーザー、Webページ、チケット、メール、文書、ツール出力に由来する場合、取得コンテンツは潜在的に信頼できないものとして扱う。

状態は構造化され、検査可能であるべきだ。状態を単なるプロンプト形式の文字列ではなく、アプリケーションデータとして保存する。呼び出し時に状態をプロンプトへ整形する。これにより、中断、再開、監査、移行がはるかに容易になる。

## 6. 人間による制御をワークフローに組み込む

人間による制御は、悪い結果が起きた後に後付けするものではなく、ローンチ前に設計すべきものである。

重大な影響を持つアクションには、事前定義された制御点が必要である。ユーザーとオペレーターは、ワークフローを崩壊させることなく、エージェントの振る舞いを承認、拒否、中断、修正、エスカレーション、復旧できなければならない。

次の用語を一貫して使う。

* **レビュー**とは、出力、トレース、計画、判断を検査することである。
* **承認**とは、実行前に特定のアクションを許可することである。
* **エスカレーション**とは、所有権を人間またはチームへ移すことである。
* **中断**とは、実行中のタスクを安全に停止または一時停止することである。

実践的な制御モデルでは、アクションを4つのカテゴリに分ける。

| アクションカテゴリ | 説明 | 例 |
|---|---|---|
| 自動承認 | エージェントが直接実行してよい低リスクなアクション | 公開ヘルプセンター記事を取得する |
| ポリシーチェック付き | 決定論的なポリシーチェックに合格した場合のみ許可 | 承認済みポリシーを使って標準回答を下書きする |
| 人間による承認付き | 実行前に明示的な人間の承認が必要 | 返金を実行する、顧客クレジットを送る、プルリクエストを開く |
| 禁止 | このエージェントには決して許可しない | 本番へマージする、顧客レコードを削除する、セキュリティ設定を変更する |

お金を使う、顧客データを変更する、外部公開する、本番システムを変更する、セキュリティ上重要な資産に影響する、法務・コンプライアンス上の露出を生むアクションには、明示的な承認しきい値を設けるべきである。

承認は曖昧な監督ではない。センシティブなアクションの前に置かれる、具体的な認可ステップである。承認なしにお金を返せない返金エージェントでも、適格性を説明し、リクエストを下書きし、適切なキューへルーティングすることはできるべきだ。

拒否時の挙動を設計する。ユーザーが提案アクションを拒否した場合、エージェントは次に何をすべきか知っている必要がある。提案を修正する、確認質問をする、下書きを保存する、人間へエスカレーションする、停止する、といった対応が考えられる。

中断時の挙動を設計する。ユーザーは長時間タスクを停止し、進捗を確認し、安全に再開できるべきである。ローカル変更を行ったコーディングエージェントは、プルリクエストを開く前に、何を変更したか、どのテストを実行したか、何がまだ不確実かを報告すべきである。

エスカレーション時の挙動を設計する。サポートボットは、信頼度が低い、ユーザーが不満を持っている、ポリシー例外が要求されている、タスクがリスク境界を越える、といった場合にエスカレーションすべきである。

## 7. エージェントシステムを安全にする

エージェントは言語理解と行動を組み合わせる。つまり、信頼できないコンテンツが判断、ツール呼び出し、メモリ書き込み、副作用に影響を与えうる。

エージェントの振る舞いを形成しうる面を脅威モデリングする。

* ユーザー入力
* 取得された文書
* Webページ
* メールとチケット
* ツール出力
* メモリ書き込み
* 認証情報とシークレット
* ネットワークアクセス
* コード実行
* ブラウザまたはコンピューター利用
* 外部への副作用
* 本番データ

プロンプトインジェクションは、単なるプロンプトの問題ではない。文書に隠された悪意ある指示は、エージェントのタスクを上書きし、データを持ち出し、ツールを呼び、メモリを汚染し、判断を変えようとする可能性がある。「モデルが適切に判断するはずだ」を防御策にしてはならない。多層の制御を使う。

最小権限を適用する。タスクに必要な最小限のツール、データ、権限、認証情報、ネットワークアクセスだけをエージェントに与える。読み取り能力と書き込み能力を分離する。認証情報をユーザー、テナント、環境、アクション種別にスコープする。信頼できない検索と広い権限を組み合わせることは避ける。

マルチテナントシステムではテナント分離を使う。ある顧客にサービスを提供するエージェントが、共有インデックス、キャッシュされたコンテキスト、ログ、ツール出力、メモリストアを通じて別顧客のレコードを取得できてはならない。分離はモデルへの指示だけでなく、モデルの外側で強制する。

シークレットはプロンプト文ではなくインフラとして扱う。APIキー、セッショントークン、認証情報をモデルから見えるコンテキストに置かない。短命の認証情報、スコープされたサービスアカウント、シークレットマネージャー、サーバー側の認可チェックを使う。

データ流出経路を制御する。どのツールがメッセージ送信、ファイルアップロード、外部URL呼び出し、共有システムへの書き込みをできるかを制限する。必要に応じて、ツール許可リスト、外向き通信制限、ネットワークポリシー、出力フィルターを使う。ブラウザ自動化エージェントに、無制限のインターネットアクセスと本番認証情報を同じ環境で与えてはならない。

モデルの推論と認可ロジックを分離する。モデルはアクションを提案できるが、そのアクションが許可されるかは決定論的なポリシーチェックで判断すべきである。センシティブなアクションは、リクエスト者、ポリシー判断、ツールバージョン、承認イベント、トレースIDを記録した監査ログを生成すべきである。

リスクのある実行にはサンドボックス化を使う。ブラウザエージェント、コーディングエージェント、ファイルを操作するエージェントは、可能であれば使い捨てまたは分離された環境で実行する。エフェメラルコンテナ、ローカルVM、専用テストモード、使い捨てブラウザ環境、分離された本番エンドポイントを使う。信頼できないコードを、本番認証情報を持つセンシティブな環境でエージェントに実行させてはならない。

取得コンテンツは権威ではなくデータとして扱う。取得されたポリシー文書は回答を支えることができる。しかし、支払いを認可したり、アクセス権を付与したり、システムポリシーを上書きしたりすべきではない。外部およびユーザー提供コンテンツは、エージェントのコンテキスト内で信頼できないものとしてラベル付けする。

ガードレールはポリシーを強制し、安全でないアクションをブロックすべきだが、権限やサンドボックス化の代替ではない。権限はアクションが許可されるかを決める。サンドボックス化は何かが実行された場合の被害を制限する。ガードレールは振る舞いを制約し、チェックし、リダイレクトし、またはブロックする。

最後に、安全な失敗を設計する。ブロックされたアクションは、拒否理由と許可された復旧経路を返すべきである。拒否して継続する挙動は、エージェントが境界を越えずに有用であり続ける助けになる。

## 8. ワークフロー全体を評価する

エージェントは最終回答生成以外の多くの場所で失敗する。評価はシステム全体を対象にしなければならない。

有用な評価戦略には次が含まれる。

* 実作業から作った代表的なタスクセット
* エッジケースと既知の失敗
* エンドツーエンドのワークフローEvals
* 段階ごとのEvals
* ばらつきを測るための反復実行
* ツール利用チェック
* 状態遷移チェック
* 安全性とポリシーテスト
* レイテンシとコスト測定
* 主観的または高リスクな出力に対する人間によるレビュー
* プロンプト、モデル、ツール、コンテキスト、ガードレール、ポリシー変更に対する回帰テスト

1回うまく動いたからといって成功と宣言してはいけない。エージェントは確率的システムである。同じタスクでも、反復実行の中で、異なる計画、ツール呼び出し、コスト、レイテンシ、結果を生む可能性がある。

評価マトリクスは、チームが最終回答に過度に集中することを避ける助けになる。

| 観点 | 測定すること | シグナル例 |
|---|---|---|
| 最終回答の品質 | 正確性、明瞭さ、グラウンディング、有用性 | 人間のルーブリックスコア、スポットチェック付きのモデル評価器 |
| タスク完了 | 仕事が実際に完了したか | チケット解決、PR作成、レポート提出 |
| 計画品質 | 計画が適切かつ効率的だったか | 不要なステップがない、リスク認識が正しい |
| ツール選択 | 正しいツールが選ばれたか | 正しい検索、CRM、返金、リポジトリツール |
| ツール入力の正確性 | ツール引数が有効かつ安全だったか | スキーマ検証、ポリシー準拠のパラメータ |
| 状態の正確性 | 状態が実際の進捗を反映しているか | ワークフロー状態がツール結果と一致 |
| 復旧挙動 | 失敗、拒否、不確実性を扱えたか | エスカレーション、リトライ、質問、停止が正しく選ばれた |
| 安全性とポリシー遵守 | 境界が守られたか | 禁止アクションなし、プロンプトインジェクション耐性 |
| レイテンシ | 有用な応答またはタスク完了までの時間 | P50/P95のエンドツーエンドおよび段階別レイテンシ |
| コスト | モデル、ツール、インフラ、リトライのコスト | 完了タスクあたりのコスト |
| UX | ユーザーがエージェントを理解し、信頼し、制御できるか | UXテスト、満足度、エスカレーション品質 |

実際のタスクから早期にEvalsを作る。サポートエージェントでは、よくあるリクエスト、エッジケース、ポリシー例外、不満を持つユーザー、欠落データ、安全でない要求を含む匿名化ケースを使う。コーディングエージェントでは、同じリポジトリに対して反復タスクを実行し、パッチ品質、テスト実行、プルリクエスト挙動のばらつきを測る。リサーチエージェントでは、トレースを採点し、検索、抽出、統合、ファクトチェックの失敗を特定する。

リスクに合った評価方法を使う。スキーマ、状態遷移、拒否されたアクション、必須ツール呼び出しには決定論的チェックが向いている。定性的な出力にはモデル評価器が役立つこともあるが、キャリブレーションと人間によるレビューが必要である。主観的、重大、曖昧なタスクでは、人間によるレビューが引き続き重要である。

本番での観察は、次のEvalsセットに取り込むべきである。インシデント、ユーザー修正、ツール失敗、エスカレーション、予想外のトレースは、回帰テストの材料になる。

## 9. トレースとテストからデバッグする

評価は何かが失敗したことを教えてくれる。デバッグは、どこで、なぜ失敗したかを教えてくれる。

エージェントが失敗したとき、最初にランダムにプロンプトを書き換えてはいけない。

まず失敗箇所を特定する。それから、テスト可能な最小の変更を加え、変更前後のトレースを比較する。

どこで失敗したのかを問う。

* モデルに必要な能力があったか。
* 正しいコンテキストがあったか。
* 指示は明確で優先順位が付いていたか。
* ツール契約は明確だったか。
* 権限は十分で、かつスコープされていたか。
* 状態は正しかったか。
* 計画は適切だったか。
* エージェントはテスト、検証、確認からフィードバックを受け取ったか。
* 復旧は機能したか。
* 統合結果は根拠と一致していたか。

実装エージェントでは、explore-plan-codeパターンまたは同等の手法を使う。エージェントはリポジトリを調べ、関連ファイルを特定し、計画を提案し、焦点を絞った変更を実装し、必要なテストとlintコマンドを実行し、プルリクエストを開く前に根拠を報告すべきである。パッチが「正しそうに見える」からといって、テストを省略してはならない。

会話エージェントでは、既知の失敗に対する回帰テストを維持する。エスカレーション漏れ、安全でないコンプライアンス助言、誤った返金適格性、不適切なハンドオフ、拒否後の復旧失敗などである。

ツール利用型エージェントでは、多くの失敗がツールインターフェースの失敗である。エージェントが繰り返し無効なパラメータを渡すなら、スキーマが不明確かもしれない。出力を誤解するなら、応答形状が冗長または曖昧すぎるかもしれない。誤ったツールを選ぶなら、ツール名または説明を修正する必要があるかもしれない。契約を修正し、トレース比較で変更を検証する。

大がかりな書き換えより、小さな変更がよい。プロンプト、ツールスキーマ、検索戦略、状態表現、モデル、ポリシーチェック、オーケストレーションのうち、ひとつだけを変更する。変更前後で同じEvalsを実行する。重要な失敗ごとに、対象を絞った回帰ケースを保持する。

## 10. オブザーバビリティとレジリエンスを持って運用する

エージェントは、分散され、確率的で、ツールを使うシステムである。本番エンジニアリングが必要だ。

### すべてをバージョン管理する

エージェントを明示的な成果物としてパッケージ化する。

* プロンプトと指示のバージョン
* モデルバージョンと設定
* ツールバージョンとスキーマ
* ポリシーとガードレールのバージョン
* 状態スキーマ
* 検索インデックスとデータソースのバージョン
* 評価メタデータ
* デプロイ環境
* オーナーとエスカレーション経路

### ワークフローをトレースする

エージェントをブラックボックスとして運用してはならない。オブザーバビリティには、ログ、トレース、メトリクス、ツール呼び出し記録、エラー、状態遷移、ポリシー拒否、承認イベント、モデルバージョン、プロンプトバージョン、リリース識別子が含まれるべきである。

本番のリサーチエージェントには、トレースID、リリースバージョン、コストダッシュボード、フォールバック経路、プライバシーに配慮したログが必要である。オペレーターは次の問いに答えられるべきだ。エージェントは何を取得したのか。どのツールを呼んだのか。各ツールは何を返したのか。このリリースと前回リリースの差分は何か。実行コストはいくらだったのか。どこで失敗したのか。

### リトライと副作用を制御する

実行時失敗を想定しておく。

* ツールのタイムアウト
* レート制限
* 一時的なモデルエラー
* 継続的なプロバイダー障害
* 検索失敗
* 状態ストアエラー
* リトライ増幅
* コスト急増
* レイテンシ回帰
* プロンプトまたはモデル変更後の品質ドリフト

リトライには規律が必要である。失敗したモデル呼び出しやツール呼び出しのリトライは、一時的な失敗には有効な場合がある。しかし制御されていないリトライは、負荷、コスト、副作用を増幅する。変更を伴うアクションには冪等性キーを使う。リトライ可能なエラーと不可能なエラーを分ける。リトライしても品質改善が見込めない場合はフォールバックを使う。

たとえばCRM更新処理は、タイムアウト後にリトライが発火したために、重複したメモを作成したり、重複した顧客メールを送信したりすべきではない。変更を伴うツールは冪等性キーを受け取り、ワークフローがそのアクションがすでに起きたかどうかを判断できるだけの状態を返すべきである。

### レイテンシ、コスト、プライバシーをモニタリングする

トラフィックは段階的に増やす。季節的なスパイクの前に、カスタマーサービスエージェントを負荷テストする。レート制限とキュー挙動をテストする。事業継続性が必要な場合は、リージョンフェイルオーバーまたは代替プロバイダーを使う。

ロギングとトレーシングはプライバシーに配慮しなければならない。機密データは編集または最小化する。ハッシュ、参照、構造化サマリーで十分な場合は、生のシークレット、不要な個人データ、全文書を保存しない。

運用上のフィードバックはリリース判断に反映すべきである。本番トレースに、ツール失敗、ポリシー拒否、エスカレーション、コスト急増が繰り返し現れるなら、次回リリース前にそれらのケースをEvalsと回帰テストへ追加する。

## 11. 信頼と復旧のためにUXを設計する

ユーザーは、エージェントに何ができるのか、今何をしているのか、なぜブロックされたのか、どう修正すればよいのか、どうエスカレーションすればよいのかが分からないと信頼を失う。

信頼できるUXは、能力、境界、進捗、不確実性、復旧を、適切な詳細度で見えるようにする。

ユーザーの意図とジャーニーマッピングから始める。ユーザーはエージェントに何ができると思っているのか。エージェントには実際に何をする権限があるのか。ユーザーはどこで停止、修正、承認、エスカレーションを必要とする可能性があるのか。

オンボーディングでは能力と制限を明確にすべきである。サポートエージェントは、自分がポリシーを検索するだけなのか、回答を下書きできるのか、チケットを作成できるのか、実際にアカウントを変更できるのかを説明すべきである。社内アシスタントは、「この文書を要約できる」と「CRMを更新できる」を区別すべきである。

長時間または複数ステップの作業では、進捗を見せる。ユーザーはすべての内部トークンやトレースイベントを必要としているわけではない。しかし、検索中、ポリシー確認中、下書き中、承認待ち、テスト実行中、エスカレーション中、完了といった状況把握は必要である。

明示的なUX状態を設計する。

| 状態 | ユーザーのニーズ |
|---|---|
| 確認 | 「私からどの情報が必要ですか？」 |
| 進行中 | 「今、何をしていますか？」 |
| 承認待ち | 「承認すると、どのアクションが実行されますか？」 |
| ブロック中 | 「なぜこれはできないのですか？」 |
| エラー | 「何が失敗し、次に何ができますか？」 |
| エスカレーション済み | 「今は誰が担当していますか？」 |
| 完了 | 「何が変更されましたか？」 |
| 復旧可能 | 「取り消し、修正、再開、リトライはできますか？」 |

承認は具体的にする。たとえば、「25ドルの返金を実行する準備ができました。これにより顧客アカウントが更新され、確認メールが送信されます。承認しますか？」のようにする。

透明性には層がある。エンドユーザーには、状況把握、理解しやすい説明、復旧経路が必要である。オペレーターには、トレース、ツール呼び出し、状態遷移、リリースメタデータが必要である。すべてのユーザーに生の運用トレースを見せる必要はないが、意味のある進捗と制御を隠してはいけない。

UXテストはデプロイ準備であり、ローンチ後の仕上げではない。自律性を広げる前に、会話挙動、ブロックされたアクション、修正フロー、不満、エスカレーション、キャンセル、復旧をテストする。

## 12. ガバナンスと共有標準でスケールさせる

小さなチームは初日から完全なコントロールプレーンを必要としないかもしれない。しかし、共有された可視性と標準へ成長できる形で設計すべきである。

各チームが異なる定義、ツール、権限、Evals、ログ、デプロイ実践で個別に構築すると、エージェントリスクは複合的に増加する。ガバナンスは、責任あるチームがより速く動けるようにするものであり、実験を凍結するものではない。

組織には、エージェント種別、ユースケース、アクション境界、リスク階層に関する共有定義が必要である。読み取り専用の検索アシスタントが、顧客レコードを変更したり本番インフラを変更したりするエージェントと同じレビューを受けるべきではない。しかし、その区別は明示的でなければならない。

実践的なガバナンスモデルには次が含まれる。

* 標準エージェントカテゴリ：読み取り専用、ツール利用型、行動実行型、自律型
* データアクセス、副作用、ユーザー影響、可逆性に基づくリスク階層
* 承認済みツールテンプレート
* スコープされた認証情報パターン
* リスク階層ごとの評価要件
* ロギングとトレーシング要件
* 人間による承認ポリシー
* セキュリティベースライン
* インシデント対応経路
* オーナーシップと廃止ルール
* デプロイゲートとロールアウト段階

導入が広がるにつれて、コントロールプレーンまたは同等の集中可視化が重要になる。組織は、どのエージェントが存在し、誰が所有し、どのツールを呼べて、どの認証情報を使い、どのEvalsでゲートされ、どのインシデントを経験し、まだ必要とされているかを把握すべきである。

所有権は明確でなければならない。各エージェントには、データアクセス、ツール、承認、保守、インシデント、コスト、廃止に責任を持つオーナーが必要である。共有プラットフォームチームはテンプレートと実行基盤を提供できるが、ユースケースの振る舞いに対する説明責任はプロダクトチームにも残る。

ロールアウトは段階的に行う。低リスクな社内ユースケースから始める。より広い社内ワークフローへ拡張する。その後、制御が成熟するにつれて、顧客向けまたは行動実行型のシステムへ進む。サポートアシスタントなら、読み取り専用のポリシー検索から始め、回答下書き、チケット作成、承認付き返金リクエストへ進み、さらに後になってポリシー下で狭い自動承認アクションを実行する、という流れになる。

良いガバナンスは、速度低下と標準化を区別する。ツール契約、Evalsハーネス、権限、オブザーバビリティ、デプロイ、インシデント対応の再利用可能なテンプレートは、重複作業を減らし、安全な導入を容易にする。

本記事は、エージェント設計、評価、セキュリティ、運用、UX、ガバナンスに関する公開エンジニアリングおよびプロダクトガイダンスを統合して作成したものである。付随するソースインデックスには、統合に使った公開記事を一覧化すべきである。

## 13. エージェント準備チェックリスト

このチェックリストは、リリース準備レビューの簡潔な確認項目として使える。チームは、影響の大きいシステム向けに、これをより長いリスク階層別レビューへ拡張できる。

### エージェントを選ぶ前に

* 具体的な言葉で、達成すべき仕事を定義する。
* システムが読み取り専用、ツール利用型、行動実行型のどれに該当するかを特定する。
* より単純な決定論的、ルーティング型、検索型、連鎖型ワークフローをベースラインとしてテストする。
* 推論、マルチモーダル、長いコンテキスト、ツール選択、自律性が本当に必要か判断する。
* 追加のエージェンシーを正当化する改善とは何かを定義する。

### 設計中

* ワークフローを検査可能な段階へ分解する。
* スキーマ、副作用、権限、エラー時の挙動、拒否時の挙動、トレーシングを備えた狭いツール契約を定義する。
* コンテキスト、検索・取得された事実、メモリ、永続状態、中間成果物を分離する。
* お金、顧客データ、外部公開、本番システム、セキュリティ上重要なアクションに対する承認しきい値を定義する。
* エスカレーション、中断、修正、復旧、フォールバック経路を設計する。
* 信頼できない入力、ツール出力、メモリ書き込み、認証情報、コード実行、外部副作用を脅威モデリングする。

### デプロイ前

* 実タスク、エッジケース、既知の失敗、拒否されたアクション、安全でない入力、反復実行からEvalsを作る。
* 計画、検索、ツール選択、ツール入力、状態遷移、復旧挙動、安全性、レイテンシ、コスト、UXを評価する。
* プロンプトインジェクション、安全でないツール利用、メモリ汚染、過剰な権限に対する敵対的テストを実行する。
* コード実行、ブラウザ利用、変更を伴うアクション、認証情報、本番データを分離する。
* モニタリング、ロギング、トレーシング、編集・マスキング、ダッシュボード、リリースメタデータ、ロールバック計画、オーナーシップを準備する。

### 本番運用中

* トレース、ツール失敗、権限拒否、レイテンシ、コスト、リトライ、フォールバック、エスカレーション、ユーザー修正をモニタリングする。
* リトライがコスト、負荷、副作用を増幅しないようにする。
* インシデント、サポート観察、予想外のトレースを回帰テストへ取り込む。
* モデル、プロンプト、ツール、ポリシー、検索、コンテキストの変更をEvalsでゲートする。
* フォールバック経路と人間へのエスカレーションを維持する。

### 組織的ロールアウト中

* エージェント種別、アクション境界、オーナーシップ、セキュリティベースライン、承認ポリシーを標準化する。
* デプロイ済みエージェント、ツール、認証情報、Evals、リリース、インシデントに対する可視性を維持する。
* ツール契約、権限、ロギング、トレーシング、Evals、デプロイ、インシデント対応の再利用可能なテンプレートを提供する。
* 制御が成熟するにつれて、低リスクなシステムから影響の大きい自動化へ段階的にロールアウトする。
* 既存エージェントを単純化、拡張、一時停止、廃止すべきかレビューする。

## 14. 結論

効果的なAIエージェントは、より大きなモデル、より多くのツール、より自律的なループを追加するだけでは生まれない。

仕事に合わせてエージェンシーを調整し、ツールとコンテキストを慎重に形作り、人間による制御を保ち、ワークフロー全体をテストし、システムを可視的に運用し、共有標準によって導入をスケールさせることで生まれる。

本番エージェントが信頼できるのは、優れたプロンプトを持っているからではない。権限が境界づけられ、ツールが狭く、状態が検査可能で、アクションが制御され、振る舞いが評価され、失敗が観測可能だからである。

仕事を解決できる最も自律性の低いシステムから始める。そして、追加するエージェンシーの一段階ごとに、根拠をもって獲得する。

## 15. 用語集

| 用語 | 意味 |
|---|---|
| AIエージェント | AIモデルを基盤とし、目標を解釈し、次のステップを推論し、ツールを使い、一定の自律性を持って環境内で行動できるソフトウェアシステム。 |
| エージェント的ワークフロー | AIモデルが制御フロー、ツール選択、推論、次のアクションに動的に影響を与えるワークフロー。 |
| エージェント的システム | ツール、ワークフロー、制御、実行基盤、オブザーバビリティ、UX、人間のプロセスを含む、エージェントを取り巻くより広いプロダクトまたはプラットフォーム。 |
| エージェンシー | 固定された経路に従うのではなく、システムがステップ、ツール、タイミング、行動を選べる度合い。 |
| 自律性 | AIエージェントが人間の直接介入なしに判断し、行動し、作業を継続できる度合い。 |
| 作用範囲 | エージェントが影響を与えうる外部システム、レコード、ユーザー、環境、副作用の集合。 |
| 副作用 | メッセージ送信、データ更新、支出、コード変更など、ツールまたはエージェントのアクションによって引き起こされる変更。 |
| 権限境界 | エージェントがアクセスできるデータ、ツール、認証情報、環境、アクションに対する明示的な制限。 |
| ツール利用 | エージェントがAPI、データベース、コード実行、ブラウザ、ファイル、アプリケーションなどの外部機能を使う広範な設計パターン。 |
| ツールスキーマ | モデルがツールを正しく呼び出す助けとなる、ツール名、入力、出力、制約の構造化された記述。 |
| コンテキストエンジニアリング | 指示、検索・取得された事実、ツール出力、メモリ、状態、コンテキストウィンドウ制限を含む、エージェントが利用できる情報環境全体の設計と管理。 |
| メモリ | 直近のモデル呼び出し、ターン、セッション、実行を超えて保持される情報。 |
| 状態 | 進捗、中間結果、判断、保留中のアクションを含む、エージェント実行の現在の表現。 |
| 評価 | エージェントの品質、信頼性、安全性、タスク成功、回帰を体系的に測定するプロセス。 |
| オブザーバビリティ | トレース、ログ、メトリクス、ツール呼び出し記録、実行時診断を通じてシステム挙動を理解できる能力。 |
| ガードレール | 安全でない挙動を制約、リダイレクト、ブロックするためのポリシー、チェック、分類器、ルール、実行時制御。 |
| ポリシーチェック | アクションが許可されるかを判断する、決定論的または監査可能な判断。 |
| プロンプトインジェクション | 信頼できないコンテンツがエージェントの指示を上書き、操作、または無効化しようとする攻撃または失敗モード。 |
| トレース | ステップ、ツール呼び出し、入力、出力、状態変更、判断を含む、エージェント実行の構造化記録。 |
| 冪等性 | 重複した副作用を引き起こさず、安全にリトライできる操作の性質。 |
| 人間によるレビュー | 出力、トレース、計画、判断を人間が検査すること。 |
| 人間による承認 | センシティブなアクションが実行される前に、人間が認可すること。 |
| エスカレーション | タスク、判断、インシデントをエージェントから人間またはチームへ移すこと。 |
| リスク階層 | データの機密性、副作用、可逆性、ユーザー影響に基づいて制御を設定するためのカテゴリ。 |
| コントロールプレーン | エージェント全体にわたる可視性、ポリシー、設定、ガバナンス、ライフサイクル管理のための共有システム。 |
