# 11. GitHub Markdown記法見本

このページは、GitHub と同じ Markdown 記法で書ける表現の見本です。  
リポジトリ独自のスタイルを当てる場合でも、Markdown本文では `tone-*` のような独自コードフェンスを使わず、GitHub Flavored Markdown の記法に合わせます。

> [!IMPORTANT]
> スタイルは後からCSSや変換処理で調整できます。  
> ただし、Markdown本文の記法はGitHub上でそのまま読める形にそろえます。

## 使い分けの早見表

| 表現したい内容 | 使うMarkdown記法 | 向いている文章 |
| --- | --- | --- |
| 補足、背景、前提 | `> [!NOTE]` | 読み飛ばしてもよいが、知っておくと理解しやすい情報 |
| コツ、推奨、効率化 | `> [!TIP]` | 実務でうまく進めるためのヒント |
| 必須の原則、重要な判断基準 | `> [!IMPORTANT]` | そのページで必ず覚えてほしい内容 |
| よくある失敗、注意点 | `> [!WARNING]` | 問題を避けるために注意すべき内容 |
| 危険、損失、重大な副作用 | `> [!CAUTION]` | セキュリティ、削除、権限、コストなどの重大リスク |
| 順番のない項目 | `-` の箇条書き | 条件、観点、要素の列挙 |
| 順番が重要な作業 | 番号付きリスト | 手順、プロセス、優先順位 |
| 確認項目 | タスクリスト | レビュー、抜け漏れ防止、作業チェック |
| 項目と説明の対応 | 表 | 比較、属性、キーと値の整理 |
| コードや設定例 | 言語名付きコードブロック | JSON、YAML、シェルコマンド、Markdown例 |

## NOTE: 補足を書く

補足情報は `NOTE` を使います。  
本文の理解を助ける情報や、前提として知っておくと読みやすい情報に向いています。

> [!NOTE]
> PoCは、まず「1回成功すれば価値が伝わる」状態を作ることが目的です。  
> 本番運用に必要な監視、権限、コスト制御は、次の段階で確認します。

## TIP: コツや推奨を書く

実務上のコツや、作業を進めやすくするヒントは `TIP` を使います。

> [!TIP]
> デモでは、最初からすべての例を見せるより、代表例を1つ選んで成功体験を先に見せると伝わりやすくなります。

TIPの中で箇条書きを使うこともできます。

> [!TIP]
> PoCで見せる内容は、次のように絞ると分かりやすくなります。
>
> - 1回成功する
> - デモで動く
> - 代表例で便利に見える
> - 人間が横で見ている

## IMPORTANT: 最重要の原則を書く

ページの中核になる原則や、必ず守る判断基準は `IMPORTANT` を使います。

> [!IMPORTANT]
> AIエージェントは、最終結果だけでなく、途中で何が起きたかを確認できる形で設計します。

IMPORTANTは強い表現なので、多用しないようにします。  
目安として、1ページあたり1〜3個までにします。

## WARNING: よくある失敗を書く

問題を避けるために注意すべき内容は `WARNING` を使います。  
本番運用、権限管理、監視、コスト確認のような内容と相性がよいです。

> [!WARNING]
> PoCで動いた構成を、そのまま本番環境へ移すと失敗しやすくなります。  
> 本番では、失敗検知、再実行性、権限制御、ログ保存、コスト予測を確認してください。

## CAUTION: 重大なリスクを書く

危険、損失、セキュリティ上の問題、削除操作などは `CAUTION` を使います。  
読者に強く止まって確認してほしい場面に限定します。

> [!CAUTION]
> 削除、外部送信、権限変更を伴う処理は、人間の確認ポイントなしで自動実行しないでください。

## 箇条書き: 順番のない項目を書く

順番が重要でない項目は、通常の箇条書きで書きます。  
独自のコードフェンスで囲まず、Markdown標準の `-` を使います。

- 失敗時に検知できる
- 何度実行しても安定する
- コストが予測できる
- 権限が制御されている
- ログが残る
- 人間確認ポイントがある
- 改善前後を比較できる

## 番号付きリスト: 手順を書く

順番が意味を持つ作業は、番号付きリストで書きます。

1. 調査する
2. 修正する
3. 検証する
4. レビューする

## タスクリスト: 確認項目を書く

レビューや抜け漏れ防止には、GitHubのタスクリストを使います。

- [ ] 誰が監視するかを決める
- [ ] 失敗時に誰へ渡すかを決める
- [ ] どの指標を見るかを決める
- [ ] いつ評価を回すかを決める
- [ ] どのログを保存するかを決める
- [ ] どの権限を許すかを決める
- [ ] どの変更をレビューするかを決める

質問として洗い出したい場合も、独自記法ではなく通常の箇条書きで書きます。

- 誰が監視するか？
- 失敗時に誰へ渡すか？
- どの指標を見るか？
- いつ評価を回すか？
- どのログを保存するか？
- どの権限を許すか？
- どの変更をレビューするか？

## 表: 段階や比較を見せる

リスクの段階や、項目と説明を対応させたい場合は表を使います。

| リスク | 例 | 確認ポイント |
| --- | --- | --- |
| 低 | ファイルを読む | 読み取り対象が意図どおりか |
| 中 | ローカルファイルを編集する | 差分を人間が確認できるか |
| 高 | ファイルを削除する | 実行前に人間の承認があるか |

## 定義: 見出しと本文で説明する

用語や概念を定義したい場合は、見出しと本文で自然に説明します。  
独自の `markdown.definition` コードフェンスは使いません。

### Goal

AIに任せたときでも、期待した結果にたどり着ける状態。

### Constraints

権限、ログ、コスト、再実行性など、運用前に確認すべき制約。

## 項目と説明: 表または箇条書きで整理する

短い属性の一覧は、表にすると流し読みしやすくなります。

| 項目 | 説明 |
| --- | --- |
| 目標 | 1回成功させる |
| 確認 | デモで動く |
| 監視 | 人間が横で見る |

本文に近い説明なら、箇条書きでも十分です。

- **目標**: 1回成功させる
- **確認**: デモで動く
- **監視**: 人間が横で見る

## コード例: 本当にコードだけを囲む

コード、設定、APIレスポンス、コマンド例はコードブロックにします。  
コードブロックには、できるだけ `json`、`yaml`、`bash`、`md` などの言語名を付けます。

```json
{
  "status": "ok",
  "next": "verify"
}
```

Markdown記法そのものを説明したい場合だけ、`md` のコードブロックを使います。

```md
> [!IMPORTANT]
> ここに重要な内容を書く。
```

## まとめ

- 補足は `NOTE` を使う
- コツは `TIP` を使う
- 最重要の原則は `IMPORTANT` を使う
- よくある失敗は `WARNING` を使う
- 重大なリスクは `CAUTION` を使う
- 通常の列挙は `-` の箇条書きを使う
- 手順は番号付きリストを使う
- 確認項目はタスクリストを使う
- 比較や段階は表を使う
- 本当にコードや設定例の場合だけコードブロックを使う

Markdown本文はGitHub上でそのまま読める記法にそろえ、見た目の調整はCSSやビルド処理側に寄せます。
