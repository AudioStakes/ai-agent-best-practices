# 06. コーディングエージェント系

エージェントと一緒にソフトウェア開発を進める方法を考える章です。コード生成、レビュー、テスト、リファクタリング、任せる範囲を扱います。

この章を読むことで、調査から検証までを含む作業の組み立て方を見直せます。詳細な参照元は章末の引用リンクを参照してください。

> **対象時点: 2026年5月**  
> この章は、2026年5月時点で公開されている主要な公式ドキュメントをもとに整理しています。最新の仕様や推奨事項は、各公式ドキュメントを確認してください。

## この章で見直せること

- リポジトリ文脈を渡せているか
- 実装前に調査や計画を挟んでいるか
- テスト、lint、ビルドまで含めているか
- 変更範囲と禁止事項が明確か
- 人間レビューと承認の線引きがあるか

## 結論

結論から言うと、コーディングエージェント系で一番大事なのは、**「AIにコードを書かせること」ではなく、「調査・変更・検証・安全確認まで回せる作業環境を作ること」**です。

## どの記事でも共通

### 1. リポジトリ文脈を明示的に与える

**重要度: 5**

コーディングエージェントで最重要です。

AIはコードだけ見ても、プロジェクトの前提を知りません。

必要なのは、たとえばこういう情報です。

```tone-good.guideline
- プロジェクトの目的
- ディレクトリ構成
- 主要な設計方針
- 触ってよい範囲
- 触ってはいけない範囲
- テストコマンド
- lint / format コマンド
- PRやコミットのルール
- よくある失敗
```

ここが弱いと、AIは「それっぽい修正」はできますが、プロジェクトに合った修正ができません。

コーディングエージェントでは、**プロンプトより先にリポジトリ文脈**です。

---

### 2. いきなり実装させず、まず調査・計画させる

**重要度: 5**

かなり多くの記事で共通するポイントです。

悪い依頼はこうです。

```tone-neutral.takeaway
このバグを直して
```

良い依頼はこうです。

```tone-neutral.guideline
まず関連ファイルを調査してください。
原因を特定し、修正方針を説明してください。
その後、最小変更で修正し、テストを実行してください。
```

つまり、流れはこうです。

```tone-neutral.process
調査
↓
原因説明
↓
修正方針
↓
実装
↓
検証
```

いきなりコードを書かせると、既存設計を無視したり、不要に大きい変更をしがちです。

コーディングエージェントには、まず **読む・考える・計画する** をやらせるのが大事です。

---

### 3. 小さく、明確なタスクに分ける

**重要度: 5**

コーディングエージェントに大きすぎる依頼をすると失敗しやすいです。

悪い例：

```tone-bad.risk
このアプリをいい感じに改善して
```

良い例：

```tone-good.guideline
ログイン画面のバリデーションエラー表示を改善してください。
対象は src/pages/Login.tsx と関連テストのみです。
既存APIの仕様は変更しないでください。
```

タスクを小さくすると、

```tone-neutral.guideline
- 影響範囲が読みやすい
- テストしやすい
- レビューしやすい
- ロールバックしやすい
- AIが迷いにくい
```

です。

コーディングエージェントは、広すぎる自由度より、**狭く明確な作業範囲**のほうが強いです。

---

### 4. テスト・lint・実行確認まで含める

**重要度: 5**

コーディングエージェント系で、これは絶対に外せません。

コードを書かせるだけでは不十分です。

```tone-bad.risk
- テストを実行する
- lint を実行する
- 型チェックを実行する
- ビルドする
- 必要なら手動確認手順を書く
- 失敗したら原因を見て修正する
```

までがセットです。

AIに「完了」を判断させるなら、完了条件はこういう形にすべきです。

```tone-good.guideline
- npm test が通る
- npm run lint が通る
- 対象機能の動作確認手順を説明できる
- 変更理由を説明できる
```

**検証できないコード変更は、エージェントに任せるには危ない**です。

---

### 5. 成功条件・禁止事項・変更範囲を明示する

**重要度: 5**

コーディングエージェントには、何をしてよくて、何をしてはいけないかを明示する必要があります。

たとえば、

```tone-neutral.guideline
- APIレスポンス形式は変えない
- DBスキーマは変えない
- 既存テストは消さない
- 依存ライブラリは追加しない
- UI文言は指定されたものだけ変更する
- 大きなリファクタリングはしない
```

こういう制約がないと、AIは「きれいにする」つもりで余計な変更をします。

コーディングエージェントでは、**何をするか**と同じくらい、**何をしないか**が重要です。

---

### 6. 作業環境・ハーネスを整える

**重要度: 4**

本格的に使うなら重要度5に近いです。

コーディングエージェントは、環境が整っていないとかなり弱くなります。

必要なのは、

```tone-good.guideline
- 依存関係をインストールできる
- テストを実行できる
- ビルドできる
- ログを見られる
- 失敗を再現できる
- 初期状態へ戻せる
- 評価用タスクを繰り返し実行できる
```

という環境です。

Anthropicのハーネス系記事はこの観点が強いです。

個人利用なら最初は軽くてよいですが、チームや業務で使うなら、**エージェントが検証できる環境**は必須です。

---

### 7. 権限・サンドボックス・人間確認を設計する

**重要度: 5**

コーディングエージェントは、ファイルを書き換え、コマンドを実行し、外部通信をする可能性があります。

なので、安全設計が必要です。

特に注意すべき操作は、

```tone-good.risk
- rm / delete 系
- git push
- npm publish
- 本番環境への操作
- 秘密情報へのアクセス
- 外部API呼び出し
- パッケージインストール
- 権限昇格
```

です。

基本方針はこうです。

```tone-neutral.risk
読み取りは広めに許可
書き込みは作業範囲を限定
破壊的操作は人間確認
外部送信は人間確認
秘密情報には触らせない
```

コーディングエージェントは便利ですが、**実行権限を持ったAI**なので、セキュリティはかなり重要です。

---

### 8. 変更内容を説明させる

**重要度: 4**

AIがコードを変えたら、最後に説明させるべきです。

見たいのは、

```tone-neutral.question-checklist
- 何を変えたか
- なぜ変えたか
- 影響範囲はどこか
- 実行したテストは何か
- 残っている懸念は何か
```

です。

これはレビュー効率に効きます。

単に「完了しました」ではなく、**人間がレビューしやすい報告**までが成果物です。

---

## OpenAIとAnthropicで共通

### 1. 良いコーディングには十分な文脈が必要

**重要度: 5**

OpenAI Codex系も、Anthropic Claude Code系も、共通して「文脈を渡すこと」を重視します。

必要なのは、

```tone-good.guideline
- タスクの目的
- 関連ファイル
- 既存コードの意図
- テスト方法
- 期待する出力
- 制約
- 完了条件
```

です。

共通する実務判断はこれです。

```tone-neutral.guideline
AIが変なコードを書いたら、
まず「必要な文脈を渡していたか」を疑う
```

コーディングエージェントでは、モデル性能よりも **コンテキスト設計の差** がかなり出ます。

---

### 2. テスト実行までを作業に含める

**重要度: 5**

OpenAIとAnthropicの両方に共通する大事な点です。

コーディングエージェントには、コード変更だけでなく、

```tone-neutral.guideline
- テストを走らせる
- 失敗ログを読む
- 原因を切り分ける
- 修正する
- 再テストする
```

までやらせます。

これは「エージェントらしさ」の中心です。

```tone-neutral.process
書く
↓
実行する
↓
結果を見る
↓
直す
```

のループが作れるからです。

---

### 3. リポジトリ内の指示ファイルを活用する

**重要度: 5**

OpenAIなら `AGENTS.md`、Anthropicなら `CLAUDE.md` のように、リポジトリ内に恒久的な作業指示を置く発想があります。

ここに書くべきなのは、

```tone-good.guideline
- プロジェクト概要
- セットアップ方法
- テストコマンド
- コーディング規約
- 注意すべきファイル
- 禁止事項
- PR前チェック
```

です。

これはかなり重要です。

毎回プロンプトに長く書くより、**リポジトリ側に作業ルールを置く**ほうが安定します。

---

### 4. 外部情報やMCPで必要な文脈を補う

**重要度: 4**

OpenAIとAnthropicのどちらも、外部情報やMCP的な接続で、エージェントの文脈を補う考え方があります。

たとえば、

```tone-neutral.guideline
- GitHub issue
- Linear / Jira
- design docs
- API docs
- logs
- analytics
- database schema
- internal docs
```

を参照できるようにする。

ただし、何でも接続すればよいわけではありません。

```tone-neutral.risk
必要な情報源だけ接続する
読み取り権限を基本にする
書き込み系は制限する
```

が大事です。

---

### 5. 人間レビュー・承認を残す

**重要度: 5**

OpenAIとAnthropicの共通点として、完全自動化よりも、人間レビューを組み込む発想が重要です。

特に、

```tone-neutral.risk
- 大きな設計変更
- セキュリティ関連
- 本番影響
- 依存関係追加
- 削除・破壊的操作
- 外部公開
```

は人間確認を入れるべきです。

コーディングエージェントでは、**PRを作るところまで自動化しても、mergeは人間が確認する**くらいが現実的です。

---

### 6. 変更を小さく保つ

**重要度: 5**

OpenAIもAnthropicも、コーディングエージェントには大きすぎる仕事を丸投げしないほうがよい、という方向性です。

```tone-neutral.guideline
小さい変更
明確な完了条件
限定されたファイル
具体的なテスト
```

のほうが成功しやすい。

これはかなり重要です。

大きな機能開発を任せる場合も、

```tone-neutral.guideline
調査
設計案
小さな実装
テスト追加
レビュー
次の変更
```

に分けるべきです。

## OpenAIのみ

### 1. Codex向けにタスク指示を明確化する

**重要度: 5**

OpenAIのCodexベストプラクティスは、かなり「どう依頼するとCodexがうまく動くか」に寄っています。

重要なのは、

```tone-good.guideline
- 何をしてほしいか
- どのファイルを見るべきか
- 期待する挙動
- テスト方法
- 変更してよい範囲
- 追加で調べるべき情報
```

を明確にすることです。

これは、Codexだけでなくコーディングエージェント全般に効きます。

---

### 2. `AGENTS.md` 的な永続指示を置く

**重要度: 5**

OpenAI系では、リポジトリ内にエージェント向けの指示ファイルを置く発想が重要です。

ここには、

```tone-neutral.guideline
- セットアップ
- テスト
- スタイル
- ディレクトリ構造
- 変更時の注意
- PR前チェック
```

を書きます。

これは実務上かなり強いです。

毎回のプロンプトで説明しなくても、エージェントがリポジトリの作法を理解しやすくなります。

---

### 3. Codexの作業単位は「Issue / PR / タスク」に寄せる

**重要度: 4**

OpenAI系の実践では、Codexに渡す仕事は、自然な開発単位に寄せると扱いやすいです。

```tone-neutral.guideline
- GitHub issueを解決する
- バグを修正する
- テストを追加する
- 小さな機能を実装する
- PRを作る
```

のような単位です。

これは実務的に重要ですが、設計原則としては「タスクを小さくする」の具体形なので重要度4です。

---

### 4. OpenAIの実装・運用機能に寄ったベストプラクティス

**重要度: 3**

Codex固有の環境、設定、外部接続、クラウド実行、MCPなどの話は、OpenAIスタックを使うなら重要です。

ただし、汎用的なベストプラクティスとしては製品依存です。

考え方として拾うなら、

```tone-neutral.takeaway
コーディングエージェントが必要な情報源へアクセスできるようにする
```

という点です。

## Anthropicのみ

### 1. Claude Codeの作業ループを明確にしている

**重要度: 5**

AnthropicのClaude Code系では、かなり実務的な作業ループが重視されています。

典型的には、

```tone-neutral.process
探索する
↓
計画する
↓
実装する
↓
検証する
↓
コミット/PR向けに説明する
```

です。

特に重要なのは、**最初に探索させること**です。

コードベースを読まずに修正させると、局所最適なコードを書きがちです。

---

### 2. `CLAUDE.md` を育てる

**重要度: 5**

Anthropic系では、`CLAUDE.md` をかなり重要な実践として扱います。

ここには、

```tone-neutral.guideline
- よく使うコマンド
- コーディング規約
- テスト方法
- プロジェクト固有の注意点
- よくある落とし穴
- ファイル構成
- チームの好み
```

を書きます。

ポイントは、一度書いて終わりではなく、使いながら育てることです。

AIが何度も同じ失敗をするなら、それは `CLAUDE.md` に追記するサインです。

---

### 3. サブエージェント、hooks、slash commands などで作業を型化する

**重要度: 4**

AnthropicのClaude Code系は、日常的な開発作業を型にする発想が強いです。

たとえば、

```tone-neutral.guideline
- よく使う作業を slash command にする
- 特定の作業を subagent に分ける
- 作業後に hooks でテストや整形を走らせる
- ルール違反を検出する
```

です。

これはかなり実務的です。

ただし、最初から作り込むより、繰り返し出てくる作業を見つけてから型化するのがよいです。

---

### 4. 権限スキップと安全性を両立させる設計が深い

**重要度: 5**

Anthropicの `auto mode` や `sandboxing` 系の記事では、エージェントにもっと自律的に動いてもらうための安全設計が深掘りされています。

ポイントは、

```tone-good.question-checklist
- どの操作は自動で許可するか
- どの操作は確認するか
- どの操作は禁止するか
- サンドボックス内だけで実行するか
- ネットワークアクセスをどう制御するか
- ファイルアクセスをどう制御するか
```

です。

これはかなり重要です。

コーディングエージェントは、権限を広げるほど便利になりますが、その分危険になります。
なので、**自律性を上げるなら、同時に封じ込めも強くする**必要があります。

---

### 5. 長時間実行エージェントには評価ハーネスが必要

**重要度: 5**

Anthropicのハーネス系記事は、コーディングエージェントを長く動かす場合に重要です。

短い修正なら、人間が見れば済みます。

でも、長時間の開発タスクでは、

```tone-neutral.guideline
- 環境を初期化する
- タスクを与える
- 途中状態を観測する
- テストを実行する
- 生成物を評価する
- 失敗時に再現できる
```

仕組みが必要になります。

これは高度ですが、本格的に使うなら重要度5です。

---

### 6. フロントエンドなど主観評価が難しい領域も評価対象にする

**重要度: 4**

Anthropicのアプリ開発ハーネス系では、見た目や体験のような、テストだけでは測りづらい品質も扱います。

たとえば、

```tone-neutral.question-checklist
- UIが仕様通りか
- 操作できるか
- レイアウトが崩れていないか
- エラー状態が自然か
- ユーザー体験が意図に合うか
```

です。

これはコーディングエージェントにフロントエンド開発を任せるなら重要です。

ただし、バックエンドや小さな修正だけなら優先度は少し下がります。

---

## 実務で重要な順

コーディングエージェント系で押さえるべき順番はこうです。

| 重要度 | ポイント                                    | 判断への使い方                       |
| --: | --------------------------------------- | ----------------------------- |
|   5 | リポジトリ文脈を渡す                              | AGENTS.md / CLAUDE.md に作法を書く  |
|   5 | まず調査・計画させる                              | いきなり実装させない                    |
|   5 | 小さく明確なタスクにする                            | 変更範囲と完了条件を絞る                  |
|   5 | テスト・lint・ビルドまで含める                       | 書いたコードを検証させる                  |
|   5 | 成功条件・禁止事項を明示する                          | 余計な変更を防ぐ                      |
|   5 | 人間レビューを残す                               | merge / deploy / 外部公開は確認する    |
|   5 | 権限・サンドボックスを設計する                         | 自律性を上げるほど重要                   |
|   5 | 長時間タスクにはハーネスを用意する                       | 本格運用では環境ごと評価する                |
|   4 | 外部情報やMCPで文脈を補う                          | Issue、設計書、ログ、API docsへ接続する    |
|   4 | 変更内容を説明させる                              | レビューしやすくする                    |
|   4 | hooks / slash commands / subagentsで型化する | 繰り返し作業を安定化する                  |
|   4 | UIなど主観品質も評価する                           | フロントエンド開発では重要                 |
|   3 | 製品固有機能を活用する                             | Codex / Claude Codeごとの便利機能を使う |

## 一言でいうと

コーディングエージェント系で一番大事なのは、これです。

```tone-good.guideline
AIにコードを書かせるのではなく、
AIが安全にコードを読み、変更し、実行し、検証し、
人間がレビューできる形で報告する環境を作ること。
```

実務向けにはこうです。

```tone-neutral.process
1. AGENTS.md / CLAUDE.md にプロジェクト作法を書く
2. タスクを小さく切る
3. まず調査・計画させる
4. 実装範囲と禁止事項を明示する
5. テスト・lint・ビルドを走らせる
6. 失敗したらログを読ませて修正させる
7. 危険操作は人間承認にする
8. 最後に変更内容・検証結果・懸念点を報告させる
```

コーディングエージェントは、雑に使ってもそれなりに動きます。
でも業務で安定して使うなら、**プロンプト術よりも「リポジトリ文脈・検証環境・権限管理」**が効いてきます。
