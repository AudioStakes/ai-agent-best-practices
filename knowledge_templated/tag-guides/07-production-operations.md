## 結論

結論から言うと、本番運用系で一番大事なのは、**「動くエージェントを作ること」ではなく、「壊れたときに検知でき、安全に止められ、改善し続けられる状態にすること」**です。

## どの記事でも共通

### 1. PoCと本番運用は別物として扱う

**重要度: 5**

本番運用系で最初に大事なのは、**「一回うまく動いた」ことと「継続的に任せられる」ことを分ける**ことです。

PoCでは、

```tone-neutral.guideline
- 1回成功する
- デモで動く
- 代表例で便利に見える
- 人間が横で見ている
```

でもよいです。

でも本番では、

```tone-neutral.risk
- 失敗時に検知できる
- 何度実行しても安定する
- コストが予測できる
- 権限が制御されている
- ログが残る
- 人間確認ポイントがある
- 改善前後を比較できる
```

必要があります。

これは最重要です。
AIエージェントはデモ映えしやすいぶん、**本番化の地味な要件を後回しにしがち**です。

---

### 2. 評価・テスト・回帰確認を運用に組み込む

**重要度: 5**

本番運用では、評価は「開発時だけのもの」ではありません。

エージェントは、次の変更で簡単に挙動が変わります。

```tone-neutral.risk
- モデル変更
- プロンプト変更
- ツール説明変更
- API仕様変更
- データ更新
- 権限変更
- ワークフロー変更
```

そのたびに、以前できていたことが壊れる可能性があります。

なので、本番運用では、

```tone-neutral.guideline
- 評価データセット
- 回帰テスト
- 代表ケース
- 失敗ケース
- 安全性チェック
- ツール利用チェック
```

を継続的に回す必要があります。

これは重要度5です。
評価なしで本番エージェントを運用するのは、テストなしで本番コードを出すのに近いです。

---

### 3. ログ・トレース・監視を残す

**重要度: 5**

本番運用では、エージェントが何をしたかを追えることが必須です。

最低限見たいのは、

```tone-neutral.guideline
- 入力
- 出力
- 使用したモデル
- 呼び出したツール
- ツール引数
- ツール結果
- エラー
- 実行時間
- コスト
- 人間確認の有無
- 最終状態
```

です。

最終回答だけ見ても、なぜ失敗したか分かりません。

たとえば、

```tone-neutral.risk
回答は正しいが、不要なツールを大量に呼んでいた
回答は正しいが、危険な操作をしようとしていた
回答は間違っているが、検索結果の時点で間違っていた
途中で権限エラーが出ていた
```

のようなことがあります。

本番運用では、**観測できないエージェントは改善できない**です。

---

### 4. 人間確認・承認・エスカレーションを設計する

**重要度: 5**

本番運用では、全部自動化するより、**どこで人間に渡すか**を設計するほうが重要です。

人間確認が必要になりやすいのは、

```tone-neutral.risk
- 外部送信
- 課金・支払い
- 削除
- 本番環境への変更
- 法務・医療・金融など高リスク判断
- 個人情報や機密情報の扱い
- 低信頼度の回答
- ユーザーへの不利益が大きい処理
```

です。

大事なのは、

```tone-good.takeaway
AIが全部やるか、人間が全部やるか
```

ではなく、

```tone-neutral.risk
AIが下書き・調査・候補作成をする
人間が高リスク部分だけ承認する
```

という分担です。

これは本番運用では最重要です。

---

### 5. 権限を最小化する

**重要度: 5**

エージェントはツールを使うほど便利になりますが、同時に危険になります。

本番運用では、原則として、

```tone-neutral.risk
必要な権限だけ渡す
読み取りと書き込みを分ける
不可逆操作は制限する
環境ごとに権限を分ける
秘密情報へのアクセスを制御する
外部送信を制御する
```

必要があります。

特に危険なのは、

```tone-bad.risk
- delete
- send
- purchase
- deploy
- publish
- approve
- write to production database
- access secrets
```

のような操作です。

便利だから全部許可する、はかなり危ないです。
**自律性を上げるほど、権限制御も強くする**のが基本です。

---

### 6. 失敗時の扱いを決める

**重要度: 5**

本番運用では、エージェントは失敗します。
大事なのは失敗しないことではなく、**失敗したときにどう振る舞うか**です。

決めるべきことは、

```tone-good.question-checklist
- 何回まで再試行するか
- いつ人間に渡すか
- どのエラーなら停止するか
- 部分的に成功した場合どうするか
- ユーザーにどう説明するか
- ロールバックできるか
- 失敗ログをどう残すか
```

です。

悪い本番運用は、失敗したときにAIがその場で適当に続けることです。

良い本番運用は、

```tone-neutral.guideline
失敗を検知する
原因を分類する
安全に止める
必要なら人間へ渡す
記録して改善につなげる
```

です。

---

### 7. コスト・レイテンシ・品質のバランスを見る

**重要度: 4**

本番では、精度だけでなくコストと速度も重要です。

たとえば、

```tone-neutral.guideline
- 毎回高性能モデルを使うとコストが高い
- ツールを呼びすぎると遅い
- 長いコンテキストを入れすぎると高い
- 評価ループを何度も回すと遅い
- 並列化すると速いがコストが増える
```

というトレードオフがあります。

本番では、タスクごとに、

```tone-neutral.question-checklist
品質重視か
速度重視か
コスト重視か
安全性重視か
```

を決める必要があります。

重要ですが、まずは安全性・評価・ログのほうが優先なので、重要度は4です。

---

### 8. デプロイ後も改善し続ける

**重要度: 4**

エージェントはリリースして終わりではありません。

本番運用では、

```tone-neutral.guideline
- 失敗例を集める
- 評価ケースに追加する
- プロンプトを直す
- ツール説明を直す
- ワークフローを分ける
- 人間確認ポイントを調整する
- モデルを見直す
```

という改善ループが必要です。

特に重要なのは、**失敗例を資産化すること**です。

本番で出た失敗を評価データに加えれば、同じ失敗を繰り返しにくくなります。

---

## OpenAIとAnthropicで共通

### 1. 本番運用ではトレース・観測可能性が重要

**重要度: 5**

OpenAIもAnthropicも、エージェントがどう動いたかを観測できることを重視しています。

OpenAIはAgents SDKやtracingの文脈で、ツール呼び出し、ハンドオフ、ガードレールなどを追えるようにする発想があります。
Anthropicも、長時間実行エージェントやハーネスの文脈で、実行過程・環境・中間状態を観測することを重視しています。

共通する大事な点はこれです。

```tone-neutral.takeaway
最終結果だけでなく、途中で何が起きたかを見る
```

これは本番運用では最重要です。

---

### 2. 評価を運用サイクルに組み込む

**重要度: 5**

OpenAIもAnthropicも、評価を「作った後の採点」ではなく、改善と安全運用のための仕組みとして扱います。

本番で見るべきなのは、

```tone-good.guideline
- 成功率
- 失敗率
- ツール利用の正しさ
- 人間確認率
- ガードレール発火率
- 回帰評価の通過率
- 変更前後の品質差
```

です。

特にAnthropicは評価体系やハーネスの考え方が強く、OpenAIはワークフロー評価やトレースとの接続が実務的です。

共通して大事なのは、

```tone-good.takeaway
改善したつもりで壊れていないか確認する
```

ことです。

---

### 3. ガードレールと人間確認を組み込む

**重要度: 5**

OpenAIとAnthropicの両方に共通しているのは、エージェントには制御が必要という点です。

特に本番運用では、

```tone-neutral.risk
- 入力チェック
- 出力チェック
- ツール利用制御
- 権限管理
- 人間承認
- 高リスク操作のブロック
```

が必要です。

大事なのは、ガードレールを後付けにしないことです。

```tone-good.takeaway
設計段階から、どこで止めるかを決める
```

これが重要です。

---

### 4. 長時間・複数ステップの実行を前提にする

**重要度: 4**

OpenAIもAnthropicも、エージェントは単発応答ではなく、複数ステップで動くものとして扱います。

本番では、

```tone-neutral.guideline
- 途中で状態が変わる
- ツール結果によって分岐する
- 長時間処理が発生する
- 人間確認を挟む
- 途中失敗から回復する
```

ことがあります。

このため、状態管理や中間ログが必要です。

重要度は4ですが、長時間タスクや業務自動化では5です。

---

### 5. プロダクト機能だけでなく運用設計が必要

**重要度: 4**

OpenAIにもAnthropicにも便利なSDKやプロダクト機能がありますが、本番運用はツールを導入するだけでは成立しません。

必要なのは、

```tone-good.question-checklist
- 誰が監視するか
- 失敗時に誰へ渡すか
- どの指標を見るか
- いつ評価を回すか
- どのログを保存するか
- どの権限を許すか
- どの変更をレビューするか
```

です。

これは地味ですが重要です。
**エージェント運用は、技術設計と業務設計の両方**です。

## OpenAIのみ

### 1. Agents SDK / tracing / guardrails を運用部品として使う

**重要度: 4**

OpenAIの特徴は、本番運用に必要な要素をSDKやAPIの構成要素として扱いやすいことです。

たとえば、

```tone-neutral.guideline
- Agent
- Tool
- Handoff
- Guardrail
- Session
- Tracing
```

のような部品です。

OpenAIスタックで作るなら重要です。
ただし、一般原則としては製品依存なので重要度は4です。

本質は、

```tone-neutral.takeaway
エージェントの実行・制御・観測を一体で設計する
```

ことです。

---

### 2. ワークフロー単位で評価する

**重要度: 4**

OpenAIは、agent workflowを評価対象にする発想が強いです。

つまり、

```tone-neutral.takeaway
このエージェントは賢いか
```

ではなく、

```tone-neutral.takeaway
この業務フローは期待通り動くか
```

を見る。

これは本番運用に向いています。

本番で重要なのは、モデル単体の能力より、

```tone-good.takeaway
入力から最終結果までの流れが安定しているか
```

だからです。

---

### 3. built-in tools / hosted tools によって運用負荷を下げられる

**重要度: 3**

OpenAIでは、検索、ファイル、コード実行などの一部を提供ツールとして使えます。

これは実装・運用を早めるには便利です。

ただし、本番運用の一般原則としては、

```tone-neutral.takeaway
自前実装するか、マネージド機能を使うか
```

の判断に近いです。

重要度は3です。
便利ですが、これだけで本番運用ができるわけではありません。

---

### 4. モデル選定とコスト管理を運用設計に入れる

**重要度: 4**

OpenAIは、モデルの使い分けを比較的明示的に扱います。

本番では、

```tone-neutral.question-checklist
- どのステップで高性能モデルを使うか
- どこは軽量モデルでよいか
- 推論モデルをどこに使うか
- どの処理をキャッシュできるか
- どこでツール呼び出しを減らせるか
```

を考える必要があります。

これは運用コストに直結します。

---

## Anthropicのみ

### 1. 長時間実行エージェントのハーネス設計が深い

**重要度: 5**

Anthropicの本番運用系で特に重要なのは、長時間実行エージェントのためのハーネス設計です。

ハーネスとは、

```tone-neutral.guideline
エージェントを実行し、
環境を用意し、
状態を観測し、
成果物を評価し、
失敗を再現可能にする仕組み
```

です。

長時間タスクでは、最終結果だけ見ても不十分です。

```tone-bad.question-checklist
- 途中で何をしたか
- どのファイルを変えたか
- どんなエラーが出たか
- どの時点で迷ったか
- どこで人間確認が必要だったか
```

を見る必要があります。

これは本格運用では重要度5です。

---

### 2. サンドボックスと封じ込めの考え方が強い

**重要度: 5**

Anthropicは、エージェントを安全に動かすための隔離・封じ込めをかなり重視しています。

特に、

```tone-neutral.risk
- 一時環境
- コンテナ
- VM
- ファイルアクセス制限
- ネットワーク制限
- 権限の分離
- 機密情報の保護
```

のような考え方です。

本番運用では、エージェントに強い権限を与えるほど危険です。

そのため、

```tone-neutral.takeaway
自律性を上げるなら、実行環境を閉じ込める
```

という原則が大事です。

---

### 3. 自動化レベルと安全性のバランスを細かく設計する

**重要度: 5**

AnthropicのClaude Code auto mode系では、許可確認を減らしながら安全性を保つ工夫が出てきます。

本番運用にもそのまま応用できます。

考えるべきことは、

```tone-good.question-checklist
- どの操作は自動で許可するか
- どの操作は毎回確認するか
- どの操作は禁止するか
- どの条件なら一時的に許可するか
- 許可ルールを誰が管理するか
```

です。

これは本番では非常に重要です。

「全部確認」だと便利さが消えます。
「全部許可」だと危険です。

だから、**操作ごとに自動化レベルを設計する**必要があります。

---

### 4. 環境からのフィードバックを評価・改善に使う

**重要度: 4**

Anthropicは、エージェントが環境から得る事実情報を重視します。

たとえば、

```tone-neutral.guideline
- テスト結果
- コマンド結果
- 実行ログ
- ファイル差分
- UIの状態
- APIレスポンス
```

です。

本番運用では、エージェントが自分の出力だけで判断するのではなく、実際の環境から返ってくる結果を使って改善する必要があります。

これは特にコーディングエージェントや業務自動化で重要です。

---

### 5. 主観的品質も評価対象にする

**重要度: 3**

Anthropicのアプリ開発ハーネス系では、フロントエンドの見た目や使いやすさのような、主観的品質も扱います。

本番運用では、

```tone-neutral.guideline
- テストは通るが使いにくい
- UIが崩れている
- ユーザー体験が悪い
- 文章が不自然
```

のような問題もあります。

これは重要ですが、対象領域によります。
業務ワークフローやバックエンド中心なら優先度は少し下がります。

---

## 実務で重要な順

本番運用系で押さえるべき順番はこうです。

| 重要度 | ポイント              | 判断への使い方              |
| --: | ----------------- | -------------------- |
|   5 | PoCと本番を分ける        | デモ成功を本番可能と見なさない      |
|   5 | 評価・回帰テストを運用に入れる   | 変更で壊れていないか確認する       |
|   5 | ログ・トレース・監視を残す     | 失敗原因を追えるようにする        |
|   5 | 人間確認・承認を設計する      | 高リスク操作はAIだけで完了させない   |
|   5 | 権限を最小化する          | 必要なツール・情報だけ使わせる      |
|   5 | 失敗時の扱いを決める        | 再試行・停止・エスカレーションを定義する |
|   5 | サンドボックス・隔離を使う     | 自律実行するほど閉じ込める        |
|   5 | 長時間タスクにはハーネスを用意する | 環境・状態・成果物を評価可能にする    |
|   4 | コスト・レイテンシ・品質を見る   | 本番では精度だけでは判断しない      |
|   4 | デプロイ後も改善し続ける      | 失敗例を評価データに追加する       |
|   4 | モデル選定を運用設計に入れる    | 高性能モデルを使う場所を絞る       |
|   4 | 環境からのフィードバックを使う   | 実行結果をもとに改善する         |
|   3 | マネージドツールを活用する     | 便利だが本質ではない           |
|   3 | 主観的品質も評価する        | UI・文章品質が重要な場合に見る     |

## 一言でいうと

本番運用系で一番大事なのは、これです。

```tone-good.guideline
エージェントを「動くもの」から、
「監視でき、評価でき、止められ、改善できるもの」にすること。
```

実務向けにはこうです。

```tone-neutral.process
1. 成功条件を定義する
2. 評価ケースを作る
3. ログとトレースを残す
4. 権限を最小化する
5. 危険操作には人間承認を入れる
6. 失敗時の再試行・停止・エスカレーションを決める
7. サンドボックスで隔離する
8. コスト・速度・品質を継続的に見る
9. 失敗例を評価データに戻す
```

本番運用系は、派手な「AIエージェントすごい」話ではなく、かなり地味です。
でも、ここを押さえないと、エージェントは **便利なおもちゃ** から **任せられる仕組み** になりません。
