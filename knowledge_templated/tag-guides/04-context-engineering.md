## 結論

ここでの結論は、**コンテキスト設計とは「プロンプトを長くすること」ではなく、AIが仕事を進めるために必要な情報を、必要なタイミングで、使いやすい形で渡すこと**です。

## どの記事でも共通

### 1. AIに必要な情報を明示的に渡す

**重要度: 5**

コンテキスト設計系で一番大事なのはこれです。

AIは、あなたの頭の中、組織の暗黙知、過去の経緯、プロジェクト固有のルールを自動では知りません。
だから、作業に必要な情報をきちんと渡す必要があります。

たとえば、コーディングエージェントなら、

```text
- 何を作るのか
- どのファイルを見るべきか
- 既存の設計方針
- テストコマンド
- 変更してはいけない範囲
- 完了条件
- 過去の失敗例
```

を渡す必要があります。

ここで大事なのは、**AIの性能不足に見える失敗の多くが、実はコンテキスト不足で起きる**ということです。

---

### 2. コンテキストは「量」より「関連性」が重要

**重要度: 5**

たくさん情報を渡せば良いわけではありません。

むしろ、関係ない情報を大量に入れると、

```text
- 重要情報が埋もれる
- 判断がブレる
- 出力が長くなる
- コストが増える
- 間違った文脈を拾う
```

という問題が起きます。

コンテキスト設計で大事なのは、

```text
必要な情報を
必要な粒度で
必要な順番で
必要なタイミングで渡す
```

ことです。

これは重要度5です。
長いプロンプトを書くより、**不要な情報を削る力**のほうが重要な場合が多いです。

---

### 3. 作業の目的・制約・成功条件を渡す

**重要度: 5**

AIには「何をすれば終わりか」を伝える必要があります。

悪い例：

```text
この機能を改善してください
```

良い例：

```text
この機能の表示速度を改善してください。
ただし既存APIのレスポンス形式は変更しないでください。
完了条件は、既存テストが通り、一覧画面の初回表示が2秒以内になることです。
```

コンテキストには、単なる資料だけでなく、

```text
目的
制約
優先順位
完了条件
評価基準
禁止事項
```

を含める必要があります。

これは、OpenAI、Anthropic、Google Cloud、LangChain、Hugging Face系の記事で広く共通する考え方です。

---

### 4. コンテキストを構造化する

**重要度: 5**

AIに情報を渡すときは、雑に文章を貼るより、構造化したほうが使いやすいです。

たとえば、

```markdown
## Goal
...

## Background
...

## Constraints
...

## Relevant files
...

## Tools available
...

## Success criteria
...

## Do not
...
```

のように整理します。

構造化すると、AIは「どれが目的で、どれが制約で、どれが参考情報か」を区別しやすくなります。

これはかなり重要です。
特にエージェントは複数ステップで作業するので、最初に渡すコンテキストがぐちゃぐちゃだと、後続の判断も崩れます。

---

### 5. コンテキストは固定情報と動的情報に分ける

**重要度: 4**

コンテキストには、毎回変わらない情報と、タスクごとに変わる情報があります。

固定情報：

```text
- プロジェクト概要
- コーディング規約
- ディレクトリ構成
- テスト方法
- 禁止事項
- レビュー基準
```

動的情報：

```text
- 今回の依頼内容
- 今回触るファイル
- 今回のエラー
- 今回のユーザー要望
- 今回の調査結果
```

固定情報は `AGENTS.md`、`CLAUDE.md`、README、システムプロンプトなどに置く。
動的情報は毎回の依頼プロンプトやツール結果として渡す。

この分離はかなり大事です。
全部を毎回プロンプトに詰めると、運用が重くなります。

---

### 6. ツール結果もコンテキストとして設計する

**重要度: 5**

コンテキストは、最初に渡すプロンプトだけではありません。
ツールから返ってくる検索結果、ファイル内容、テスト結果、APIレスポンスもコンテキストです。

たとえば、ツール結果がこうだと弱いです。

```json
{ "status": "ok" }
```

こう返すほうが、AIは次に進みやすいです。

```json
{
  "status": "failed",
  "command": "npm test",
  "failed_tests": ["UserList renders empty state"],
  "error_summary": "Expected empty message but got loading state",
  "suggested_next_files": ["src/UserList.tsx", "src/UserList.test.tsx"]
}
```

ツール利用系とも重なりますが、コンテキスト設計の観点では、

```text
AIが次の判断に使える情報を返す
```

ことが重要です。

---

### 7. 長期タスクではコンテキストを更新・圧縮・再取得する

**重要度: 4**

長い作業では、最初に渡した情報だけでは足りません。

途中で、

```text
調査結果
実行結果
失敗理由
中間判断
ユーザーからの追加指示
変更済みファイル
未解決事項
```

が増えていきます。

このとき、すべてを会話履歴に残すだけではなく、

```text
要点をまとめる
古い情報を捨てる
必要な情報を再検索する
現在の作業状態を更新する
```

必要があります。

長時間動くエージェントやコーディングエージェントではかなり重要です。
ただし、単発タスクではそこまで重く考えなくてもよいので重要度4です。

---

## OpenAIとAnthropicで共通

### 1. 良い出力には良いコンテキストが必要

**重要度: 5**

OpenAI と Anthropic で最も共通しているのは、モデルの性能だけでなく、**渡す文脈の質が成果を左右する**という考え方です。

OpenAIのCodex系では、コードベース情報、作業目的、関連ファイル、テスト方法などをきちんと渡すことが重要です。
Anthropicも、エージェントが使う情報・ツール・メモリ・環境からのフィードバックをどう設計するかを重視します。

共通する判断はこれです。

```text
AIが失敗したとき、まず「モデルが悪い」と考える前に、
必要な文脈を渡せていたか確認する
```

これは最重要です。

---

### 2. コンテキストは作業単位に合わせて与える

**重要度: 5**

OpenAIもAnthropicも、AIに全部の情報を渡すのではなく、作業に必要な情報を渡すことを重視しています。

たとえば、バグ修正なら、

```text
- 問題の説明
- 再現手順
- 関連ファイル
- エラーログ
- テストコマンド
- 期待する挙動
```

が必要です。

一方で、関係ない仕様書や過去ログを大量に入れる必要はありません。

大事なのは、

```text
タスクに必要な文脈を選ぶ
```

ことです。

---

### 3. ツールや検索で不足コンテキストを補う

**重要度: 5**

OpenAIもAnthropicも、コンテキストを最初のプロンプトだけで完結させる発想ではありません。

不足する情報は、

```text
- ファイル検索
- Web検索
- ドキュメント検索
- コード実行
- テスト実行
- API呼び出し
```

などで取得します。

これはエージェントらしい重要ポイントです。

```text
最初から全部渡すのではなく、
必要になったら取りに行けるようにする
```

という設計です。

特に長いドキュメントや大きいコードベースでは、コンテキストウィンドウに全部入れるより、検索・取得の仕組みを持たせるほうが現実的です。

---

### 4. コンテキストとツール説明は一体で考える

**重要度: 4**

OpenAIもAnthropicも、ツールを使うエージェントでは、ツール説明そのものがコンテキストになります。

たとえば、

```text
このツールは何をするか
いつ使うべきか
何を返すか
失敗したらどうするか
```

をツール定義に書くことで、AIはそれを読んで行動します。

なので、コンテキスト設計は、単に「資料を渡す」だけではなく、

```text
ツールの使い方をどう伝えるか
```

も含みます。

重要度は4ですが、ツール利用型エージェントでは5に近いです。

---

### 5. 出力形式・判断基準・制約を明示する

**重要度: 5**

OpenAIのプロンプト設計でも、Anthropicのエージェント設計でも、指示や制約を明確にすることは非常に重要です。

特に、

```text
何を優先するか
何をしてはいけないか
どんな形式で返すか
どこまで自律的に進めるか
いつ確認するか
```

を明示する必要があります。

これはコンテキスト設計の中核です。

```text
背景情報だけではなく、判断の基準も渡す
```

ことが大切です。

---

## OpenAIのみ

### 1. Codexではリポジトリ文脈を与えることが特に重要

**重要度: 5**

OpenAIのCodexベストプラクティスでは、コーディングエージェントに十分な文脈を与えることが強く重視されます。

特に重要なのは、

```text
- リポジトリ構造
- 関連ファイル
- 期待する変更内容
- 実行すべきテスト
- 既存の実装方針
- 失敗時のログ
```

です。

これはコーディングエージェントでは最重要です。
「コードを書いて」だけではなく、**どの世界でコードを書くのか**を伝える必要があります。

---

### 2. Prompt engineeringを一般原則として整理している

**重要度: 4**

OpenAIは、プロンプト設計の一般原則として、

```text
指示を明確にする
文脈を与える
出力形式を指定する
例を与える
モデルの強みに合わせる
```

といった点を整理しています。

これはエージェント専用ではありませんが、エージェントのシステムプロンプト、タスク指示、ツール説明にもそのまま使えます。

重要度は4です。
基礎体力として重要ですが、エージェント特化の文脈ではAnthropicの context engineering のほうが踏み込んでいます。

---

### 3. 推論モデルには「考える余地のあるタスク」を渡す

**重要度: 4**

OpenAIのReasoning best practicesでは、推論モデルに向くタスクとして、

```text
- 複雑な判断
- 多段階の計画
- コードレビュー
- 曖昧な依頼の整理
- 大量情報からの統合
```

が想定されます。

コンテキスト設計上の意味は、

```text
推論モデルには、判断材料とゴールをきちんと渡す
```

ことです。

単純作業には過剰ですが、エージェントの計画・判断フェーズでは重要です。

---

### 4. 出力形式や制約をプロンプトで明示する実践色が強い

**重要度: 4**

OpenAIのプロンプト系記事は、かなり実践的に、

```text
こういう情報を入れる
こういう形式で返させる
こういう制約を書く
```

という方向に寄っています。

これは、既存ツールを使う人にとって扱いやすいです。

ただし、コンテキストの長期管理やツール結果設計という意味では、OpenAI単独の資料だけだとやや広義のプロンプト設計に寄ります。

---

## Anthropicのみ

### 1. Context engineering を「エージェント性能の中核」として扱う

**重要度: 5**

Anthropicの特徴は、コンテキストを単なるプロンプトではなく、エージェントの性能を決める中核要素として扱っている点です。

ここでいうコンテキストは、

```text
- システム指示
- ユーザー依頼
- ツール説明
- ツール結果
- メモリ
- 検索結果
- 環境からのフィードバック
- 中間状態
```

を含む広い概念です。

これは非常に重要です。
「プロンプトをうまく書く」から一段進んで、**AIに流れ込む情報全体を設計する**という発想です。

---

### 2. 情報は必要なタイミングで取り出せるようにする

**重要度: 5**

Anthropicのコンテキスト設計で重要なのは、すべてを最初から入れるのではなく、必要なときに必要な情報へアクセスできるようにすることです。

たとえば、

```text
- 検索
- メモリ
- ファイル参照
- コード実行結果
- 外部ツール
```

を使って、状況に応じてコンテキストを増やします。

これは、長いタスクや大量情報を扱うエージェントでは最重要です。

```text
最初に全部詰め込むより、
必要な情報を取りに行く設計にする
```

という考え方です。

---

### 3. ツール結果の返し方もコンテキスト設計である

**重要度: 5**

Anthropicは、ツールの出力がそのままエージェントのコンテキストになることを強く意識しています。

だから、

```text
- 返却値が長すぎる
- 重要情報が埋もれる
- エラー理由が分からない
- 次に何をすべきか分からない
```

ようなツールは、コンテキスト設計として悪いです。

良いツール結果は、

```text
次の判断に必要な情報だけを
分かりやすく
構造化して
必要なら根拠も含めて返す
```

ことです。

これはツール利用系とも重なりますが、コンテキスト設計では非常に重要です。

---

### 4. コンテキストの圧縮・整理・管理が重要

**重要度: 4**

Anthropic系の記事では、長期タスクやエージェントの自律実行において、コンテキストが増えすぎる問題が重要になります。

対策としては、

```text
- 中間結果を要約する
- 現在の状態を明示する
- 古い情報を整理する
- 必要な情報だけ再取得する
- メモリを使う
```

があります。

これは長期実行エージェントではかなり重要です。

単発プロンプトではそこまで気にしなくてよいですが、業務フロー化するなら早めに設計したいです。

---

### 5. エージェントが環境から得る事実情報を重視する

**重要度: 4**

Anthropicは、エージェントがツールや環境から得る情報、つまり ground truth を重視しています。

たとえば、

```text
- テスト結果
- コマンド結果
- ファイル内容
- APIレスポンス
- ユーザー確認
```

です。

AIに「考えさせる」だけではなく、実際の環境から得た結果をもとに判断させる。

これは、特にコーディングエージェントや業務自動化エージェントで重要です。

---

## 実務で重要な順

コンテキスト設計系で押さえるべき順番はこうです。

| 重要度 | ポイント                 | 判断への使い方                                  |
| --: | -------------------- | ---------------------------------------- |
|   5 | 必要な情報を明示的に渡す         | AIの失敗をモデル性能だけのせいにしない                     |
|   5 | 関連性の高い情報だけ渡す         | 大量投入ではなく、必要十分を目指す                        |
|   5 | 目的・制約・成功条件を渡す        | 何を達成し、何を避けるかを明確にする                       |
|   5 | コンテキストを構造化する         | 目的・背景・制約・資料・完了条件を分ける                     |
|   5 | 不足情報をツールや検索で補えるようにする | 最初に全部詰め込まない                              |
|   5 | ツール結果を次の判断に使える形にする   | ツール出力もコンテキストとして設計する                      |
|   4 | 固定情報と動的情報を分ける        | AGENTS.md / CLAUDE.md / README と都度指示を分ける |
|   4 | コンテキストを更新・圧縮する       | 長期タスクで情報が溢れないようにする                       |
|   4 | 出力形式・判断基準を明示する       | 期待とズレた出力を減らす                             |
|   4 | 環境からの事実情報を使わせる       | テスト結果・API結果・ファイル内容で判断させる                 |
|   3 | 例を入れる                | 効くが、常に必須ではない                             |
|   3 | モデルごとに渡し方を変える        | 高度化したら考える                                |

## 一言でいうと

コンテキスト設計系で一番大事なのは、これです。

```text
AIに何を知っていてほしいかを考えるのではなく、
AIがその仕事を進めるために、今どの情報が必要かを設計すること。
```

実務向けには、こうです。

```text
1. 目的を渡す
2. 背景を渡す
3. 制約を渡す
4. 関連資料を渡す
5. 使えるツールを渡す
6. ツール結果を次の判断に使える形にする
7. 長い作業では要約・更新・再取得する
```

プロンプト設計との違いで言うと、

```text
プロンプト設計:
AIにどう指示するか

コンテキスト設計:
AIが判断するための情報環境をどう作るか
```

です。
