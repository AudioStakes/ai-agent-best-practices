# 03. ツール利用系

## 対象タグ

`tool_use`

## 対象記事

- Anthropic — Writing effective tools for AI agents
- Anthropic — Building Effective AI Agents
- Anthropic — Effective context engineering for AI agents
- OpenAI — Building agents
- Google Cloud — Best practices and patterns

## 結論

結論から言うと、ツール利用系で一番大事なのは、**「AIにツールを渡すこと」ではなく、「AIが迷わず・安全に・正しく使える形でツールを設計すること」**です。

## どの記事でも共通

### 1. ツールは「人間向け」ではなく「AI向け」に設計する

**重要度: 5**

ツール利用系で最重要です。

人間が使うAPIやUIをそのままAIに渡しても、AIは迷います。
AIにとって重要なのは、ツール名、説明、入力項目、返却値、失敗時のエラーが明確であることです。

たとえば悪いツールはこうです。

```tone-neutral.code-example
search(query)
```

良いツールはこうです。

```tone-neutral.code-example
search_internal_docs(query, max_results)
説明:
社内ドキュメントから関連情報を検索する。
最新情報が必要な場合に使う。
返却値:
title, url, updated_at, snippet
```

ポイントは、**ツールそのものがプロンプトの一部になる**ということです。

AIはツールの名前と説明を読んで、「いつ使うか」「何を入れるか」「結果をどう解釈するか」を判断します。
なので、ツール定義が雑だと、プロンプトが良くても失敗します。

---

### 2. ツールの責務を小さく、明確にする

**重要度: 5**

多くの記事で共通するのは、ツールを万能化しすぎないことです。

悪い例はこうです。

```tone-bad.risk
do_everything(input)
```

これはAIにとって、何が起きるか予測しにくいです。

良い例はこうです。

```tone-good.guideline
search_docs
read_file
create_draft
send_email
run_tests
create_pull_request
```

のように、ツールの役割を分けることです。

ただし、細かくしすぎても逆に迷います。
重要なのは、**1つのツールが1つの明確な目的を持つこと**です。

```tone-good.question-checklist
何をするツールか
いつ使うツールか
何を入力すべきか
何が返ってくるか
何をしてはいけないか
```

が分かる状態にする必要があります。

---

### 3. ツールの説明文は、短くても具体的に書く

**重要度: 5**

ツール説明は、AIにとっての利用マニュアルです。

説明が曖昧だと、AIは似たツールの使い分けに失敗します。

たとえば、

```tone-neutral.code-example
get_user_data
```

だけでは足りません。

```tone-neutral.risk
get_customer_profile
指定した customer_id の氏名、契約プラン、利用状況を取得する。
請求履歴や支払い情報は含まない。
```

のように、**含む情報と含まない情報**まで書くと使いやすくなります。

特に重要なのはこの4つです。

```tone-good.question-checklist
いつ使うか
何を入力するか
何が返るか
何には使わないか
```

ツールが増えるほど、この説明の品質が効いてきます。

---

### 4. 返却値は、AIが次の判断に使いやすい形にする

**重要度: 5**

ツールは呼び出せればよいわけではありません。
呼び出した後、AIがその結果を読んで次の行動を決められる必要があります。

悪い返却値はこうです。

```json.code-example
{
  "result": "ok"
}
```

これだと、AIは何が起きたのか判断できません。

良い返却値はこうです。

```json.code-example
{
  "status": "success",
  "created_draft_id": "123",
  "recipient": "customer@example.com",
  "subject": "Invoice follow-up",
  "requires_user_confirmation": true
}
```

重要なのは、**結果・理由・次に必要な行動**が分かることです。

特に失敗時は重要です。

```json.code-example
{
  "status": "error",
  "error_code": "CUSTOMER_NOT_FOUND",
  "message": "No customer found for customer_id=123",
  "suggested_next_action": "Ask the user to confirm the customer ID."
}
```

AIはエラー文を見て回復しようとするので、エラーも設計対象です。

---

### 5. ツール利用には安全策・権限・確認ポイントが必要

**重要度: 5**

ツールを使えるということは、AIが外部世界に影響を与えられるということです。

たとえば、

```tone-neutral.risk
メールを送る
ファイルを削除する
支払いを実行する
データベースを書き換える
PRを作る
コマンドを実行する
```

のようなツールは、失敗時の影響が大きいです。

そのため、ツール利用では必ず以下を考えます。

```tone-neutral.question-checklist
読み取り専用か、書き込みありか
元に戻せる操作か、不可逆操作か
人間確認が必要か
許可された範囲だけ操作しているか
ログが残るか
```

実務では、まず読み取り系ツールから始めるのが安全です。
書き込み・送信・削除・購入・外部公開などは、人間確認を入れるべきです。

---

### 6. ツールを増やしすぎない

**重要度: 4**

ツールが多いほど、AIは選択に迷います。

似たようなツールが並ぶと、

```tone-neutral.code-example
search
web_search
doc_search
knowledge_search
find_info
```

のように、どれを使うべきか分かりにくくなります。

ツール数が増える場合は、

```tone-neutral.guideline
名前空間を分ける
用途別にまとめる
説明文で使い分けを書く
不要なツールを渡さない
タスクに必要なツールだけ渡す
```

ことが重要です。

「全部のツールを常に渡す」のではなく、**タスクに応じて使えるツールを絞る**のが理想です。

---

### 7. ツール利用を評価・デバッグできるようにする

**重要度: 4**

ツール利用型エージェントでは、出力だけ見ても失敗原因が分からないことがあります。

重要なのは、

```tone-good.question-checklist
どのツールを呼んだか
なぜそのツールを選んだか
どんな引数を渡したか
返却値をどう解釈したか
どこで失敗したか
```

を追えるようにすることです。

特に業務利用では、トレースやログがないと改善できません。

最初から大げさな評価基盤は不要ですが、最低限、

```tone-neutral.code-example
tool_name
input
output
error
timestamp
```

は残したいです。

---

## OpenAIとAnthropicで共通

### 1. エージェントの中心は「モデル + ツール + 制御」である

**重要度: 5**

OpenAI も Anthropic も、エージェントを単なるチャットモデルではなく、ツールを使って行動するシステムとして扱っています。

OpenAI は、エージェントをモデル、ツール、状態、オーケストレーションなどの構成要素で説明します。
Anthropic も、ツール・検索・メモリで拡張されたLLMを基本単位として扱います。

ここで大事なのは、エージェント設計はプロンプトだけでは終わらないということです。

```tone-good.question-checklist
どのツールを使えるか
どの順番で使うか
どの権限を与えるか
失敗時にどう回復するか
```

まで含めて設計する必要があります。

これは最重要です。

---

### 2. ツールは明確なスキーマと説明を持つべき

**重要度: 5**

OpenAI は function calling や built-in tools の文脈で、ツールの名前、説明、パラメータスキーマを重視します。
Anthropic も、ツール定義の説明、引数、返却値、使い分けを非常に重視します。

共通する大事な点は、

```tone-neutral.guideline
AIに「何となく使わせる」のではなく、
構造化されたツール定義として渡す
```

ことです。

特に重要なのは、

```tone-good.guideline
ツール名
説明
引数
必須項目
返却値
エラー
使用条件
```

です。

これは、プロンプト品質と同じくらい重要です。

---

### 3. ツール利用はオーケストレーションの一部として考える

**重要度: 5**

OpenAI も Anthropic も、ツール利用を単発の呼び出しではなく、ワークフローやオーケストレーションの一部として扱っています。

たとえば、

```tone-neutral.process
情報検索
↓
判断
↓
ツール実行
↓
結果確認
↓
必要なら再実行
```

という流れです。

ツールだけを渡して「適当に使って」ではなく、

```tone-neutral.question-checklist
どの段階で使うか
ツール結果をどう評価するか
次のステップへどうつなぐか
```

を考える必要があります。

---

### 4. ツール利用にはガードレールが必要

**重要度: 5**

OpenAI も Anthropic も、ツールを使うエージェントには制御が必要という立場です。

OpenAI は guardrails、human-in-the-loop、input/output validation を重視します。
Anthropic は、ツール利用時の明確な制約、環境からのフィードバック、人間確認、安全な実行環境を重視します。

共通する実務判断はこれです。

```tone-neutral.risk
読み取り系ツールは比較的自由に使わせる
書き込み系ツールは確認を入れる
不可逆操作は原則人間承認
外部送信は確認対象
```

これはかなり重要です。
ツール利用が増えるほど、AIのミスが現実の損害につながりやすくなります。

---

### 5. ツール結果を見て、次の行動を変える設計にする

**重要度: 4**

OpenAI も Anthropic も、ツール呼び出しの結果をモデルが読み、次の判断に使う前提です。

たとえば、

```tone-neutral.process
検索結果が少ない → クエリを変える
テストが失敗した → 修正する
ファイルが存在しない → ユーザーに確認する
権限がない → 処理を止める
```

のような流れです。

このため、ツールは成功・失敗だけでなく、**次に何をすべきか判断できる情報**を返す必要があります。

重要度は4ですが、長期タスクや自律度が高いエージェントでは5に近いです。

---

## OpenAIのみ

### 1. Built-in tools と function calling の使い分け

**重要度: 4**

OpenAI の特徴は、ツール利用を built-in tools と function calling に分けて整理している点です。

たとえば、

```tone-neutral.guideline
Web search
File search
Computer use
Code interpreter
Function calling
```

のような道具を、用途に応じて使います。

OpenAIスタックで実装するなら重要です。
ただし、一般原則としては「外部能力をどう与えるか」という話なので、重要度は4です。

---

### 2. ツール呼び出しのスキーマをAPI側で強く扱える

**重要度: 4**

OpenAIでは、function calling により、ツールの引数を構造化して渡せます。

これは実務上かなり大事です。

```tone-neutral.code-example
自然文で「検索して」ではなく、
search_docs({ query, max_results }) のように呼ぶ
```

形にできるからです。

スキーマがあることで、

```tone-neutral.guideline
入力漏れ
型の間違い
曖昧な引数
余計な自然文
```

を減らせます。

---

### 3. Agents SDK によるツール・ガードレール・トレースの統合

**重要度: 3**

OpenAI では Agents SDK を使うと、ツール、ハンドオフ、ガードレール、トレースなどをまとめて扱えます。

OpenAIで実装するなら便利ですが、概念としては製品依存です。

なので重要度は3です。

ただし、考え方としては重要です。

```tone-neutral.guideline
ツールを呼べるだけではなく、
ツール利用を観測し、
必要なら制御し、
失敗を追跡できるようにする
```

ということです。

---

### 4. Hosted tools を使うことで実装コストを下げる

**重要度: 3**

OpenAI の built-in / hosted tools は、検索、ファイル処理、コード実行などを自前実装せずに使える点が特徴です。

これは実装スピードには効きます。

ただし、AIエージェントのベストプラクティスとしては、

```tone-neutral.takeaway
自前で作るか、提供ツールを使うか
```

の判断なので、重要度は3です。

プロトタイプでは大事、本番では要件次第です。

---

## Anthropicのみ

### 1. ACI、Agent-Computer Interface を重視する

**重要度: 5**

Anthropicのツール利用系で最も重要なのがこれです。

ACIは、ざっくり言うと、

```tone-neutral.takeaway
AIがコンピュータやツールを使いやすくするためのインターフェース設計
```

です。

人間向けUIにUXデザインがあるように、AI向けツールにも設計が必要という考え方です。

具体的には、

```tone-neutral.guideline
ツール名
説明
入力スキーマ
返却値
エラー
使用例
ツール同士の境界
トークン効率
```

をAIが理解しやすい形にします。

これは最重要です。
ツール利用系の中心概念として置いてよいです。

---

### 2. ツール説明には使用例・制約・エッジケースまで書く

**重要度: 5**

Anthropic は、ツール定義の説明をかなり重視します。

ただ「このツールは検索します」では不十分です。

```tone-bad.risk
どんな時に使うか
どんな時に使わないか
入力の例
エラー時の意味
他のツールとの違い
返却値の読み方
```

まで説明することが重要です。

これは実務でもかなり効きます。
ツール選択ミスや引数ミスを減らせます。

---

### 3. ツール結果はトークン効率よく、必要十分に返す

**重要度: 4**

Anthropic は、ツールから返す情報が多すぎても少なすぎても良くない、という観点が強いです。

多すぎると、

```tone-bad.risk
コンテキストを圧迫する
重要情報が埋もれる
判断が遅くなる
```

少なすぎると、

```tone-bad.risk
次の判断ができない
再問い合わせが増える
誤解する
```

そのため、ツール結果は **次の判断に必要な情報を、簡潔に返す** のが大事です。

---

### 4. 既存APIをそのまま渡さず、AI用にラップする

**重要度: 5**

Anthropicの記事で特に実務的に大事なのがこれです。

既存のAPIは人間やプログラム向けに作られていることが多く、AIにとっては使いにくい場合があります。

たとえば既存APIがこうだとします。

```tone-neutral.guideline
GET /customers
GET /contracts
GET /billing
GET /tickets
```

AIには、より目的単位のツールとして渡したほうがよいことがあります。

```tone-neutral.code-example
get_customer_support_context(customer_id)
```

返却値：

```tone-neutral.guideline
顧客概要
契約状態
最近の問い合わせ
請求上の注意点
次に確認すべきこと
```

つまり、**AIがタスクを進めるために必要な形でAPIを再設計する**ということです。

これは非常に重要です。

---

### 5. ツール改善にエージェント自身を使う

**重要度: 3**

Anthropic は、ツール定義や説明を改善するときに、エージェント自身を使ってレビュー・改善する発想も扱っています。

たとえば、

```tone-neutral.question-checklist
このツール説明でAIは正しく使えるか
似たツールと混同しないか
返却値は十分か
エラー時に復旧できるか
```

をAIに点検させる形です。

これは便利ですが、最初に押さえるべき本質ではないので重要度は3です。

---

## 実務で重要な順

ツール利用系で押さえるべき順番はこうです。

| 重要度 | ポイント                    | 判断への使い方                |
| --: | ----------------------- | ---------------------- |
|   5 | AI向けにツールを設計する           | 人間向けAPIをそのまま渡さない       |
|   5 | ツールの責務を明確にする            | 何をするツールか迷わせない          |
|   5 | ツール説明・スキーマを具体化する        | いつ使うか、何を入れるか、何が返るかを書く  |
|   5 | ツール結果を次の判断に使える形にする      | success/errorだけで終わらせない |
|   5 | 書き込み・送信・削除には安全策を入れる     | 人間確認、権限、ログを設計する        |
|   5 | 既存APIをAI用にラップする         | タスク単位で使いやすいツールにする      |
|   4 | ツール利用をワークフローに組み込む       | どの段階でどのツールを使うか決める      |
|   4 | ツール数を増やしすぎない            | タスクに必要なツールだけ渡す         |
|   4 | ツール利用をログ・評価できるようにする     | 失敗原因を追えるようにする          |
|   4 | ツール結果は必要十分にする           | 多すぎても少なすぎてもダメ          |
|   3 | hosted tools / SDKを活用する | 実装効率には効くが製品依存          |
|   3 | AIにツール定義をレビューさせる        | 改善には便利だが補助的            |

## 一言でいうと

ツール利用系で一番大事なのは、これです。

```tone-good.guideline
ツールを増やすことではなく、
AIが正しく選び、正しく入力し、
結果を読んで次の行動に移れるようにすること。
```

実務向けに言い換えると、

```tone-neutral.process
1. AIに何の道具を渡すか決める
2. その道具をいつ使うか説明する
3. 入力と出力を構造化する
4. 失敗時に復旧できる情報を返す
5. 危険な操作には確認と権限を入れる
6. 必要な道具だけ渡す
```

です。

このタグは、**プロンプト設計より一段実務寄り**です。
AIエージェントが「考える」だけでなく「行動する」ようになると、ツール設計の品質がそのまま成果と安全性に直結します。
