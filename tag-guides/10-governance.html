10. ガバナンス系

★は重要度を表します。★★★★★ほど、設計・運用時に優先して確認すべき項目です。

結論

結論から言うと、ガバナンス系で一番大事なのは、「エージェントを禁止する/自由に使わせる」の二択ではなく、誰が・何を・どのツール権限で・どの範囲まで任せてよいかを組織として決めることです。

どの記事でも共通

★★★★★

1. エージェントの利用範囲と責任者を明確にする

ガバナンス系で最重要です。

エージェントは、ただのチャットツールではなく、ツールを使い、情報を読み、場合によっては外部へ影響を与えます。

だから組織として、

どの業務で使ってよいか
どの業務では使ってはいけないか
誰が利用を承認するか
誰が設定を管理するか
誰が結果に責任を持つか
問題発生時に誰へエスカレーションするか

を決める必要があります。

特に重要なのは、エージェントがやったことでも、最終責任は人間・組織側に残るという前提です。

★★★★★

2. データ・機密情報・個人情報の扱いを決める

ガバナンスで外せないのがデータ管理です。

エージェントに渡してよい情報と、渡してはいけない情報を分ける必要があります。

渡してよい可能性がある
  • 公開情報
  • 社内で共有済みの一般資料
  • 匿名化されたデータ
  • テストデータ
慎重に扱う
  • 顧客情報
  • 個人情報
  • 契約情報
  • 売上・財務情報
  • 社内の未公開戦略
  • ソースコード
  • APIキーやトークンなどの認証情報

特に、エージェントは複数ツールや外部サービスに接続するため、どの情報がどこへ流れるかを管理する必要があります。

これは重要度★★★★★です。

★★★★★

3. ツール権限管理を組織ルールにする

個人が自由にツール接続を増やすと危険です。

組織では、

読み取り権限
書き込み権限
外部送信のツール権限
本番環境操作のツール権限
顧客情報アクセスのツール権限
管理者のツール権限

を分けて管理する必要があります。

基本は、セキュリティ系と同じで 最小権限 です。

必要な人に
必要な業務で
必要な期間だけ
必要なツール権限を与える

エージェントは便利なので、ついツール権限を広げたくなります。 でもガバナンスでは、便利さより事故時の影響範囲を狭めることが重要です。

★★★★★

4. 人間の承認ポイントを制度として決める

人間レビューは、個人の気分で入れるものではなく、組織ルールとして定義するべきです。

たとえば、

必ず承認が必要
  • 外部顧客への送信
  • 契約・請求・支払い
  • 本番環境への変更
  • 個人情報の利用
  • 法務・医療・金融など高リスク判断
  • 削除・公開・承認など不可逆操作

承認不要にできるもの：

下書き作成
社内向け要約
調査メモ作成
テスト環境での実験
読み取り専用の検索

大事なのは、エージェントに任せる範囲と、人間レビューで最終判断する範囲を明確に分けることです。

★★★★★

5. トレース・監査証跡を残す

ガバナンスでは、あとから説明できることが重要です。

残すべきものは、

誰が使ったか
いつ使ったか
どのエージェントを使ったか
どのデータにアクセスしたか
どのツールを呼んだか
どんな出力をしたか
誰が承認したか
どこで失敗したか

です。

これは単なるデバッグではありません。

監査 コンプライアンス セキュリティ調査 品質改善 責任分界 再発防止

に必要です。

トレースやログがないと、「エージェントが何をしたのか」が説明できません。 組織利用ではかなり致命的です。

★★★★☆

6. 評価・品質基準を組織で持つ

エージェントの良し悪しを、利用者の感覚だけで判断すると危険です。

組織として、

  • 正確性
  • 安全性
  • 完了率
  • 人間レビュー率
  • 失敗率
  • コスト
  • 処理時間
  • 顧客影響
  • コンプライアンス違反の有無

などを見る必要があります。

特に、業務に組み込むなら、

このエージェントは本番利用してよい品質か
変更後も壊れていないか
特定業務で使ってよいか

を判断する基準が必要です。

★★★★☆

7. 導入・利用・廃止のライフサイクルを管理する

ガバナンスでは、作って終わりではありません。

エージェントごとに、

申請
審査
試験運用
本番化
監視
改善
権限見直し
廃止

の流れを持つのが理想です。

放置されたエージェントは危険です。

古いプロンプト
古いツール説明
古いツール権限
管理者不明
使われていない外部接続

が残ると、セキュリティリスクになります。

★★★★☆

8. 利用者教育と共通ルールが必要

エージェントは、使う人の理解によってリスクが大きく変わります。

組織では、利用者に最低限これを共有する必要があります。

入れてよい情報 / 入れてはいけない情報
エージェント出力をそのまま信用しない
外部送信前に確認する
機密情報を貼らない
危険な操作は承認を取る
出力の責任は人間側にある
プロンプトインジェクションに注意する

ツールだけ導入して教育しないと、現場で危ない使われ方をします。

OpenAIとAnthropicで共通

★★★★★

1. エージェントにはガードレールと人間レビューが必要

OpenAI と Anthropic で共通している重要点は、エージェントを完全自由に動かさず、制御を入れることです。

OpenAI は ガードレール、人間レビュー、入力・出力制御、ツール利用制御を扱います。 Anthropic は封じ込め、サンドボックス、権限確認、自動化レベルの設計を重視します。

共通する判断はこれです。

危険な判断や操作は、AIだけで完了させない

これはガバナンスでも最重要です。 個別プロンプトではなく、組織の運用ルールとして決める必要があります。

★★★★★

2. ツールや権限を管理対象にする

OpenAI も Anthropic も、エージェントはツールを使って行動する存在として扱います。

そのため、組織では、

どのツールを許可するか
誰がツール接続を追加できるか
どのデータソースへ接続してよいか
どの操作は読み取り専用にするか
どの操作は承認制にするか

を管理する必要があります。

これはかなり重要です。

エージェントのリスクは、モデルそのものより 接続先と権限 で大きく変わります。

★★★★★

3. 監査・トレース・ログが必要

OpenAI は トレース、Anthropic は containment / long-running agents / sandboxing の文脈で、エージェントの挙動を追えることを重視しています。

ガバナンスでは、これは必須です。

誰が どのエージェントに 何をさせ どの情報を使い どのツールを呼び 何を出力したか

を説明できる必要があります。

これはセキュリティだけでなく、社内説明責任にも関わります。

★★★★★

4. プロンプトやモデルだけではなく、運用設計が必要

OpenAI と Anthropic の共通点として、エージェントはプロンプトだけで安全になるものではありません。

必要なのは、

権限
ツール
ガードレール
人間レビュー
ログ
評価
サンドボックス
利用ルール

です。

ガバナンスの視点では、良いプロンプトを書くことより、良い運用境界を作ることが重要です。

★★★★☆

5. 高リスク領域では段階的に自動化する

OpenAI も Anthropic も、最初から自律実行するより、段階的に進める考え方と相性が良いです。

ガバナンスとしては、

Level 1
エージェントが下書き・候補を作る
Level 2
エージェントが内部処理を行い、人間レビューする
Level 3
低リスク処理は自動化する
Level 4
高リスク処理のみ承認制にする
Level 5
一部業務を自律実行する

のように考えるとよいです。

いきなり自律実行にしない。 自動化レベルは、安全性・評価・監査が整ってから上げるのが現実的です。

Openエージェントのみ

★★★★☆

1. ガードレール / トレース / Agents SDK を統制部品として使える

OpenAI の特徴は、ガードレール、トレース、ハンドオフ、セッションなどをエージェント実装の部品として扱いやすいことです。

組織で使う場合は、

  1. ガードレール で入力・出力を制御する
  2. トレース で挙動を追う
  3. ハンドオフ で専門エージェントへ渡す
  4. セッションメモリ で状態を管理する

といった設計ができます。

ただし、これはOpenAIスタックに寄った話です。 ガバナンス原則としては、製品機能よりも 制御・記録・承認を仕組みにすることが本質です。

★★★★☆

2. ワークフロー単位で管理する発想がある

OpenAIは、エージェントを単体ではなく ワークフロー として扱う見方が強いです。

ガバナンス上もこれは有効です。

このエージェントが安全か

ではなく、

この業務フローでエージェントをどこに入れるか どこで人間レビューするか どのツールを使うか どのログを残すか

を見るべきです。

エージェント単体の許可ではなく、業務フロー単位で許可・監査するのが実務的です。

★★★☆☆

3. モデル・ツール選定を統制対象にできる

OpenAIでは、モデルやHosted Toolの選択肢が多いため、組織として選定ルールを持つ価値があります。

たとえば、

高リスク業務では推論モデルを使う
低リスク処理では軽量モデルを使う
Web検索利用時は引用を必須にする
ファイル検索は許可されたデータソースだけにする
コード実行は検証環境だけにする

です。

重要ですが、OpenAI固有の運用設計に近いので重要度は★★★☆☆〜★★★★☆です。

Anthropicのみ

★★★★★

1. 封じ込め、containment を組織設計として考える

Anthropic の強みは、エージェントをどう封じ込めるかの発想が非常に強いことです。

ガバナンスではこれがかなり重要です。

エージェントが触れるファイル範囲
エージェントが実行できるコマンド
エージェントがアクセスできるネットワーク
エージェントが読める機密情報
エージェントが外部送信できる内容
エージェントが書き込める環境

を組織として決める必要があります。

これは、単なるセキュリティ設定ではなく、AI活用の運用境界です。

★★★★★

2. 自律性と安全性をセットで管理する

Anthropic の auto mode / sandboxing 系から重要なのは、エージェントの自動化レベルを上げるなら、安全境界も強化するという発想です。

たとえば、

自動化レベル低
  • 毎回人間レビュー。サンドボックスは軽めでもよい。
自動化レベル中
  • 一部操作は自動。危険操作は確認。権限を限定。
自動化レベル高
  • サンドボックス必須。ネットワーク制限。認証情報遮断。トレース必須。

です。

ガバナンス上は、自動化レベルごとに必要な安全対策を定義するのがよいです。

★★★★☆

3. 開発者PC・ローカル環境をリスク領域として扱う

Anthropic のClaude Code系では、ローカル環境で動くエージェントのリスクが重要です。

開発者PCには、

SSH鍵
APIトークンなどの認証情報
.env
private repository
顧客データ
社内資料
本番アクセス情報

がある可能性があります。

組織としては、

ローカルでエージェントを使うルール
認証情報を置かない運用
sandbox利用
許可コマンド
外部送信制限
会社支給端末での利用方針

を決める必要があります。

これはコーディングエージェント導入時にかなり重要です。

★★★★☆

4. 許可ルールを運用で育てる

AnthropicのClaude Code系では、どの操作を許可し、どの操作を確認し、どの操作を禁止するかを実運用で調整していく発想があります。

ガバナンスでも同じです。

最初から完璧なルールは作れません。

よく使う安全な操作は自動化する
危険だった操作は確認対象にする
事故りそうな操作は禁止する
失敗例をルールに反映する

という改善が必要です。

これは重要度★★★★☆です。 最初は控えめに始め、実績を見ながら広げるのが良いです。

実務で重要な順

ガバナンス系で押さえるべき順番はこうです。

重要度 ポイント 判断への使い方
5 利用範囲と責任者を明確にする 誰が何に使ってよいか決める
5 データ・機密情報の扱いを決める 入れてよい情報とダメな情報を分ける
5 ツール権限管理を組織ルールにする ツール・データ・操作ごとに権限を分ける
5 承認ポイントを制度化する 外部送信・本番変更・支払いなどは承認制
5 トレース・監査証跡を残す 誰が何をしたか説明できるようにする
5 ガードレールを設計に入れる 入力・出力・ツール利用を制御する
5 自律性と安全性をセットで管理する 自動化レベルごとに必要な対策を決める
5 封じ込めを運用境界として考える エージェントが触れる範囲を限定する
4 評価・品質基準を持つ 本番利用してよい品質か判断する
4 導入から廃止まで管理する 放置されたエージェントを作らない
4 利用者教育を行う 現場の危ない使い方を防ぐ
4 ローカル環境の利用ルールを決める 開発者PCの秘密情報を守る
4 許可ルールを改善する 失敗例をルールに反映する
3 製品機能を統制に使う 便利だが本質は運用設計

一言でいうと

ガバナンス系で一番大事なのは、これです。

エージェントを誰が、どの業務で、どのデータ・権限・承認のもとで使ってよいかを決めること。

実務向けにはこうです。

  1. 利用してよい業務を決める
  2. 入れてよいデータを決める
  3. 使ってよいツールと権限を決める
  4. 承認が必要な操作を決める
  5. トレースと監査証跡を残す
  6. 品質・安全性の評価基準を持つ
  7. 自動化レベルごとに安全対策を決める
  8. 利用者にルールを教育する
  9. 使われなくなったエージェントやツール権限を廃止する

ガバナンスは、現場のスピードを止めるためのものではありません。 むしろ、安心してエージェントを広げるための交通ルールです。
