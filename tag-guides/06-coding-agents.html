06. コーディングエージェント系

★は重要度を表します。★★★★★ほど、設計・運用時に優先して確認すべき項目です。

対象タグ

  • Anthropic — Effective harnesses for long-running agents

結論

結論から言うと、コーディングエージェント系で一番大事なのは、**「エージェントにコードを書かせること」ではなく、「調査・変更・検証・安全確認まで回せる作業環境を作ること」**です。

どの記事でも共通

★★★★★

1. リポジトリコンテキストを明示的に与える

コーディングエージェントで最重要です。

エージェントはコードだけ見ても、プロジェクトの前提を知りません。

必要なのは、たとえばこういう情報です。

  • プロジェクトの目的
  • ディレクトリ構成
  • 主要な設計方針
  • 触ってよい範囲
  • 触ってはいけない範囲
  • テストコマンド
  • lint / format コマンド
  • PRやコミットのルール
  • よくある失敗

ここが弱いと、エージェントは「それっぽい修正」はできますが、プロジェクトに合った修正ができません。

コーディングエージェントでは、コンテキスト設計より先にリポジトリコンテキストです。

★★★★★

2. いきなり実装させず、まず調査・計画させる

かなり多くの記事で共通するポイントです。

悪い依頼はこうです。

このバグを直して

良い依頼はこうです。

  • まず関連ファイルを調査してください。
  • 原因を特定し、修正方針を説明してください。
  • その後、最小変更で修正し、テストを実行してください。

つまり、流れはこうです。

  1. 調査
  2. 原因説明
  3. 修正方針
  4. 実装
  5. 検証

いきなりコードを書かせると、既存設計を無視したり、不要に大きい変更をしがちです。

コーディングエージェントには、まず 読む・考える・計画する をやらせるのが大事です。

★★★★★

3. 小さく、明確なタスクに分ける

コーディングエージェントに大きすぎる依頼をすると失敗しやすいです。

悪い例：

このアプリをいい感じに改善して

良い例：

  • ログイン画面のバリデーションエラー表示を改善してください。
  • 対象は src/pages/Login.tsx と関連テストのみです。
  • 既存APIの仕様は変更しないでください。

タスクを小さくすると、

影響範囲が読みやすい テストしやすい レビューしやすい ロールバックしやすい エージェントが迷いにくい

です。

コーディングエージェントは、広すぎる自由度より、狭く明確な作業範囲のほうが強いです。

★★★★★

4. テスト・lint・実行確認まで含める

コーディングエージェント系で、これは絶対に外せません。

コードを書かせるだけでは不十分です。

  1. テストを実行する
  2. lint を実行する
  3. 型チェックを実行する
  4. ビルドする
  5. 必要なら手動確認手順を書く
  6. 失敗したら原因を見て修正する

までがセットです。

エージェントに「完了」を判断させるなら、完了条件はこういう形にすべきです。

  • npm test が通るか
  • npm run lint が通るか
  • 対象機能の動作確認手順を説明できるか
  • 変更理由を説明できるか

検証できないコード変更は、エージェントに任せるには危ないです。

★★★★★

5. 成功条件・禁止事項・変更範囲を明示する

コーディングエージェントには、何をしてよくて、何をしてはいけないかを明示する必要があります。

たとえば、

APIレスポンス形式は変えない DBスキーマは変えない 既存テストは消さない 依存ライブラリは追加しない UI文言は指定されたものだけ変更する 大きなリファクタリングはしない

こういう制約がないと、エージェントは「きれいにする」つもりで余計な変更をします。

コーディングエージェントでは、何をするかと同じくらい、何をしないかが重要です。

★★★★☆

6. 作業環境・ハーネスを整える

本格的に使うなら重要度★★★★★に近いです。

コーディングエージェントは、環境が整っていないとかなり弱くなります。

必要なのは、

  1. 依存関係をインストールできる
  2. テストを実行できる
  3. ビルドできる
  4. ログを見られる
  5. 失敗を再現できる
  6. 初期状態へ戻せる
  7. 評価用タスクを繰り返し実行できる

という環境です。

Anthropicのハーネス系記事はこの観点が強いです。

個人利用なら最初は軽くてよいですが、チームや業務で使うなら、エージェントが検証できる環境は必須です。

★★★★★

7. ツール権限・サンドボックス・人間レビューを設計する

コーディングエージェントは、ファイルを書き換え、コマンドを実行し、外部通信をする可能性があります。

なので、安全設計が必要です。

特に注意すべき操作は、

  • rm / delete 系
  • git push
  • npm publish
  • 本番環境への操作
  • 秘密情報へのアクセス
  • 外部API呼び出し
  • パッケージインストール
  • 権限昇格

です。

基本方針はこうです。

読み取りは広めに許可
書き込みは作業範囲を限定
破壊的操作は人間レビュー
外部送信は人間レビュー
秘密情報には触らせない

コーディングエージェントは便利ですが、実行権限を持ったエージェントなので、セキュリティはかなり重要です。

★★★★☆

8. 変更内容を説明させる

エージェントがコードを変えたら、最後に説明させるべきです。

見たいのは、

何を変えたか なぜ変えたか 影響範囲はどこか 実行したテストは何か 残っている懸念は何か

です。

これはレビュー効率に効きます。

単に「完了しました」ではなく、人間がレビューしやすい報告までが成果物です。

OpenAIとAnthropicで共通

★★★★★

1. 良いコーディングには十分なコンテキストが必要

OpenAI Codex系も、Anthropic Claude Code系も、共通して「コンテキストを渡すこと」を重視します。

必要なのは、

タスクの目的 関連ファイル 既存コードの意図 テスト方法 期待する出力 制約 完了条件

です。

共通する実務判断はこれです。

エージェントが変なコードを書いたら、 まず「必要なコンテキストを渡していたか」を疑う

コーディングエージェントでは、モデル性能よりも コンテキスト設計の差 がかなり出ます。

★★★★★

2. テスト実行までを作業に含める

OpenAIとAnthropicの両方に共通する大事な点です。

コーディングエージェントには、コード変更だけでなく、

  1. テストを走らせる
  2. 失敗ログを読む
  3. 原因を切り分ける
  4. 修正する
  5. 再テストする

までやらせます。

これは「エージェントらしさ」の中心です。

  1. 書く
  2. 実行する
  3. 結果を見る
  4. 直す

のループが作れるからです。

★★★★★

3. リポジトリ内の指示ファイルを活用する

OpenAIなら AGENTS.md、Anthropicなら CLAUDE.md のように、リポジトリ内に恒久的な作業指示を置く発想があります。

ここに書くべきなのは、

プロジェクト概要 セットアップ方法 テストコマンド コーディング規約 注意すべきファイル 禁止事項 PR前チェック

です。

これはかなり重要です。

毎回の指示に長く書くより、リポジトリ側に作業ルールを置くほうが安定します。

★★★★☆

4. 外部情報やMCPで必要なコンテキストを補う

OpenAIとAnthropicのどちらも、外部情報やModel Context Protocol（MCP）による接続で、エージェントのコンテキストを補う考え方があります。

たとえば、

GitHub issue Linear / Jira design docs API docs logs analytics database schema internal docs

を参照できるようにする。

ただし、何でも接続すればよいわけではありません。

必要な情報源だけ接続する
読み取り権限を基本にする
書き込み系は制限する

が大事です。

★★★★★

5. 人間レビュー・承認を残す

OpenAIとAnthropicの共通点として、完全自動化よりも、人間レビューを組み込む発想が重要です。

特に、

大きな設計変更
セキュリティ関連
本番影響
依存関係追加
削除・破壊的操作
外部公開

は人間レビューを入れるべきです。

コーディングエージェントでは、PRを作るところまで自動化しても、mergeは人間が確認するくらいが現実的です。

★★★★★

6. 変更を小さく保つ

OpenAIもAnthropicも、コーディングエージェントには大きすぎる仕事を丸投げしないほうがよい、という方向性です。

小さい変更 明確な完了条件 限定されたファイル 具体的なテスト

のほうが成功しやすい。

これはかなり重要です。

大きな機能開発を任せる場合も、

調査 設計案 小さな実装 テスト追加 レビュー 次の変更

に分けるべきです。

OpenAIのみ

★★★★★

1. Codex向けにタスク指示を明確化する

OpenAIのCodexベストプラクティスは、かなり「どう依頼するとCodexがうまく動くか」に寄っています。

重要なのは、

何をしてほしいか どのファイルを見るべきか 期待する挙動 テスト方法 変更してよい範囲 追加で調べるべき情報

を明確にすることです。

これは、Codexだけでなくコーディングエージェント全般に効きます。

★★★★★

2. AGENTS.md 的な永続指示を置く

OpenAI系では、リポジトリ内にエージェント向けの指示ファイルを置く発想が重要です。

ここには、

セットアップ テスト スタイル ディレクトリ構造 変更時の注意 PR前チェック

を書きます。

これは実務上かなり強いです。

毎回の指示で説明しなくても、エージェントがリポジトリの作法を理解しやすくなります。

★★★★☆

3. Codexの作業単位は「Issue / PR / タスク」に寄せる

OpenAI系の実践では、Codexに渡す仕事は、自然な開発単位に寄せると扱いやすいです。

  1. GitHub issueを解決する
  2. バグを修正する
  3. テストを追加する
  4. 小さな機能を実装する
  5. PRを作る

のような単位です。

これは実務的に重要ですが、設計原則としては「タスクを小さくする」の具体形なので重要度★★★★☆です。

★★★☆☆

4. OpenAIの実装・運用機能に寄ったベストプラクティス

Codex固有の環境、設定、外部接続、クラウド実行、MCPなどの話は、OpenAIスタックを使うなら重要です。

ただし、汎用的なベストプラクティスとしては製品依存です。

考え方として拾うなら、

コーディングエージェントが必要な情報源へアクセスできるようにする

という点です。

Anthropicのみ

★★★★★

1. Claude Codeのエージェントループを明確にしている

AnthropicのClaude Code系では、かなり実務的なエージェントループが重視されています。

典型的には、

  1. 探索する
  2. 計画する
  3. 実装する
  4. 検証する
  5. コミット/PR向けに説明する

です。

特に重要なのは、最初に探索させることです。

コードベースを読まずに修正させると、局所最適なコードを書きがちです。

★★★★★

2. CLAUDE.md を育てる

Anthropic系では、CLAUDE.md をかなり重要な実践として扱います。

ここには、

よく使うコマンド コーディング規約 テスト方法 プロジェクト固有の注意点 よくある落とし穴 ファイル構成 チームの好み

を書きます。

ポイントは、一度書いて終わりではなく、使いながら育てることです。

エージェントが何度も同じ失敗をするなら、それは CLAUDE.md に追記するサインです。

★★★★☆

3. サブエージェント、hooks、slash commands などで作業を型化する

AnthropicのClaude Code系は、日常的な開発作業を型にする発想が強いです。

たとえば、

  1. よく使う作業を slash command にする
  2. 特定の作業を subagent に分ける
  3. 作業後に hooks でテストや整形を走らせる
  4. ルール違反を検出する

です。

これはかなり実務的です。

ただし、最初から作り込むより、繰り返し出てくる作業を見つけてから型化するのがよいです。

★★★★★

4. ツール権限スキップと安全性を両立させる設計が深い

Anthropicの auto mode や sandboxing 系の記事では、エージェントにもっと自律的に動いてもらうための安全設計が深掘りされています。

ポイントは、

どの操作は自動で許可するか どの操作は確認するか どの操作は禁止するか サンドボックス内だけで実行するか ネットワークアクセスをどう制御するか ファイルアクセスをどう制御するか

です。

これはかなり重要です。

コーディングエージェントは、ツール権限を広げるほど便利になりますが、その分危険になります。 なので、自律性を上げるなら、同時に封じ込めも強くする必要があります。

★★★★★

5. 長時間実行エージェントには評価ハーネスが必要

Anthropicのハーネス系記事は、コーディングエージェントを長く動かす場合に重要です。

短い修正なら、人間が見れば済みます。

でも、長時間の開発タスクでは、

  1. 環境を初期化する
  2. タスクを与える
  3. 途中状態を観測する
  4. テストを実行する
  5. 生成物を評価する
  6. 失敗時に再現できる

仕組みが必要になります。

これは高度ですが、本格的に使うなら重要度★★★★★です。

★★★★☆

6. フロントエンドなど主観評価が難しい領域も評価対象にする

Anthropicのアプリ開発ハーネス系では、見た目や体験のような、テストだけでは測りづらい品質も扱います。

たとえば、

UIが仕様通りか 操作できるか レイアウトが崩れていないか エラー状態が自然か ユーザー体験が意図に合うか

です。

これはコーディングエージェントにフロントエンド開発を任せるなら重要です。

ただし、バックエンドや小さな修正だけなら優先度は少し下がります。

実務で重要な順

コーディングエージェント系で押さえるべき順番はこうです。

重要度 ポイント 判断への使い方
5 リポジトリコンテキストを渡す AGENTS.md / CLAUDE.md に作法を書く
5 まず調査・計画させる いきなり実装させない
5 小さく明確なタスクにする 変更範囲と完了条件を絞る
5 テスト・lint・ビルドまで含める 書いたコードを検証させる
5 成功条件・禁止事項を明示する 余計な変更を防ぐ
5 人間レビューを残す merge / deploy / 外部公開は確認する
5 ツール権限・サンドボックスを設計する 自律性を上げるほど重要
5 長時間タスクにはハーネスを用意する 本格運用では環境ごと評価する
4 外部情報やMCPでコンテキストを補う Issue、設計書、ログ、API docsへ接続する
4 変更内容を説明させる レビューしやすくする
4 hooks / slash commands / サブエージェントsで型化する 繰り返し作業を安定化する
4 UIなど主観品質も評価する フロントエンド開発では重要
3 製品固有機能を活用する Codex / Claude Codeごとの便利機能を使う

一言でいうと

コーディングエージェント系で一番大事なのは、これです。

  • エージェントにコードを書かせるのではなく、
  • エージェントが安全にコードを読み、変更し、実行し、検証し、
  • 人間がレビューできる形で報告する環境を作ること。

実務向けにはこうです。

  1. AGENTS.md / CLAUDE.md にプロジェクト作法を書く
  2. タスクを小さく切る
  3. まず調査・計画させる
  4. 実装範囲と禁止事項を明示する
  5. テスト・lint・ビルドを走らせる
  6. 失敗したらログを読ませて修正させる
  7. 危険操作は人間承認にする
  8. 最後に変更内容・検証結果・懸念点を報告させる

コーディングエージェントは、雑に使ってもそれなりに動きます。 でも業務で安定して使うなら、**コンテキスト設計よりも「リポジトリコンテキスト・検証環境・ツール権限管理」**が効いてきます。
