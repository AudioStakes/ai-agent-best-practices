# 10. ガバナンス系

エージェントを組織で安全に使うための章です。利用方針、責任分界、データ管理、承認、監査、廃止までを扱います。

この章を読むことで、誰が何をどこまで使うか、どのデータを渡してよいか、組織ルールをどう育てるかを見直せます。詳細な参照元は章末の引用リンクを参照してください。

> **対象時点: 2026年5月**  
> この章は、2026年5月時点で公開されている主要な公式ドキュメントをもとに整理しています。最新の仕様や推奨事項は、各公式ドキュメントを確認してください。

[← トップへ戻る](../index.md) | [用語集](../domain-glossary.md)

## この章で見直せること

- 誰が何をどこまで使うか決まっているか
- どのデータを渡してよいか決まっているか
- 承認や監査が組織ルールになっているか
- 導入後の改善や廃止まで見ているか
- 現場に共通ルールが定着しているか

## 結論

結論から言うと、ガバナンス系で一番大事なのは、**「AIエージェントを禁止する/自由に使わせる」の二択ではなく、誰が・何を・どの権限で・どの範囲まで任せてよいかを組織として決めること**です。

## どの記事でも共通

### 1. AIエージェントの利用範囲と責任者を明確にする

**重要度: 5**

ガバナンス系で最重要です。

AIエージェントは、ただのチャットツールではなく、ツールを使い、情報を読み、場合によっては外部へ影響を与えます。

だから組織として、

```tone-neutral.question-checklist
- どの業務で使ってよいか
- どの業務では使ってはいけないか
- 誰が利用を承認するか
- 誰が設定を管理するか
- 誰が結果に責任を持つか
- 問題発生時に誰へエスカレーションするか
```

を決める必要があります。

特に重要なのは、**AIがやったことでも、最終責任は人間・組織側に残る**という前提です。

---

### 2. データ・機密情報・個人情報の扱いを決める

**重要度: 5**

ガバナンスで外せないのがデータ管理です。

AIエージェントに渡してよい情報と、渡してはいけない情報を分ける必要があります。

```tone-bad.risk
渡してよい可能性がある:
- 公開情報
- 社内で共有済みの一般資料
- 匿名化されたデータ
- テストデータ

慎重に扱う:
- 顧客情報
- 個人情報
- 契約情報
- 売上・財務情報
- 社内の未公開戦略
- ソースコード
- APIキーやトークン
```

特に、エージェントは複数ツールや外部サービスに接続するため、**どの情報がどこへ流れるか**を管理する必要があります。

これは重要度5です。

---

### 3. 権限管理を組織ルールにする

**重要度: 5**

個人が自由にツール接続を増やすと危険です。

組織では、

```tone-neutral.risk
- 読み取り権限
- 書き込み権限
- 外部送信権限
- 本番環境操作権限
- 顧客情報アクセス権限
- 管理者権限
```

を分けて管理する必要があります。

基本は、セキュリティ系と同じで **最小権限** です。

```tone-neutral.risk
必要な人に
必要な業務で
必要な期間だけ
必要な権限を与える
```

AIエージェントは便利なので、つい権限を広げたくなります。
でもガバナンスでは、**便利さより事故時の影響範囲を狭めること**が重要です。

---

### 4. 人間の承認ポイントを制度として決める

**重要度: 5**

人間確認は、個人の気分で入れるものではなく、組織ルールとして定義するべきです。

たとえば、

```tone-neutral.risk
必ず承認が必要:
- 外部顧客への送信
- 契約・請求・支払い
- 本番環境への変更
- 個人情報の利用
- 法務・医療・金融など高リスク判断
- 削除・公開・承認など不可逆操作
```

承認不要にできるもの：

```tone-neutral.guideline
- 下書き作成
- 社内向け要約
- 調査メモ作成
- テスト環境での実験
- 読み取り専用の検索
```

大事なのは、**AIに任せる範囲と、人間が最終判断する範囲を明確に分けること**です。

---

### 5. ログ・監査証跡を残す

**重要度: 5**

ガバナンスでは、あとから説明できることが重要です。

残すべきものは、

```tone-good.question-checklist
- 誰が使ったか
- いつ使ったか
- どのエージェントを使ったか
- どのデータにアクセスしたか
- どのツールを呼んだか
- どんな出力をしたか
- 誰が承認したか
- どこで失敗したか
```

です。

これは単なるデバッグではありません。

```tone-neutral.guideline
- 監査
- コンプライアンス
- セキュリティ調査
- 品質改善
- 責任分界
- 再発防止
```

に必要です。

ログがないと、「AIが何をしたのか」が説明できません。
組織利用ではかなり致命的です。

---

### 6. 評価・品質基準を組織で持つ

**重要度: 4**

AIエージェントの良し悪しを、利用者の感覚だけで判断すると危険です。

組織として、

```tone-neutral.guideline
- 正確性
- 安全性
- 完了率
- 人間確認率
- 失敗率
- コスト
- 処理時間
- 顧客影響
- コンプライアンス違反の有無
```

などを見る必要があります。

特に、業務に組み込むなら、

```tone-neutral.question-checklist
このエージェントは本番利用してよい品質か
変更後も壊れていないか
特定業務で使ってよいか
```

を判断する基準が必要です。

---

### 7. 導入・利用・廃止のライフサイクルを管理する

**重要度: 4**

ガバナンスでは、作って終わりではありません。

AIエージェントごとに、

```tone-neutral.risk
- 申請
- 審査
- 試験運用
- 本番化
- 監視
- 改善
- 権限見直し
- 廃止
```

の流れを持つのが理想です。

放置されたエージェントは危険です。

```tone-bad.risk
- 古いプロンプト
- 古いツール説明
- 古い権限
- 管理者不明
- 使われていない外部接続
```

が残ると、セキュリティリスクになります。

---

### 8. 利用者教育と共通ルールが必要

**重要度: 4**

AIエージェントは、使う人の理解によってリスクが大きく変わります。

組織では、利用者に最低限これを共有する必要があります。

```tone-good.risk
- 入れてよい情報 / 入れてはいけない情報
- AI出力をそのまま信用しない
- 外部送信前に確認する
- 機密情報を貼らない
- 危険な操作は承認を取る
- 出力の責任は人間側にある
- プロンプトインジェクションに注意する
```

ツールだけ導入して教育しないと、現場で危ない使われ方をします。

---

## OpenAIとAnthropicで共通

### 1. エージェントにはガードレールと人間確認が必要

**重要度: 5**

OpenAI と Anthropic で共通している重要点は、エージェントを完全自由に動かさず、制御を入れることです。

OpenAI は guardrails、人間レビュー、入力・出力制御、ツール利用制御を扱います。
Anthropic は封じ込め、サンドボックス、権限確認、自動化レベルの設計を重視します。

共通する判断はこれです。

```tone-neutral.risk
危険な判断や操作は、AIだけで完了させない
```

これはガバナンスでも最重要です。
個別プロンプトではなく、組織の運用ルールとして決める必要があります。

---

### 2. ツールや権限を管理対象にする

**重要度: 5**

OpenAI も Anthropic も、エージェントはツールを使って行動する存在として扱います。

そのため、組織では、

```tone-neutral.question-checklist
- どのツールを許可するか
- 誰がツール接続を追加できるか
- どのデータソースへ接続してよいか
- どの操作は読み取り専用にするか
- どの操作は承認制にするか
```

を管理する必要があります。

これはかなり重要です。

エージェントのリスクは、モデルそのものより **接続先と権限** で大きく変わります。

---

### 3. 監査・トレース・ログが必要

**重要度: 5**

OpenAI は tracing、Anthropic は containment / long-running agents / sandboxing の文脈で、エージェントの挙動を追えることを重視しています。

ガバナンスでは、これは必須です。

```tone-neutral.guideline
誰が
どのエージェントに
何をさせ
どの情報を使い
どのツールを呼び
何を出力したか
```

を説明できる必要があります。

これはセキュリティだけでなく、社内説明責任にも関わります。

---

### 4. プロンプトやモデルだけではなく、運用設計が必要

**重要度: 5**

OpenAI と Anthropic の共通点として、AIエージェントはプロンプトだけで安全になるものではありません。

必要なのは、

```tone-good.risk
- 権限
- ツール
- ガードレール
- 人間確認
- ログ
- 評価
- サンドボックス
- 利用ルール
```

です。

ガバナンスの視点では、**良いプロンプトを書くことより、良い運用境界を作ること**が重要です。

---

### 5. 高リスク領域では段階的に自動化する

**重要度: 4**

OpenAI も Anthropic も、最初から完全自動化するより、段階的に進める考え方と相性が良いです。

ガバナンスとしては、

```tone-neutral.risk
Level 1: AIが下書き・候補を作る
Level 2: AIが内部処理を行い、人間が確認する
Level 3: 低リスク処理は自動化する
Level 4: 高リスク処理のみ承認制にする
Level 5: 一部業務を自律実行する
```

のように考えるとよいです。

いきなり全自動にしない。
**自律性は、安全性・評価・監査が整ってから上げる**のが現実的です。

---

## OpenAIのみ

### 1. Guardrails / tracing / Agents SDK を統制部品として使える

**重要度: 4**

OpenAI の特徴は、ガードレール、トレース、ハンドオフ、セッションなどをエージェント実装の部品として扱いやすいことです。

組織で使う場合は、

```tone-neutral.guideline
- guardrails で入力・出力を制御する
- tracing で挙動を追う
- handoff で専門エージェントへ渡す
- sessions で状態を管理する
```

といった設計ができます。

ただし、これはOpenAIスタックに寄った話です。
ガバナンス原則としては、製品機能よりも **制御・記録・承認を仕組みにすること**が本質です。

---

### 2. Workflow単位で管理する発想がある

**重要度: 4**

OpenAIは、エージェントを単体ではなく workflow として扱う見方が強いです。

ガバナンス上もこれは有効です。

```tone-neutral.takeaway
このAIが安全か
```

ではなく、

```tone-neutral.question-checklist
この業務フローでAIをどこに入れるか
どこで人間が確認するか
どのツールを使うか
どのログを残すか
```

を見るべきです。

エージェント単体の許可ではなく、**業務フロー単位で許可・監査する**のが実務的です。

---

### 3. モデル・ツール選定を統制対象にできる

**重要度: 3**

OpenAIでは、モデルやbuilt-in toolsの選択肢が多いため、組織として選定ルールを持つ価値があります。

たとえば、

```tone-neutral.risk
- 高リスク業務では推論モデルを使う
- 低リスク処理では軽量モデルを使う
- Web検索利用時は引用を必須にする
- ファイル検索は許可されたデータソースだけにする
- コード実行は検証環境だけにする
```

です。

重要ですが、OpenAI固有の運用設計に近いので重要度は3〜4です。

---

## Anthropicのみ

### 1. 封じ込め、containment を組織設計として考える

**重要度: 5**

Anthropic の強みは、エージェントをどう封じ込めるかの発想が非常に強いことです。

ガバナンスではこれがかなり重要です。

```tone-neutral.risk
- AIが触れるファイル範囲
- AIが実行できるコマンド
- AIがアクセスできるネットワーク
- AIが読める機密情報
- AIが外部送信できる内容
- AIが書き込める環境
```

を組織として決める必要があります。

これは、単なるセキュリティ設定ではなく、**AI活用の運用境界**です。

---

### 2. 自律性と安全性をセットで管理する

**重要度: 5**

Anthropic の auto mode / sandboxing 系から重要なのは、エージェントの自律性を上げるなら、安全境界も強化するという発想です。

たとえば、

```tone-neutral.risk
自律性低:
毎回人間確認。サンドボックスは軽めでもよい。

自律性中:
一部操作は自動。危険操作は確認。権限を限定。

自律性高:
サンドボックス必須。ネットワーク制限。secrets遮断。ログ必須。
```

です。

ガバナンス上は、**自律性レベルごとに必要な安全対策を定義する**のがよいです。

---

### 3. 開発者PC・ローカル環境をリスク領域として扱う

**重要度: 4**

Anthropic のClaude Code系では、ローカル環境で動くエージェントのリスクが重要です。

開発者PCには、

```tone-neutral.risk
- SSH鍵
- APIトークン
- .env
- private repository
- 顧客データ
- 社内資料
- 本番アクセス情報
```

がある可能性があります。

組織としては、

```tone-neutral.risk
- ローカルでAIエージェントを使うルール
- secretsを置かない運用
- sandbox利用
- 許可コマンド
- 外部送信制限
- 会社支給端末での利用方針
```

を決める必要があります。

これはコーディングエージェント導入時にかなり重要です。

---

### 4. 許可ルールを運用で育てる

**重要度: 4**

AnthropicのClaude Code系では、どの操作を許可し、どの操作を確認し、どの操作を禁止するかを実運用で調整していく発想があります。

ガバナンスでも同じです。

最初から完璧なルールは作れません。

```tone-neutral.risk
- よく使う安全な操作は自動化する
- 危険だった操作は確認対象にする
- 事故りそうな操作は禁止する
- 失敗例をルールに反映する
```

という改善が必要です。

これは重要度4です。
最初は控えめに始め、実績を見ながら広げるのが良いです。

---

## 実務で重要な順

ガバナンス系で押さえるべき順番はこうです。

| 重要度 | ポイント             | 判断への使い方             |
| --: | ---------------- | ------------------- |
|   5 | 利用範囲と責任者を明確にする   | 誰が何に使ってよいか決める       |
|   5 | データ・機密情報の扱いを決める  | 入れてよい情報とダメな情報を分ける   |
|   5 | 権限管理を組織ルールにする    | ツール・データ・操作ごとに権限を分ける |
|   5 | 人間承認ポイントを制度化する   | 外部送信・本番変更・支払いなどは承認制 |
|   5 | ログ・監査証跡を残す       | 誰が何をしたか説明できるようにする   |
|   5 | ガードレールを設計に入れる    | 入力・出力・ツール利用を制御する    |
|   5 | 自律性と安全性をセットで管理する | 自動化レベルごとに必要な対策を決める  |
|   5 | 封じ込めを運用境界として考える  | AIが触れる範囲を限定する       |
|   4 | 評価・品質基準を持つ       | 本番利用してよい品質か判断する     |
|   4 | 導入から廃止まで管理する     | 放置されたエージェントを作らない    |
|   4 | 利用者教育を行う         | 現場の危ない使い方を防ぐ        |
|   4 | ローカル環境の利用ルールを決める | 開発者PCの秘密情報を守る       |
|   4 | 許可ルールを改善する       | 失敗例をルールに反映する        |
|   3 | 製品機能を統制に使う       | 便利だが本質は運用設計         |

## 一言でいうと

ガバナンス系で一番大事なのは、これです。

```tone-good.risk
AIエージェントを誰が、どの業務で、どのデータ・権限・承認のもとで使ってよいかを決めること。
```

実務向けにはこうです。

```tone-neutral.process
1. 利用してよい業務を決める
2. 入れてよいデータを決める
3. 使ってよいツールと権限を決める
4. 人間承認が必要な操作を決める
5. ログと監査証跡を残す
6. 品質・安全性の評価基準を持つ
7. 自律性レベルごとに安全対策を決める
8. 利用者にルールを教育する
9. 使われなくなったエージェントや権限を廃止する
```

ガバナンスは、現場のスピードを止めるためのものではありません。
むしろ、**安心してAIエージェントを広げるための交通ルール**です。
