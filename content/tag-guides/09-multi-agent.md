# 09. マルチエージェント系

エージェントを役割分担させて協調させる設計を考える章です。探索、委譲、統合、レビュー、複数エージェントの責任分担を扱います。

この章を読むことで、単一エージェントで足りるか、分担の価値があるか、情報共有をどう設計するかを見直せます。詳細な参照元は章末の引用リンクを参照してください。

> **対象時点: 2026年5月**  
> この章は、2026年5月時点で公開されている主要な公式ドキュメントをもとに整理しています。最新の仕様や推奨事項は、各公式ドキュメントを確認してください。

[← トップへ戻る](../index.md) | [用語集](../domain-glossary.md)

## この章で見直せること

- 単一エージェントで足りない理由があるか
- 役割分担が明確か
- 情報共有と統合の設計があるか
- 評価やログで重複や抜け漏れを追えるか
- コスト増に見合う価値があるか

## 結論

結論から言うと、マルチエージェント系で一番大事なのは、**複数エージェントに分けること自体ではなく、「単一エージェントでは足りない理由があるときだけ、役割・情報・責任を分けること」**です。

## どの記事でも共通

### 1. まず単一エージェント・単一ワークフローで足りるか確認する

**重要度: 5**

マルチエージェント系で一番大事なのは、**いきなり複数エージェントにしないこと**です。

複数エージェントにすると、たしかに役割分担や並列探索ができます。
しかし同時に、

```tone-neutral.guideline
- 設計が複雑になる
- デバッグが難しくなる
- コストが増える
- レイテンシが増える
- エージェント間の情報伝達ミスが起きる
- 責任範囲が曖昧になる
```

という問題も増えます。

なので、最初の判断はこれです。

```tone-neutral.question-checklist
単一プロンプトで足りるか
固定ワークフローで足りるか
単一エージェントで足りるか
それでも足りない理由があるか
```

マルチエージェントは便利そうに見えますが、**複雑性を増やす設計**です。
必要性が明確な場合だけ使うべきです。

---

### 2. エージェントごとの役割を明確に分ける

**重要度: 5**

複数エージェントを使うなら、各エージェントの役割をはっきり分ける必要があります。

悪い例：

```tone-bad.risk
調査エージェントA
調査エージェントB
調査エージェントC
```

これだと、何が違うのか分かりません。

良い例：

```tone-good.definition
Planner: 調査計画を立てる
Researcher: 情報を集める
Critic: 根拠や抜け漏れを確認する
Synthesizer: 最終回答に統合する
Tool executor: ツール実行だけ担当する
```

重要なのは、

```tone-good.question-checklist
誰が何をするか
誰が何をしないか
誰が最終判断するか
誰が人間に確認するか
```

を明確にすることです。

役割が曖昧だと、エージェント同士が同じ作業を重複したり、誰も重要な確認をしなかったりします。

---

### 3. 情報共有の設計が重要

**重要度: 5**

マルチエージェントでは、各エージェントが何を知っているかがとても重要です。

単一エージェントなら、同じ会話履歴やコンテキストを見ています。
しかしマルチエージェントでは、

```tone-neutral.question-checklist
- 全員が全部の情報を見るのか
- 必要な情報だけ渡すのか
- 中間結果をどう共有するのか
- 誰が全体状態を持つのか
- 古い情報や誤情報をどう扱うのか
```

を設計する必要があります。

特に大事なのは、**情報共有しすぎても、しなさすぎても失敗する**ことです。

共有しすぎると、

```tone-neutral.guideline
コンテキストが肥大化する
重要情報が埋もれる
各エージェントの役割がぼやける
```

共有しなさすぎると、

```tone-neutral.guideline
重複作業する
前提がズレる
最終統合で矛盾する
```

マルチエージェントの成功は、かなりの部分が **情報設計** にかかっています。

---

### 4. オーケストレーター、つまり司令塔を置くか決める

**重要度: 5**

複数エージェントを使う場合、誰が全体を管理するのかを決める必要があります。

代表的にはこの2つです。

```tone-neutral.definition
中央集権型:
オーケストレーターがタスクを分解し、各エージェントへ指示し、結果を統合する

分散型:
各エージェントが互いにやり取りしながら進める
```

実務では、まず中央集権型のほうが扱いやすいです。

```tone-neutral.process
Planner / Manager
↓
Worker agents
↓
Synthesizer / Reviewer
```

のような形です。

分散型は柔軟ですが、制御が難しくなります。

なので最初は、

```tone-neutral.takeaway
全体の責任を持つエージェントを置く
```

のが安全です。

---

### 5. 最終統合・レビュー担当を決める

**重要度: 5**

マルチエージェントでは、複数の出力が出ます。
それを誰が統合し、矛盾や重複を解消するかが重要です。

たとえば調査タスクでは、

```tone-neutral.risk
Researcher A: 技術情報を調べる
Researcher B: 事例を調べる
Researcher C: リスクを調べる
```

だけでは終わりません。

最後に、

```tone-neutral.question-checklist
- どの情報を採用するか
- 矛盾する情報をどう扱うか
- 根拠が弱い情報を除外するか
- 最終回答をどう構成するか
- 不確実性をどう明記するか
```

を決める必要があります。

これを担当する Synthesizer / Reviewer / Critic が必要です。

**マルチエージェントは、分担より統合が難しい**です。
ここを軽視すると、出力が散らかります。

---

### 6. 並列化は有用だが、コストと重複に注意する

**重要度: 4**

マルチエージェントの強みの1つは並列化です。

たとえば、

```tone-neutral.guideline
- 複数の情報源を同時に調べる
- 複数の仮説を同時に検証する
- 複数の観点でレビューする
- 複数の実装案を比較する
```

には向いています。

ただし、並列化にはコストがあります。

```tone-neutral.guideline
- APIコストが増える
- 実行時間が読みにくい
- 同じ情報を何度も調べる
- 統合が難しくなる
```

なので、並列化は「速くしたいから」だけではなく、

```tone-neutral.question-checklist
独立した観点で調べる価値があるか
複数案を比較する価値があるか
```

で判断するのが良いです。

---

### 7. 評価・ログ・トレースがより重要になる

**重要度: 5**

マルチエージェントは失敗箇所が増えます。

```tone-neutral.guideline
- タスク分解が悪い
- 役割分担が悪い
- 情報共有が悪い
- 特定エージェントの出力が悪い
- 統合が悪い
- レビューが機能していない
```

どこで失敗したのか分からないと改善できません。

そのため、

```tone-neutral.question-checklist
- どのエージェントが何をしたか
- どんな入力を受け取ったか
- どんな出力を返したか
- どのツールを使ったか
- 最終回答にどの出力が使われたか
```

を追えるようにする必要があります。

単一エージェントよりも、ログ・トレースの重要性は上がります。

---

## OpenAIとAnthropicで共通

### 1. 複数エージェントは「役割分担」のために使う

**重要度: 5**

OpenAI と Anthropic で共通しているのは、マルチエージェントを単なる数の増加ではなく、**役割分担の仕組み**として扱う点です。

OpenAI では、handoff や multi-agent collaboration の文脈で、専門エージェントへ処理を渡す発想があります。
Anthropic では、multi-agent research system で、調査・探索・統合などを分けています。

共通する大事な点はこれです。

```tone-neutral.takeaway
複数にするなら、役割が違う必要がある
```

同じ能力のエージェントを何体も並べるだけでは、コストが増えるだけになりやすいです。

---

### 2. オーケストレーションが中心になる

**重要度: 5**

OpenAI も Anthropic も、マルチエージェントではオーケストレーションが重要になります。

つまり、

```tone-neutral.question-checklist
どのエージェントを呼ぶか
どの順番で呼ぶか
何を渡すか
結果をどう受け取るか
いつ止めるか
いつ人間に渡すか
```

を設計する必要があります。

マルチエージェントは、プロンプトを複数書けば終わりではありません。
**エージェント間の流れを設計すること**が本体です。

---

### 3. ハンドオフ時の情報量を制御する

**重要度: 4**

OpenAI では handoff、Anthropic では各エージェント間の情報共有に相当する話です。

あるエージェントから別のエージェントへ渡すとき、

```tone-neutral.guideline
全部の会話履歴を渡す
必要な要約だけ渡す
成果物だけ渡す
判断理由も渡す
根拠リンクも渡す
```

などの選択があります。

ここで重要なのは、

```tone-good.takeaway
次のエージェントが仕事をするために必要な情報だけ渡す
```

ことです。

情報を渡しすぎると混乱し、渡さなすぎると前提が欠けます。
これはかなり重要ですが、マルチエージェントを本格運用する段階で特に効くので重要度4です。

---

### 4. 人間確認やガードレールを組み込む

**重要度: 4**

OpenAIもAnthropicも、複数エージェントが動く場合でも、危険な処理や不確実な処理には制御が必要という立場です。

特に、

```tone-neutral.risk
- 外部送信
- コード実行
- ファイル変更
- 本番操作
- 機密情報共有
- 高リスク判断
```

では、人間確認や権限制御が必要です。

マルチエージェントになると、どのエージェントがどの権限を持つかも重要になります。

```tone-neutral.risk
全エージェントに同じ権限を渡さない
```

これは大事です。

## OpenAIのみ

### 1. Handoff を明示的な設計部品として扱う

**重要度: 4**

OpenAI の特徴は、エージェント間の引き継ぎ、つまり handoff を設計部品として扱うところです。

たとえば、

```tone-neutral.process
受付エージェント
↓
専門エージェント
↓
レビューエージェント
```

のように処理を渡します。

ここで大事なのは、

```tone-good.question-checklist
どの条件でハンドオフするか
何を渡すか
ハンドオフ先は何を担当するか
戻り値をどう扱うか
```

です。

これはOpenAIスタックで作るなら重要です。
ただし、一般原則としては「分岐・ルーティング・責任分担」の一部なので重要度4です。

---

### 2. Agents SDK 上でマルチエージェント構成を作りやすい

**重要度: 3**

OpenAIでは、Agents SDKで Agent、Handoff、Guardrail、Session、Tracing などを使って構成できます。

これは実装上便利です。

ただし、ベストプラクティスとして本質的なのはSDK機能ではなく、

```tone-neutral.guideline
役割分担
情報共有
責任範囲
評価
トレース
```

です。

なので重要度は3です。

OpenAIで実装するなら使う価値はありますが、概念整理では製品依存として扱えばよいです。

---

### 3. 専門エージェントに分ける発想がある

**重要度: 4**

OpenAIのマルチエージェント文脈では、専門性ごとにエージェントを分ける発想があります。

たとえば、

```tone-neutral.guideline
triage agent
refund agent
technical support agent
sales agent
```

のような形です。

これは実務ではかなり使いやすいです。

ただし、分ける理由が必要です。

```tone-neutral.risk
入力の種類が違う
必要なツールが違う
権限が違う
判断基準が違う
専門知識が違う
```

場合に分ける価値があります。

---

### 4. セッション・状態管理をSDK側で扱う発想がある

**重要度: 3**

OpenAIでは、Session や tracing などを通じて、エージェントの状態や履歴を管理しやすくする方向があります。

これはマルチエージェントでは重要ですが、一般原則としては製品機能寄りです。

本質は、

```tone-neutral.question-checklist
各エージェントがどの状態を見ているか
会話履歴や中間結果をどう保持するか
状態の不整合をどう防ぐか
```

です。

重要度は3〜4くらいです。

## Anthropicのみ

### 1. マルチエージェントはリサーチのような広い探索に向く

**重要度: 5**

Anthropic の `How we built our multi-agent research system` で特に重要なのは、マルチエージェントが向くタスクの条件です。

向いているのは、

```tone-neutral.guideline
- 調査範囲が広い
- 複数の情報源を探索する必要がある
- 複数の観点から検討したい
- 並列に探索したい
- 最終的に統合が必要
```

ようなタスクです。

つまり、マルチエージェントは、単純なQAや固定業務よりも、**探索・調査・統合**に向いています。

これは非常に重要です。

---

### 2. Lead agent / subagent の階層構造が重要

**重要度: 5**

Anthropicのマルチエージェント研究システムでは、中心となる lead agent がサブエージェントを管理する構造が重要です。

イメージはこうです。

```tone-neutral.definition
Lead agent:
調査計画、タスク分解、サブエージェント起動、統合を担当

Subagents:
個別の調査、探索、分析を担当
```

これは実務でも使いやすい形です。

分散型の自由会話より、まずはこのような階層型が安定します。

```tone-neutral.takeaway
司令塔を置き、作業担当を分ける
```

ということです。

---

### 3. サブエージェントには独立したコンテキストを持たせる

**重要度: 4**

Anthropicの重要ポイントとして、サブエージェントが独立したコンテキストを持てることがあります。

メリットは、

```tone-neutral.guideline
- 並列探索しやすい
- 各エージェントが特定観点に集中できる
- メインコンテキストを圧迫しにくい
- 複数の仮説を同時に検証できる
```

です。

ただし、独立コンテキストには注意も必要です。

```tone-neutral.guideline
- 前提がズレる
- 重複調査する
- 統合時に矛盾する
```

そのため、独立させるだけでなく、**戻り値の形式と統合ルール**が必要です。

---

### 4. 統合・引用・根拠管理が重要

**重要度: 5**

Anthropicのマルチエージェントリサーチで非常に重要なのが、最終的な統合です。

複数のサブエージェントが調べた情報を集めたあと、

```tone-neutral.question-checklist
- 根拠があるか
- 情報源が信頼できるか
- 矛盾がないか
- 重要情報が抜けていないか
- 引用できるか
- 最終回答として一貫しているか
```

を確認する必要があります。

リサーチ系では、調べることより **統合品質** が重要です。

マルチエージェントは情報量を増やせますが、情報品質を自動で保証してくれるわけではありません。

---

### 5. マルチエージェントはコスト・トークン使用量が大きい

**重要度: 4**

Anthropicは、マルチエージェントが効果的な一方で、コストやトークン使用量が増えることも示唆しています。

複数エージェントを使うと、

```tone-neutral.guideline
- 同時に複数モデル呼び出しが発生する
- 各エージェントが独自にコンテキストを使う
- 統合にも追加コストがかかる
- 探索範囲が広がりすぎる
```

ことがあります。

そのため、重要なのは、

```tone-good.takeaway
マルチエージェントで得られる品質向上が、コストに見合うか
```

です。

これは本番運用ではかなり重要です。

---

### 6. 評価しながら役割分担を改善する

**重要度: 4**

Anthropicのマルチエージェント記事では、システムを作って終わりではなく、評価と反復改善が重要です。

見るべきなのは、

```tone-good.question-checklist
- サブエージェントの分担は適切か
- 何度も同じ情報を調べていないか
- 重要な観点が抜けていないか
- lead agent が統合に失敗していないか
- どのエージェントが品質に貢献しているか
```

です。

マルチエージェントは構成要素が多いので、評価なしでは改善しづらいです。

---

## 実務で重要な順

マルチエージェント系で押さえるべき順番はこうです。

| 重要度 | ポイント                | 判断への使い方            |
| --: | ------------------- | ------------------ |
|   5 | まず単一エージェントで足りるか確認する | 複雑化する前に必要性を疑う      |
|   5 | 役割を明確に分ける           | 各エージェントの責務を定義する    |
|   5 | オーケストレーターを置く        | 最初は司令塔ありの階層型が扱いやすい |
|   5 | 情報共有を設計する           | 何を渡し、何を渡さないか決める    |
|   5 | 最終統合・レビュー担当を決める     | 分担より統合が難しい         |
|   5 | ログ・トレースを残す          | どのエージェントが何をしたか追う   |
|   5 | マルチエージェントに向くタスクを選ぶ  | 広い探索・複数観点・調査統合に向く  |
|   5 | 根拠・引用・矛盾を管理する       | リサーチ系では特に重要        |
|   4 | ハンドオフ条件を設計する        | いつ誰に渡すか決める         |
|   4 | 人間確認・権限制御を入れる       | 全エージェントに同じ権限を渡さない  |
|   4 | コスト・トークン使用量を見る      | 品質向上に見合うか確認する      |
|   4 | 評価しながら役割分担を改善する     | 重複・抜け漏れ・統合失敗を直す    |
|   3 | SDKのマルチエージェント機能を使う  | 便利だが本質ではない         |
|   3 | 完全分散型にする            | 制御が難しいので応用編        |

## 一言でいうと

マルチエージェント系で一番大事なのは、これです。

```tone-good.guideline
複数に分けることではなく、
単一エージェントでは難しい探索・分担・統合を、
役割と情報共有を設計して安全に行うこと。
```

実務向けにはこうです。

```tone-neutral.process
1. まず単一エージェントで足りるか確認する
2. 複数にする理由を明確にする
3. 役割を分ける
4. 司令塔を置く
5. 各エージェントに渡す情報を決める
6. 結果の形式を揃える
7. 最終統合・レビュー担当を置く
8. ログを残す
9. コストと品質改善のバランスを見る
```

マルチエージェントは、なんとなく先進的に見えるので手を出したくなります。
でも実務では、**「複数にしたら賢くなる」ではなく、「複数にしないと探索範囲・専門性・並列性が足りない」場合に使う**、くらいで考えるのが安全です。
