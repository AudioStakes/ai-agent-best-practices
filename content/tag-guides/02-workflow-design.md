# 02. ワークフロー設計系

AIに自由に任せる前に、仕事の流れをどう制御するかを考える章です。ステップ分解、承認ポイント、反復改善、失敗時の戻し方を扱います。

この章を読むことで、作業の流れ、分岐、レビュー、戻し方を見直せます。詳細な参照元は章末の引用リンクを参照してください。

> **対象時点: 2026年5月**  
> この章は、2026年5月時点で公開されている主要な公式ドキュメントをもとに整理しています。最新の仕様や推奨事項は、各公式ドキュメントを確認してください。

## この章で見直せること

- 作業をステップに切れているか
- 分岐やルーティングが明確か
- どの段階で人間確認するか
- 失敗時に戻れるか
- 固定できる流れを固定できているか

## 結論

ここでの結論は、**ワークフロー設計とは「AIに自由に任せる前に、仕事の流れをどう制御するか決めること」**です。

## どの記事でも共通

### 1. まず作業を「ステップ」に分解する

**重要度: 5**

ワークフロー設計で一番大事なのは、AIにいきなり「全部やって」と渡さず、作業をステップに分けることです。

たとえば、

```tone-neutral.guideline
調査する
分類する
判断する
実行する
検証する
修正する
人間に確認する
```

のように、AIが進む道筋を作ります。

Anthropic は prompt chaining、routing、parallelization などの形で、処理を段階化しています。
LangChain は「まず自動化したいプロセスを離散的なステップに分解する」とかなり明示的です。
Google Cloud も sequential pattern、parallel pattern、loop pattern、review pattern など、流れの形で分類しています。
OpenAI も orchestration の文脈で、複数ステップ、ツール利用、ハンドオフ、ガードレールを管理する話をしています。

なので、ワークフロー設計の第一歩はこれです。

```tone-neutral.takeaway
AIに任せる仕事を、処理単位に分解する
```

これは最重要です。

---

### 2. 各ステップの役割を明確にする

**重要度: 5**

ステップに分けるだけでは不十分で、各ステップが何をするのかを明確にする必要があります。

たとえば、

```tone-neutral.guideline
このステップは分類だけする
このステップは情報収集だけする
このステップはツールを呼ぶ
このステップは出力を評価する
このステップは人間に確認する
```

のように分けます。

LangChain は特に、LLM steps、data steps、action steps、user input steps に分けて考えています。
Anthropic も、ルーティング、評価、改善、並列処理など、各ステップの役割を分けています。
Google Cloud も、設計パターンごとに役割分担を変えています。
OpenAI も、モデル、ツール、オーケストレーション、ガードレールを分けて説明しています。

ここで大事なのは、**AIに何でもやらせるステップを作らないこと**です。

```tone-good.takeaway
曖昧な巨大ステップを作らず、責務を分ける
```

---

### 3. 固定できる流れは固定する

**重要度: 5**

ワークフロー設計系でかなり強い共通点です。

AIが自由に判断する必要がない部分は、AIに任せず固定します。

たとえば、

```tone-neutral.guideline
必ず最初に入力チェックする
必ず最後に形式チェックする
金額が一定以上なら必ず人間確認に回す
ツールAの後は必ずツールBを呼ぶ
```

のようなものです。

Anthropic は、予測可能な処理はワークフローとして組むべきだとしています。
Google Cloud は、deterministic workflow と dynamic orchestration を分けています。
LangChain も、グラフの edge を使って固定された流れを作ります。
OpenAI も、ガードレールやツール呼び出し、ハンドオフをオーケストレーションの対象にしています。

つまり、重要なのはこれです。

```tone-good.takeaway
AIが考えるべきところと、システムが制御すべきところを分ける
```

これはかなり重要です。
エージェントの失敗は、AIに考えさせすぎているところから起きやすいです。

---

### 4. 分岐・ルーティングを設計する

**重要度: 5**

ワークフロー設計では、「次に何をするか」をどう決めるかが重要です。

たとえば、

```tone-neutral.guideline
問い合わせ内容によって担当エージェントを変える
コード修正ならコーディング用フローへ進む
請求書なら会計処理フローへ進む
信頼度が低いなら人間確認へ進む
```

のような分岐です。

Anthropic は routing を代表的なワークフローパターンとして扱っています。
LangChain も routing を実装パターンとして扱っています。
Google Cloud も coordinator pattern や custom logic pattern で分岐を整理しています。
OpenAI も multi-agent collaboration や handoff の文脈で、どのエージェント・処理へ渡すかを扱っています。

ポイントは、**分岐条件を曖昧にしないこと**です。

```tone-good.takeaway
何を見て、どのルートへ進むかを決める
```

---

### 5. 評価・レビュー・修正ループを入れる

**重要度: 4**

ワークフロー設計では、AIの出力をそのまま終わりにしないことが重要です。

よく出てくる形は、

```tone-neutral.guideline
生成する
評価する
修正する
再評価する
```

です。

Anthropic は evaluator-optimizer パターンを扱っています。
Google Cloud は review and critique、iterative refinement、loop pattern を扱っています。
LangChain も evaluator-optimizer を実装パターンとして扱います。
OpenAI も出力検証、ガードレール、tracing などの文脈で、結果を確認する設計に触れています。

これは重要度4にしました。
理由は、すべての軽いタスクで必須ではないからです。
ただし、業務利用ではかなり重要です。

```tone-neutral.takeaway
重要な出力ほど、生成ステップと確認ステップを分ける
```

---

### 6. 並列化できる処理は並列化する

**重要度: 3**

複数の独立した処理がある場合、並列に走らせる設計もあります。

たとえば、

```tone-neutral.guideline
複数観点で同時にレビューする
複数の情報源を並列に調べる
複数案を生成して比較する
```

Anthropic、Google Cloud、LangChain は parallelization / parallel pattern を扱っています。
OpenAI でも複数ツールや複数エージェントの協調に近い話があります。

ただし、これは最初から必須ではありません。

まずは、

```tone-neutral.guideline
順番に処理する
分岐する
レビューする
```

が先です。
並列化は、速度や多面的検討が必要になったときに使えばよいです。

---

## OpenAIとAnthropicで共通

### 1. ワークフローは「オーケストレーション」の問題である

**重要度: 5**

OpenAI と Anthropic で共通している重要点は、ワークフロー設計を単なるプロンプト設計ではなく、**複数ステップ・ツール・判断・検証をどう流すか**の問題として扱っていることです。

OpenAI は orchestration という言葉で、

```tone-neutral.guideline
複数ステップ
ツール利用
エージェント間ハンドオフ
ガードレール
コンテキスト管理
```

を扱います。

Anthropic は workflows と agents を分け、prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer などで整理しています。

つまり共通点はこれです。

```tone-neutral.takeaway
プロンプト単体ではなく、処理全体の流れを設計する
```

これは最重要です。

---

### 2. ツール利用をワークフローに組み込む

**重要度: 5**

OpenAI も Anthropic も、エージェントやワークフローを「モデルだけ」で完結するものとして見ていません。
ツール利用が前提です。

OpenAI は built-in tools、function calling、file search、web search、code interpreter などを扱っています。
Anthropic は augmented LLM、つまりツール・検索・メモリで拡張されたLLMを基本単位にしています。

共通する重要点はこれです。

```tone-neutral.takeaway
どのステップで、どのツールを、何のために使うかを決める
```

ワークフローの中でツールの位置づけが曖昧だと、AIはかなり迷います。

---

### 3. 必要に応じて人間確認を入れる

**重要度: 4**

OpenAI と Anthropic の両方に、人間確認を残す発想があります。

OpenAI ではガードレールや human-in-the-loop の文脈で出てきます。
Anthropic でも、エージェントが途中で人間に判断を求めたり、チェックポイントで確認したりする設計が出てきます。

重要なのは、

```tone-good.takeaway
全部自動化するか、人間確認するか
```

ではなく、

```tone-neutral.takeaway
どの地点で人間確認を入れるか
```

です。

たとえば、

```tone-neutral.risk
実行前
外部送信前
高額処理前
削除前
信頼度が低いとき
```

です。

これは業務利用ではかなり重要です。

---

### 4. ワークフローを観測・デバッグできるようにする

**重要度: 4**

OpenAI は tracing を重視しています。
Anthropic も、ワークフローやエージェントは測定しながら改善するべきという立場です。

共通するのは、

```tone-neutral.question-checklist
AIがなぜその判断をしたか
どのツールを呼んだか
どこで失敗したか
```

を追えるようにすることです。

これがないと、ワークフローは改善できません。
個人利用なら軽くてもよいですが、業務化するなら重要度は5に近いです。

---

### 5. 複雑にする前に単純な流れから始める

**重要度: 5**

OpenAI も Anthropic も、いきなり複雑なマルチエージェントや動的ワークフローに行くべきではない、という考え方が読み取れます。

Anthropic は特に強く「シンプルに始める」と言っています。
OpenAI も、まず core logic を作り、必要に応じて tools や orchestration を増やしていく構成です。

共通する実務判断はこれです。

```tone-neutral.guideline
最初は単純な固定フローで作る
足りないところだけ分岐・ツール・エージェント化する
```

これはかなり重要です。

---

## OpenAIのみ

### 1. Agents SDK によるオーケストレーションを前提に整理している

**重要度: 3**

OpenAI の特徴は、ワークフロー設計をかなり実装プリミティブに寄せて説明しているところです。

たとえば、

```tone-neutral.guideline
Agent
Handoff
Guardrail
Session
Tracing
Built-in tools
```

のような単位で設計します。

これはOpenAIスタックで作るなら重要です。
ただし、ワークフロー設計の一般原則としては製品依存が強いので、重要度は3です。

---

### 2. モデル選定もワークフロー設計に含める

**重要度: 4**

OpenAI は、どのステップにどのモデルを使うかをかなり重視しています。

たとえば、

```tone-neutral.process
複雑な計画・判断 → reasoning model
低遅延な会話応答 → lighter model
ツール利用・コード生成 → 能力の高いモデル
```

のような考え方です。

ワークフロー全体で1つのモデルを使うのではなく、**ステップごとにモデルを選ぶ**という発想です。

これは実務的には重要です。
コスト・速度・精度のバランスを取りやすくなります。

---

### 3. 入力・出力のガードレールを明示的に設計要素にしている

**重要度: 4**

OpenAI は、ユーザー入力やモデル出力をどう扱うかをベストプラクティスとして整理しています。

たとえば、

```tone-neutral.risk
ユーザー入力を制限する
危険な入力を検出する
出力形式を制御する
失敗時の対応を決める
```

のような話です。

ワークフロー設計でいうと、これは **前処理・後処理ステップ** です。

```tone-neutral.process
入力チェック → 実行 → 出力検証
```

という流れを組むときに使えます。

---

### 4. 複数エージェント間の handoff を設計要素として扱う

**重要度: 3**

OpenAI は、multi-agent collaboration や handoff を設計要素として扱います。

たとえば、

```tone-neutral.guideline
受付エージェント
専門エージェント
確認エージェント
```

のように分ける設計です。

ただし、これは最初からやるものではありません。
単一ワークフローで難しくなったときに検討する応用編です。

重要度は3で十分です。

---

## Anthropicのみ

### 1. ワークフローパターンの分類が非常に明確

**重要度: 5**

Anthropic の強みは、ワークフローの基本パターンをかなりきれいに整理している点です。

代表的には、

```tone-neutral.guideline
Prompt chaining
Routing
Parallelization
Orchestrator-workers
Evaluator-optimizer
```

です。

これは非常に使いやすいです。
ワークフロー設計の型として、そのまま知識ベース化できます。

特に重要なのは、**どの型をいつ使うか**です。

```tone-good.process
段階的に処理したい → prompt chaining
入力ごとに処理を変えたい → routing
独立した処理を同時に進めたい → parallelization
タスク分解が必要 → orchestrator-workers
品質改善したい → evaluator-optimizer
```

これは重要度5です。

---

### 2. 「ワークフロー」と「エージェント」の線引きが明確

**重要度: 5**

Anthropic は、ワークフローとエージェントをかなりはっきり分けています。

```tone-neutral.definition
ワークフロー:
事前に定義されたコードパスに沿ってLLMやツールを動かす

エージェント:
LLMが自分でプロセスやツール利用を動的に決める
```

これはワークフロー設計系でかなり大事です。

なぜなら、多くの業務では「エージェント」と呼んでいても、実際にはワークフローで十分だからです。

```tone-neutral.guideline
まずワークフローで済むか考える
必要な部分だけエージェント化する
```

この判断は、設計の失敗をかなり減らします。

---

### 3. 複雑性には必ずコストがある、という警戒が強い

**重要度: 5**

Anthropic は、複雑なエージェントや多段ワークフローには、コスト・レイテンシ・デバッグ困難性があることをかなり強く警告しています。

これはワークフロー設計でも重要です。

```tone-good.guideline
ステップを増やす
分岐を増やす
ツールを増やす
エージェントを増やす
```

ほど、制御は難しくなります。

したがって、Anthropic 的には、

```tone-neutral.process
単純なプロンプト
↓
単純なワークフロー
↓
複雑なワークフロー
↓
自律エージェント
```

の順に進むべき、という読み方ができます。

---

### 4. 評価しながら反復改善する前提が強い

**重要度: 4**

Anthropic は、ワークフローやエージェントは一度作って終わりではなく、評価しながら改善するものとして扱っています。

特に evaluator-optimizer は、その考え方そのものです。

```tone-neutral.guideline
出力する
評価する
改善する
再実行する
```

これは品質が重要なタスクでは非常に有効です。

ただし、軽いタスクでは重すぎる場合もあるので、重要度は4にしました。

---

## 実務で重要な順

ワークフロー設計系で、最終的に押さえるべき順番はこうです。

| 重要度 | ポイント              | 判断への使い方             |
| --: | ----------------- | ------------------- |
|   5 | 作業をステップに分解する      | AIに丸投げせず、処理単位を作る    |
|   5 | 固定できる流れは固定する      | AIに考えさせる場所を減らす      |
|   5 | ワークフローとエージェントを分ける | 予測可能ならワークフローでよい     |
|   5 | 分岐・ルーティングを設計する    | 入力や状況に応じて正しい処理へ送る   |
|   5 | ツール利用を流れに組み込む     | どのステップで何のツールを使うか決める |
|   4 | 評価・レビュー・修正ループを入れる | 重要な出力は確認・改善ステップを分ける |
|   4 | 人間確認ポイントを設計する     | 高リスク・不可逆操作では必須      |
|   4 | ログ・トレースで観測可能にする   | 後から改善できるようにする       |
|   4 | モデルをステップごとに選ぶ     | コスト・速度・精度を調整する      |
|   3 | 並列化する             | 速度や多面的検討が必要な場合に使う   |
|   3 | マルチエージェント化する      | 単一ワークフローで限界が出たら検討する |

---

## 一言でいうと

ワークフロー設計系で一番大事なのは、これです。

```tone-good.guideline
AIに自由にやらせる前に、
仕事の流れを分解し、
固定できるところは固定し、
AIが判断すべきところだけ判断させる。
```

もう少し実務的に言うと、

```tone-neutral.process
1. まず作業手順を書く
2. 各ステップの役割を決める
3. 分岐条件を決める
4. 使うツールを決める
5. 確認・評価・人間承認ポイントを入れる
6. 必要になってから自律性を増やす
```

です。

このタグでは、**「エージェントを賢くする」より「仕事の進め方を迷わせない」こと**が中心です。
