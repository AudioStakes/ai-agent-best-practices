# Markdown記法ルール

このリポジトリのドキュメントは、GitHub上で自然に読めることを優先し、GitHub Flavored Markdown に合わせて記述する。

## 基本方針

* Markdownファイルの拡張子は `.md` とする。
* ドキュメントはGitHub上で読みやすい記法を優先する。
* 独自HTMLは必要最小限にする。
* 見た目のためだけに複雑なHTMLを書かない。
* リポジトリ内の別ファイルや画像へのリンクは、原則として相対リンクを使う。
* 重要情報の強調には GitHub Alerts を使う。

## 見出し

見出しは `#` を使って書く。

```md
# 第1階層の見出し
## 第2階層の見出し
### 第3階層の見出し
```

### ルール

* 1ページに `#` は原則1つだけ使う。
* 大きな章は `##` を使う。
* 章の中の小見出しは `###` を使う。
* 見出し階層を飛ばさない。

  * 良い例: `#` → `##` → `###`
  * 悪い例: `#` → `###`

## 段落

段落を分けるときは、空行を1行入れる。

```md
これは1つ目の段落です。

これは2つ目の段落です。
```

### ルール

* 文章を詰め込みすぎない。
* 1段落には、原則として1つの話題だけを書く。
* 箇条書きにした方が読みやすい場合は、無理に長文にしない。

## 強調

太字、斜体、取り消し線は以下の記法を使う。

```md
**太字**

*斜体*

~~取り消し線~~

**太字の中で _斜体_ を使う**

***太字かつ斜体***
```

### ルール

* 重要語句は `**太字**` を使う。
* 太字を使いすぎない。
* 斜体は日本語では読みにくくなることがあるため、原則として多用しない。
* 取り消し線は、変更履歴や「これは使わない」ことを示す場合に限定する。

## 引用

引用は `>` を使う。

```md
> これは引用文です。
```

複数行の引用も、各行の先頭に `>` を付ける。

```md
> これは引用文です。
> 複数行にできます。
```

### ルール

* 外部記事、仕様、発言などを引用するときに使う。
* 自分たちの重要メモには、原則として引用ではなく GitHub Alerts を使う。
* 引用と通常本文を混ぜない。

## インラインコード

文中のコマンド、ファイル名、変数名、コード片はバッククォートで囲む。

```md
`git status` を実行する。

`README.md` を更新する。

`agent_id` を指定する。
```

### ルール

* コマンド名、ファイル名、ディレクトリ名、設定値、変数名にはインラインコードを使う。
* 通常の日本語の強調には使わない。

## コードブロック

複数行のコードやコマンドは、トリプルバッククォートで囲む。

````md
```bash
git status
git add .
git commit -m "Update docs"
```
````

### ルール

* コードブロックには、できるだけ言語名を付ける。
* コマンド例には `bash` を使う。
* JSONには `json`、YAMLには `yaml`、Markdownには `md` を使う。
* 実行する必要があるコマンドと、単なる例は本文で区別する。

## リンク

リンクは以下の形式で書く。

```md
[リンクテキスト](https://example.com)
```

### ルール

* リンクテキストは「こちら」だけにしない。
* リンク先の内容が分かるテキストにする。
* URLをそのまま本文に貼らない。
* リンクテキストは1行で書く。

良い例:

```md
[GitHub Pagesの公式ドキュメント](https://docs.github.com/pages)
```

避ける例:

```md
[こちら](https://docs.github.com/pages)
```

## セクションへのリンク

同じページ内の見出しには、アンカーリンクで移動できる。

```md
[基本方針を見る](#基本方針)
```

英語見出しの場合、GitHubではおおむね以下のようにアンカーが作られる。

```md
## Basic Rules

[Basic Rulesを見る](#basic-rules)
```

### ルール

* 見出しを変更するとアンカーリンクも変わる可能性がある。
* 見出しへのリンクを使っている場合は、見出し名の変更時にリンクも確認する。
* 同じ見出しが複数ある場合、後ろの見出しには `-1`、`-2` のような番号が付くことがある。

## 相対リンク

リポジトリ内のファイルには、相対リンクを使う。

```md
[エージェント設計](docs/01-agent-design.md)

[ツール利用](docs/03-tool-use.md)
```

ルートからの相対パスも使える。

```md
[README](/README.md)
```

### ルール

* 同じリポジトリ内のファイルには、原則として絶対URLではなく相対リンクを使う。
* ファイルを移動した場合は、相対リンクが壊れていないか確認する。
* リンクテキストは1行で書く。

## 画像

画像は以下の形式で書く。

```md
![画像の説明](assets/images/example.png)
```

### ルール

* 画像には必ず代替テキストを書く。
* 代替テキストには、画像の内容が分かる短い説明を書く。
* リポジトリ内の画像には、原則として相対パスを使う。
* 画像ファイルは `assets/images/` など、決めた場所に置く。

良い例:

```md
![AIエージェントの処理フロー図](assets/images/agent-flow.png)
```

避ける例:

```md
![](assets/images/agent-flow.png)
```

## 箇条書き

順序のない箇条書きは `-` を使う。

```md
- エージェント設計
- ワークフロー設計
- ツール利用
```

### ルール

* 箇条書きの記号は、原則として `-` に統一する。
* `*` や `+` は使わない。
* 1項目が長くなりすぎる場合は、本文に分ける。
* 並列の項目は、文体をそろえる。

## 番号付きリスト

順番が重要な場合は番号付きリストを使う。

```md
1. 情報を集める
2. 分類する
3. 要約する
4. レビューする
```

### ルール

* 手順、優先順位、時系列には番号付きリストを使う。
* 順番が重要でない場合は、通常の箇条書きを使う。

## 入れ子のリスト

入れ子のリストは、子項目をインデントして書く。

```md
1. エージェント設計
   - 目的を定義する
   - 制約を定義する
   - 成功条件を定義する
2. ツール利用
   - 入力を確認する
   - 出力を検証する
```

### ルール

* 入れ子は深くしすぎない。
* 原則として2階層までにする。
* 3階層以上になる場合は、見出しで分ける。

## タスクリスト

作業項目はタスクリストで書く。

```md
- [x] READMEを作成する
- [ ] GitHub Pagesの設定を確認する
- [ ] Markdown記法ルールを追加する
```

### ルール

* 未完了は `- [ ]` を使う。
* 完了は `- [x]` を使う。
* タスクの文頭が括弧で始まる場合は、括弧をエスケープする。

```md
- [ ] \(任意) 補足資料を追加する
```

## GitHub Alerts

重要な情報は GitHub Alerts を使う。

```md
> [!NOTE]
> 補足情報。読み飛ばしても大きな問題はないが、知っておくと理解しやすい内容。

> [!TIP]
> 作業をよりうまく、または簡単に進めるためのコツ。

> [!IMPORTANT]
> 目的を達成するために必ず知っておくべき重要情報。

> [!WARNING]
> 問題を避けるために、すぐ注意すべき情報。

> [!CAUTION]
> リスクや悪い結果につながる可能性がある注意情報。
```

### 使い分け

| 種類          | 用途                  |
| ----------- | ------------------- |
| `NOTE`      | 補足、背景、前提            |
| `TIP`       | コツ、推奨、効率化           |
| `IMPORTANT` | 必須の原則、重要な判断基準       |
| `WARNING`   | よくある失敗、注意点、破綻しやすい設計 |
| `CAUTION`   | セキュリティ、損失、危険、重大な副作用 |

### ルール

* Alertsは本当に重要な情報にだけ使う。
* 1ページに多用しない。
* 目安として、1ページあたり1〜3個までにする。
* Alertsを連続して並べない。
* Alertsの中にさらにAlertsを入れ子にしない。
* 単なる装飾目的で使わない。

## 脚注

補足説明や出典メモには脚注を使える。

```md
本文中に脚注を付ける[^1]。

[^1]: これは脚注です。
```

複数行の脚注を書く場合は、必要に応じてインデントする。

```md
本文中に脚注を付ける[^2]。

[^2]: これは複数行の脚注です。  
    2行目の説明です。
```

### ルール

* 本文の流れを止めたくない補足に使う。
* 重要な情報を脚注に逃がさない。
* GitHub Wikiでは脚注がサポートされない場合があるため、Wiki前提の文書では使わない。

## コメント

公開表示したくないメモはHTMLコメントで書く。

```md
<!-- このコメントはレンダリング後のMarkdownには表示されない -->
```

### ルール

* 下書きメモ、レビュー用メモ、作業メモに使う。
* 公開してはいけない情報はコメントにも残さない。
* 秘密情報、個人情報、APIキーなどは絶対に書かない。

## Markdown記法のエスケープ

Markdownとして解釈されたくない文字は、バックスラッシュでエスケープする。

```md
\*これは斜体にならない\*
```

### ルール

* `*`、`_`、`#`、`[`、`]` などを記号として表示したい場合に使う。
* タスクリスト項目の文頭が括弧で始まる場合もエスケープする。

## HTMLの使用

GitHub Markdownでは一部のHTMLを使える。

```md
<sub>下付き文字</sub>

<sup>上付き文字</sup>

<ins>下線</ins>
```

### ルール

* HTMLは必要な場合だけ使う。
* 通常の強調にはMarkdown記法を優先する。
* レイアウト目的のHTMLは原則として使わない。
* GitHub Pagesで表示する場合、GitHub上のMarkdown表示と完全に同じ見た目にならないことがあるため注意する。

## 色コード

Issue、Pull Request、Discussionでは、バッククォート内の色コードが色付きで表示されることがある。

```md
`#0969DA`

`rgb(9, 105, 218)`

`hsl(212, 92%, 45%)`
```

### ルール

* 色コードは、デザインやCSSの説明で必要な場合だけ使う。
* 色コードの前後に余分なスペースを入れない。

## 絵文字

絵文字は `:EMOJICODE:` 形式で書ける。

```md
:tada:
:+1:
```

### ルール

* 技術文書では絵文字を多用しない。
* セクションタイトルや本文の意味が絵文字に依存しないようにする。
* READMEの雰囲気づくり程度に留める。

## 避ける書き方

以下は避ける。

```md
# 見出し1
### いきなり見出し3
```

```md
[こちら](https://example.com)
```

```md
![](assets/images/example.png)
```

```md
> [!IMPORTANT]
> 重要です。
> [!WARNING]
> 注意です。
> [!TIP]
> コツです。
```

```md
<div style="color: red; font-size: 24px;">
  重要です
</div>
```

## 推奨テンプレート

新しいドキュメントは、原則として次の構成で書く。

````md
# ページタイトル

このページで扱う内容を1〜3文で説明する。

> [!IMPORTANT]
> このページで最も重要な原則を書く。

## 概要

背景や目的を書く。

## ルール

- 守るべきルールを書く。
- 判断基準を書く。
- 例外があれば書く。

## 例

```md
具体例を書く。
````

## 注意点

> [!WARNING]
> よくある失敗や注意点を書く。
