05. 評価系

★は重要度を表します。★★★★★ほど、設計・運用時に優先して確認すべき項目です。

対象時点: 2026年5月

最新の仕様や推奨事項は、各公式ドキュメントを確認してください。

参照元と元記事への導線は、本文末の「対象記事」と「参考文献」を参照してください。

結論

結論から言うと、評価系で一番大事なのは、**「AIの出力が良さそうか」を見ることではなく、「エージェントが目的を達成できているかを、再現可能な形で測れるようにすること」**です。

どの記事でも共通

1. エージェントは作るだけでなく、評価できる形にする

重要度: 5

評価系で一番大事なのはこれです。

エージェントは、普通の一問一答AIよりも失敗の仕方が複雑です。

  • 間違ったツールを使う
  • 正しいツールを間違った順番で使う
  • 途中までは正しいが最後に失敗する
  • 答えは合っているが根拠が弱い
  • たまたま一回だけうまくいく
  • 前回の変更で別タスクが壊れる

そのため、単に「出力が良さそう」では足りません。

評価では、

  • このエージェントは
  • どんな入力に対して
  • どんな手順で
  • どんな結果を出せば成功なのか

を定義する必要があります。

これは最重要です。

2. 成功条件を先に決める

重要度: 5

評価を作る前に、まず「何を成功とするか」を決める必要があります。

悪い例：

  • 良い回答をする
  • うまく調査する
  • 正しくコードを書く

良い例：

  • 指定された情報源から根拠付きで回答する
  • 既存テストを壊さずにバグを修正する
  • ユーザーの問い合わせを正しいカテゴリに分類する
  • 必要なツールを使い、最終回答に不足情報を明記する

成功条件が曖昧だと、評価も曖昧になります。

評価設計では、最初にこれを決めます。

  • 何ができたら成功か
  • 何をしたら失敗か
  • どこまで許容するか

これはどの記事にも共通する最重要ポイントです。

3. 最終出力だけでなく、途中過程も見る

重要度: 5

エージェント評価では、最終回答だけを見ると失敗を見逃します。

たとえば、最終回答が正しく見えても、

  • 不要なツールを呼んでいる
  • 危険な操作をしている
  • 偶然正解している
  • 根拠を確認していない
  • 途中で不正確な情報を使っている

ことがあります。

そのため、評価では最終出力だけでなく、

  • どのツールを使ったか
  • どんな順番で進めたか
  • どこで分岐したか
  • 失敗時に回復できたか
  • 人間確認が必要な場面で止まれたか

を見る必要があります。

LangChain / LangSmith 系の記事では、この観点が特に強いです。 Anthropic も、エージェント評価ではプロセス・環境・ハーネスが重要だという立場です。

4. 評価データセットを作る

重要度: 5

評価には、テストケースが必要です。

つまり、

  • 入力
  • 期待する結果
  • 判定基準
  • 必要なら参考回答

を持った評価用データセットです。

たとえば問い合わせ分類なら、

  • 問い合わせ文
  • 正しいカテゴリ
  • 理由
  • 例外条件

コーディングエージェントなら、

  • バグ説明
  • 初期コード
  • 期待される修正
  • 通るべきテスト
  • 触ってはいけない範囲

リサーチエージェントなら、

  • 質問
  • 使ってよい情報源
  • 必要な観点
  • 期待する根拠
  • 許容されない回答

です。

評価データがないと、改善したのか悪化したのか分かりません。

これは重要度5です。

5. 回帰評価を入れる

重要度: 5

エージェントは改善したつもりで、別の能力が壊れることがあります。

たとえば、

  • ツール説明を変えたら検索は良くなったが、分類が悪くなった
  • プロンプトを強くしたら安全性は上がったが、完了率が下がった
  • モデルを変えたら速度は上がったが、複雑タスクで失敗した

こういう変化を見るには、回帰評価が必要です。

つまり、以前うまくいっていたケースが、今も通るかを見ることです。

評価系の記事では、これはかなり共通する重要ポイントです。

改善のたびに、代表的なケースを再評価する

これは本格運用では必須です。

6. 自動評価と人間評価を使い分ける

重要度: 4

すべてを自動評価するのは難しいです。

自動評価に向いているもの：

  • JSON形式が正しいか
  • 正解ラベルと一致するか
  • テストが通るか
  • 禁止語を含まないか
  • 必要な項目が含まれているか

人間評価が必要になりやすいもの：

  • 説明が分かりやすいか
  • 根拠が十分か
  • 判断が妥当か
  • ユーザーにとって役立つか
  • 微妙な品質差

LLM-as-judge も使えますが、万能ではありません。 重要な評価では、人間評価や明確なルーブリックを組み合わせるのが現実的です。

7. 評価は開発後ではなく、開発中に作る

重要度: 4

評価は最後に作るものではありません。

むしろ、エージェントを改善するたびに、

  • 今どこが壊れているか
  • 何を直したいか
  • 修正で改善したか
  • 副作用が出ていないか

を見るために使います。

Anthropic の評価系記事では、評価は開発プロセスの一部として扱われています。 LangChain も、エージェントのトレースやデータセットを使って反復改善する前提です。

最初から完璧な評価は不要ですが、最低限の評価ケースは早めに作ったほうがよいです。

OpenAIとAnthropicで共通

1. エージェント評価は、通常のLLM評価より複雑

重要度: 5

OpenAI と Anthropic の共通点として、エージェント評価は単純なチャット評価ではない、という考え方があります。

エージェントは、

  • 複数ステップで動く
  • ツールを使う
  • 外部環境に影響する
  • 途中で判断を変える
  • 失敗から回復する

ため、最終回答だけでは評価できません。

OpenAI は「agent workflows」を評価対象にし、Anthropic は「AI agents」の評価を通常のモデル評価とは分けて考えています。

これは非常に重要です。

2. タスクに応じた評価基準を作る

重要度: 5

OpenAI も Anthropic も、汎用的な1つの評価指標だけでエージェントを判断するのではなく、タスクごとに評価基準を作る必要があるという立場です。

たとえば、

カスタマーサポート

解決率、正確性、安全性、エスカレーション判断

コーディング

テスト通過、変更範囲、コード品質、既存機能の破壊なし

リサーチ

情報源の妥当性、網羅性、根拠、引用の正確さ

ツール利用

正しいツール選択、引数の正確性、失敗時の回復

です。

これは最重要です。

評価はタスク固有に作る

と覚えるとよいです。

3. 評価結果を改善サイクルに使う

重要度: 5

OpenAI と Anthropic の両方に共通するのは、評価は点数を出して終わりではなく、改善に使うものだという点です。

評価で見るべきことは、

  • どのケースで失敗したか
  • どのステップで失敗したか
  • なぜ失敗したか
  • プロンプト、ツール、モデル、ワークフローのどこを直すべきか

です。

評価結果をもとに、

  • プロンプトを変える
  • ツール説明を直す
  • ワークフローを分ける
  • 人間確認を追加する
  • モデルを変える

という改善につなげます。

これは重要度5です。

4. トレース・ログを残す

重要度: 4

OpenAI も Anthropic も、エージェントがどう動いたかを観測できることを重視しています。

評価には、最終結果だけでなく、

  • モデル呼び出し
  • ツール呼び出し
  • 入力
  • 出力
  • エラー
  • 分岐
  • 判断

のログが必要です。

ログがないと、エージェントがなぜ失敗したか分かりません。

個人利用なら軽めでもよいですが、業務化するなら重要度5に近いです。

5. 評価対象には安全性・ガードレールも含める

重要度: 4

OpenAI と Anthropic の両方で、エージェント評価には能力だけでなく安全性も含まれます。

特にツール利用型エージェントでは、

  • 危険な操作をしないか
  • 人間確認が必要な場面で止まるか
  • 権限外の情報を扱わないか
  • 不適切な外部送信をしないか
  • 不確実なときに断言しないか

を評価する必要があります。

これは、外部世界に影響するエージェントではかなり重要です。

OpenAIのみ

1. Agent workflow を評価単位として扱う

重要度: 4

OpenAI の特徴は、「エージェントそのもの」よりも、agent workflow を評価する発想が強いことです。

つまり、

  1. 入力
  2. モデル判断
  3. ツール利用
  4. ガードレール
  5. 出力

という一連の流れを評価します。

これは実務的に使いやすいです。 「エージェントが賢いか」ではなく、

この業務フローが期待通り動いたか

を見るからです。

重要度は4です。

2. OpenAI Evals / tracing / Agents SDK との接続が前提

重要度: 3

OpenAI 系の記事では、評価を OpenAI の実装スタックと結びつけて扱う部分があります。

たとえば、

  • evals
  • tracing
  • Agents SDK
  • guardrails

です。

OpenAIで実装するなら重要ですが、一般原則としては製品依存です。

ただし考え方としては、

評価と実行ログをつなぐ

という点が重要です。

3. まず小さく評価を作る方向に向いている

重要度: 4

OpenAI の評価系は、比較的「まず動く評価を作る」方向に寄っています。

たとえば、

  • 入力と期待出力を用意する
  • ワークフローを走らせる
  • 期待条件に合っているか見る
  • 失敗例を増やす

という現実的な進め方です。

これは実務ではかなり大事です。

最初から完璧な評価体系を作るより、

  • 代表ケースを10〜30個作る
  • 壊れやすいケースから評価する

くらいで始めるほうがよいです。

Anthropicのみ

1. エージェント評価を体系的に分類している

重要度: 5

Anthropic の Demystifying evals for AI agents は、評価系の中でも特に重要です。

単に「評価しよう」ではなく、

  • 何を評価するのか
  • なぜ評価するのか
  • どんな種類の評価があるのか
  • 能力評価と回帰評価をどう分けるのか
  • エージェント種別ごとに何を見るのか

をかなり体系的に整理しています。

評価系の基礎資料としては最重要です。

2. 能力評価と回帰評価を分ける

重要度: 5

Anthropic で特に重要なのが、評価の目的を分ける考え方です。

ざっくり言うと、

能力評価

このエージェントは何ができるのかを見る

回帰評価

変更後も以前できていたことができるかを見る

です。

この区別はとても重要です。

なぜなら、目的が違うからです。

  1. 新しい設計を比較したい → 能力評価
  2. 日々の変更で壊れていないか見たい → 回帰評価

この2つを混ぜると、評価の意味が曖昧になります。

3. エージェント種別ごとに評価方法が違う

重要度: 5

Anthropic は、エージェントの種類によって評価方法を変える必要があるとしています。

たとえば、

コーディングエージェント

テスト通過、バグ修正、コード品質、環境操作

会話エージェント

解決率、正確性、自然さ、安全なエスカレーション

リサーチエージェント

情報探索、根拠、引用、網羅性、統合品質

コンピュータ操作エージェント

画面操作の成功、ミスの少なさ、回復力

のように違います。

これはかなり重要です。

「エージェント評価」とひとまとめにせず、用途別に見る必要があります。

4. 評価ハーネスを設計する

重要度: 5

Anthropic の長時間エージェント系記事では、評価ハーネスが重要になります。

ハーネスとは、ざっくり言うと、

  • エージェントを実行し、
  • 環境を用意し、
  • 結果を観測し、
  • 成功・失敗を判定する仕組み

です。

コーディングエージェントなら、

  • 初期リポジトリ
  • タスク説明
  • テスト環境
  • 実行ログ
  • 成果物
  • 採点ルール

を用意します。

これは高度ですが、本格的にエージェントを使うなら非常に重要です。

5. 長時間タスクでは中間状態と環境を評価対象にする

重要度: 4

Anthropic の長時間エージェント系では、最終結果だけでなく、途中状態も重要です。

長時間タスクでは、

  • 途中で何を調べたか
  • どこまで進んだか
  • どんな仮説を立てたか
  • どのファイルを変更したか
  • 実行環境が壊れていないか
  • 途中で人間確認が必要だったか

が評価対象になります。

これは、短いQAでは不要ですが、開発・調査・業務自動化ではかなり重要です。

6. 非決定性を前提に評価する

重要度: 4

エージェントは毎回同じ経路を通るとは限りません。

そのため、

  • 一回成功したからOK
  • 一回失敗したからダメ

ではなく、

  • 複数回実行して安定性を見る
  • 成功率を見る
  • 失敗パターンを見る
  • 平均コストや時間を見る

という考え方が必要になります。

これは高度ですが、重要です。 特に本番運用や自律度の高いエージェントでは効いてきます。

実務で重要な順

評価系で押さえるべき順番はこうです。

重要度 ポイント 判断への使い方
5 成功条件を先に決める 何をもって成功か曖昧なまま作らない
5 評価データセットを作る 入力・期待結果・判定基準を持つ
5 最終出力だけでなく途中過程を見る ツール選択・分岐・回復も評価する
5 能力評価と回帰評価を分ける 新能力を見る評価と壊れていないかを見る評価を混ぜない
5 タスクごとに評価基準を作る コーディング、調査、会話で評価観点は違う
5 評価結果を改善に使う 点数ではなく、どこを直すかを見る
5 評価ハーネスを作る 本格運用では実行環境ごと評価する
4 ログ・トレースを残す なぜ失敗したか分かるようにする
4 人間評価と自動評価を使い分ける 判断品質は人間、形式やテストは自動化しやすい
4 安全性・ガードレールも評価する 危険操作や権限逸脱をチェックする
4 非決定性を前提にする 複数回実行・成功率・ばらつきを見る
3 OpenAI/ LangSmith などの評価ツールを使う 便利だが、まず評価設計が先

一言でいうと

評価系で一番大事なのは、これです。

  • エージェントが「それっぽい答え」を出したかではなく、
  • 目的を達成するための正しい手順を踏み、
  • 安全に実行し、
  • 再現可能に成功できるかを見ること。

実務向けにはこうです。

  1. 成功条件を決める
  2. 評価ケースを作る
  3. 最終出力と途中過程を見る
  4. 能力評価と回帰評価を分ける
  5. ログを残す
  6. 失敗例を増やす
  7. 評価結果でプロンプト・ツール・ワークフローを直す

評価系は、最初は地味です。 でも、エージェントを業務に入れるなら、評価がないエージェントは改善できないし、安心して任せられない、という位置づけです。
